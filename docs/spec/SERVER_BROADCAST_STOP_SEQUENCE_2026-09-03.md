# 방송 시작·종료 판단 — 서버 요청 2026-09-03

**요청은 하나다. 라이브를 끝낼 때 정지 명령을 먼저 보내고, 응답을 받은 뒤에 스트림을 닫아 달라.**

지금은 둘이 거의 동시에 나가고, 그 때문에 **정지한 단말이 방송에 다시 붙는 일**이 생긴다. 단말 쪽 방어는 넣었지만(§4), 순서를 바꾸는 것이 근본이다.

같이 정리한다 — **서버가 무엇을 보고 시작·종료로 판단하는가**(§2), 그리고 **얼마나 기다려야 하는가**(§3).

> **§3을 꼭 봐 달라.** 서버가 지금 쓰는 대기 시간 10초는 **라이브 종료에는 맞고, 라이브 시작과 파일에는 짧다.**
>
> - **라이브 시작** — `ready_timeout_sec: 30`을 보내고 있으니 대기도 **35초**여야 한다(보낸 값 + 5초)
> - **파일** — 3 MB 저장에만 40초가 걸린다

---

## 1. 바꿀 순서 (종료)

### 지금

```text
서버 ─┬─ 스트림 닫기
      └─ LIVE_STOP 발행        ← 거의 동시
```

### 바꾼 뒤

```text
서버 ── LIVE_STOP 발행
         ↓
        단말별 LIVE_RESULT 수신 대기  (최대 N초, §3.2)
         ↓
서버 ── 스트림 닫기
```

**대기 중에는 mount와 source를 유지해야 한다.** 먼저 닫으면 지금과 같아진다.

### 왜 이 순서가 필요한가

단말은 스트림이 끊기면 **끊긴 것인지 끝난 것인지 스스로 판단해야 한다.** 판단이 필요한 상황을 만들지 않는 것이 확실하다.

정지 명령이 먼저 도착하면 단말은 **멀쩡한 스트림에서 스스로 끊는다.** 해석할 일이 없다.

### 한 대만 정지시킬 때

이 경우는 **스트림을 닫지 않는다.** 마을 방송은 계속되어야 한다. `LIVE_STOP`만 그 단말에 보내고 `LIVE_RESULT`를 받으면 끝이다.

## 2. 무엇을 보고 판단하나

모든 응답은 topic `iotradio/device/<mac_nocolon>/result`, QoS 1이다.

### 2.1 라이브 시작 — `LIVE_READY`

```json
{ "type":"LIVE_READY", "ver":267, "job_id":91,
  "device":"58:e6:c5:f5:2c:ec", "ok":true, "code":"OK" }
```

**방송 한 건에 한 번만 온다.** `job_id`는 서버가 `LIVE_START`에 넣은 세션 번호다.

| `ok` | `code` | 뜻 |
|---|---|---|
| `true` | `OK` | **준비 완료.** 프레임을 보내면 바로 소리가 난다 |
| `false` | `BUSY` | 다른 방송이나 파일/OTA가 진행 중이라 못 받는다 |
| `false` | `TIMEOUT` | 제한시간 안에 준비를 못 끝냈다 |
| `false` | `BAD_FIELD` | `job_id`가 0이거나 `stream_url`이 허용되지 않는 형식이다 |

#### `ok=true`가 보증하는 것

단말은 이 응답을 보내기 전에 **둘을 끝낸다.**

```text
안내음(인트로) 재생 완료  →  코덱·앰프·녹음 준비 완료  →  LIVE_READY
```

그래서 **「프레임을 보내면 즉시 소리가 난다」**는 뜻이다. 안내음이 준비 과정에 포함되어 있어서 응답이 즉시 오지 않는다(§3.1).

#### `ok=true`가 보증하지 않는 것

**아직 스트림에 붙기 전이다.**

```text
LIVE_READY 발행  →  그다음에 Icecast 접속 시도
```

접속에 실패하면 **`LIVE_RESULT ok=false`가 뒤따른다.**

```text
LIVE_READY  ok=true       ← 준비는 됐다
LIVE_RESULT ok=false      ← 그런데 스트림에 못 붙었다
```

**`LIVE_READY ok=true`를 「방송 성공」으로 확정하면 안 된다.** 「그 단말은 준비됐다」까지다. 화면을 「대기완료」로 바꾼 뒤에도 `LIVE_RESULT ok=false`가 오면 실패로 되돌려야 한다.

### 2.2 라이브 종료 — `LIVE_RESULT`

```json
{ "type":"LIVE_RESULT", "ver":267, "job_id":91,
  "device":"58:e6:c5:f5:2c:ec", "ok":true, "code":"STOPPED_BY_SERVER" }
```

**방송 한 건에 한 번만 온다.** `job_id`가 다르면 지난 방송의 응답이므로 버린다.

| `ok` | `code` | 뜻 |
|---|---|---|
| `true` | `STOPPED_BY_SERVER` | **정상 종료.** 서버 정지 명령을 받고 끝냈다 |
| `false` | `TIMEOUT` | 방송 중 P4가 응답을 잃었다 |
| `false` | `ABORTED` | 그 밖의 이유로 끝났다 |

**셋 다 「끝났다」는 뜻이다.** `ok`는 정상 종료인지를 말할 뿐, 종료 여부가 아니다.

> `LIVE_READY`는 시작, `LIVE_RESULT`는 종료다. 한 타입이 두 뜻을 겸하지 않는다. 상세는 `SERVER_COMM_MQTT_ICECAST_HTTP_SPEC_2026-08-14.md` §5.4.

### 2.3 파일 — `FILE_RESULT`

```json
{ "type":"FILE_RESULT", "ver":267, "job_id":201,
  "ok":true, "code":"OK", "last_offset":0 }
```

**성공이든 실패든 이 하나로 온다.** 파일에는 시작 응답이 따로 없다.

| `ok` | `code` | 뜻 |
|---|---|---|
| `true` | `OK` | **정상 완료.** 받아서 저장까지 끝냈다 |
| `true` | `STOPPED_BY_SERVER` | 서버 정지 명령으로 중단했다 |
| `false` | `NET_ERROR` | 받는 중 네트워크 실패 |
| `false` | `VERIFY_FAIL` | 받았는데 검증 실패 |
| `false` | `STORAGE_FAIL` | 저장 실패 |
| `false` | `NO_MEMORY` | 메모리 부족 |
| `false` | `BAD_FIELD` | 명령 필드가 잘못됐다 |
| `false` | `NOT_ACTIVE` | 그 `job_id`로 진행 중인 것이 없다 |
| `false` | `BUSY` / `PREEMPTED_BY_LIVE` | 다른 작업 중이라 못 받는다 |

`last_offset`은 실패 지점이다. 성공이면 0이다.

### 2.4 응답이 안 올 때 — STATUS

`LIVE_READY` / `LIVE_RESULT` / `FILE_RESULT`가 **주 신호**다. STATUS는 보조다.

topic `iotradio/device/<mac_nocolon>/status`, 주기 30초.

```json
{ "type":"STATUS", "device":"58:e6:c5:f5:2c:ec", "village_id":"00000005",
  "ip":"192.168.0.43", "rssi":-36,
  "state":"IDLE", "busy":0, "live":"OFF",
  "config_version":35, "p4_fw":"...", "c6_fw":"..." }
```

| 필드 | 값 |
|---|---|
| `state` | `IDLE` `LIVE` `FILE` `RF` `OTA` `OFFLINE` |
| `busy` | `0` = 놀고 있다 |
| `live` | `OFF` `PLAYING` `RECONNECTING` |

**주기가 30초라 시작·종료 판정을 여기에 의존하면 안 된다.** 응답이 없는 단말이 실제로 어떤 상태인지 확인하는 용도다.

`live=RECONNECTING`은 **실패가 아니다.** 방송은 살아 있고 그 단말만 잠시 무음이다. 복구하면 `PLAYING`, 못 하면 `LIVE_RESULT`가 온다.

### 2.5 정지 뒤에 늦게 오는 메시지 — `job_id`로 버린다

**정지를 처리한 뒤에도 그 방송의 메시지가 한 번 더 올 수 있다.** 날아가던 중이던 것이다.

실기(2026-09-03)에서 잡힌 것이다.

```text
342352  LIVE_STOP job_id=95 수신
342365  STATUS  state=IDLE live=OFF        ← 정지 보고 완료
342719  LIVE_STATS job_id=95 ...           ← 367ms 뒤에 도착
343837  LIVE_RESULT job_id=95 ok=true
```

**서버가 `LIVE_STATS`를 「아직 방송 중」으로 읽으면 정지 직후 잠깐 되살아나 보인다.**

**규칙: 이미 종료 처리한 `job_id`의 메시지는 전부 버린다.** `LIVE_STATS`뿐 아니라 늦게 온 `LIVE_READY`, `LIVE_RESULT`도 같다.

`LIVE_STATS`는 방송 중 상태를 보여 주는 용도이지 **시작·종료 판정에 쓰는 메시지가 아니다.**

### 2.6 단말이 죽은 경우 — LWT

브로커가 대신 발행한다. 같은 status topic이다.

```json
{ "type":"STATUS", "device":"58:e6:c5:f5:2c:ec",
  "village_id":"00000005", "state":"OFFLINE" }
```

`state`가 `OFFLINE`이고 **다른 필드가 없으면** 단말이 아니라 브로커가 보낸 것이다. 그 단말은 응답을 기다릴 필요가 없다.

keepalive가 20초이므로 **끊긴 뒤 20~30초** 안에 온다.

## 3. 얼마나 기다려야 하나

### 3.1 라이브 시작 — 서버가 보내는 `ready_timeout_sec`에 **5초를 더해** 기다린다

서버는 이미 `LIVE_START`에 `ready_timeout_sec: 30`을 넣어 보내고 있다. **그 값 자체는 충분하다.**

```json
{ "type":"LIVE_START", "job_id":91, "ready_timeout_sec":30, ... }
```

준비에 걸리는 시간은 짧다.

| | |
|---|---|
| 안내음 | 최대 **5초**에서 잘린다. 현재 파일은 그보다 짧다 |
| 그 뒤 준비 | 코덱·앰프·녹음. 짧다 |

**30초는 넉넉하다.** 안내음을 훨씬 긴 것으로 바꿔도 견딘다.

#### 문제는 서버가 기다리는 시간이다

**단말은 받은 값에 여유 5초를 더해서 잰다.** P4와 C6가 같은 값을 쓴다.

```text
서버가 보낸 값  30초
단말이 재는 값  30 + 5 = 35초      ← 답이 늦어도 여기까지는 온다
```

30초를 보내고 **서버도 30초만 기다리면 5초 구멍이 남는다.**

```text
30초  서버가 실패로 처리
32초  단말이 준비를 마치고 LIVE_READY ok=true 발행
      → 서버가 실패로 본 단말에서 소리가 나기 시작한다
```

**권고: 30을 보내고 서버는 35초를 기다린다.**

화면에 보이는 값을 30초로 유지하고 싶으면 반대로 맞춰도 된다 — **`ready_timeout_sec: 25`를 보내고 30초를 기다린다.** 어느 쪽이든 **「보낸 값 + 5초」**만 지키면 된다.

#### 값을 안 보내면

단말이 **기본 30초**를 쓴다. 지금은 서버가 보내고 있으므로 해당 없지만, 빠뜨리면 위와 같은 어긋남이 생긴다.

> `ready_timeout_sec`는 **1~60** 범위다. 벗어나면 단말이 기본값 30으로 되돌린다.

#### 시간이 지나면 단말도 알려 준다

35초까지 준비를 못 끝내면 단말이 **`LIVE_READY ok=false code=TIMEOUT`**을 보낸다. 서버가 35초를 기다리면 **침묵 대신 이 응답을 받는다** — 그 단말이 왜 실패했는지가 로그에 남는다.

### 3.2 라이브 종료 — 10초

실기에서 잰 값이다.

```
+0ms      LIVE_STOP 도착
+1494ms   LIVE_RESULT 발행
```

P4가 오디오를 정리하는 시간이라 **즉시 오지 않는다.** 1초 안에 안 온다고 이상한 것이 아니다.

**10초 유지를 권한다.**

### 3.3 파일 — **10초는 짧다**

**여기가 라이브와 다르다.**

파일은 다 받은 뒤 **검증하고 저장하는 구간**이 있고, 이 구간이 길다.

| | |
|---|---|
| 저장 속도 | LittleFS 약 80~100 KB/s |
| 3 MB 파일 | **약 40초** |
| 단말이 스스로 기다리는 한계 | **120초** (`FILE_END_RESULT_TIMEOUT_MS`) |

**10초로 끊으면 정상 동작을 실패로 본다.** 단말은 멀쩡히 저장 중인데 서버만 포기한 상태가 되고, 실제 `FILE_RESULT`는 그 뒤에 도착한다.

**권고: 크기에 비례하게 둔다.** 예: `10초 + (파일 KB / 80)초`.

고정값을 쓰겠다면 **120초**가 안전하다 — 단말이 스스로 포기하는 값과 같아진다. 그보다 길게 잡을 이유는 없다.

### 3.4 서버가 관리할 값 — **셋이다**

설정 화면에 두는 것을 권한다. 자주 바꿀 값은 아니므로 **방송 화면이 아니라 시스템/관리자 설정**이 맞다.

| 설정 | 기본 | 단말에 전달 | 범위 |
|---|---|---|---|
| **라이브 준비 제한** | **30초** | **예** — `LIVE_START.ready_timeout_sec` | 1~60 |
| **라이브 종료 대기** | **10초** | 아니오 | — |
| **파일 대기** | **120초** | 아니오 | — |

#### 「라이브 시작 대기」는 설정으로 두지 말 것

**위의 「라이브 준비 제한」에서 계산해서 나온다.**

```text
라이브 시작 대기 = ready_timeout_sec + 5
```

`+5`는 **단말 펌웨어에 박혀 있는 값**이라 서버가 정하는 것이 아니다. 별도 설정으로 두면 둘이 어긋나고, 어긋나면 §3.1의 구멍이 다시 열린다.

**한 값만 설정하게 하고 대기는 서버가 계산한다.**

#### 타임아웃은 상한이지 고정 대기가 아니다

**단말이 모두 응답하면 그 자리에서 끝난다.** 타임아웃은 안 오는 단말을 언제까지 기다릴지일 뿐이다.

```text
10대 중 10대가 1.5초에 응답  →  1.5초에 종료 처리. 10초를 채우지 않는다
10대 중 9대만 응답           →  나머지 하나를 기다리다 제한시간에 포기
```

**그래서 값을 넉넉히 잡아도 정상 동작에서는 비용이 없다.** 특히 파일은 120초로 둬도 대부분 훨씬 빨리 끝난다 — 죽었거나 느린 단말에서만 그 시간을 다 쓴다.

**빠듯하게 조이는 쪽이 오히려 손해다.** 멀쩡한 단말을 실패로 기록하게 된다.

### 3.5 시간이 지나면

**그 단말은 「응답 없음」으로 처리하고 다음으로 넘어간다.**

라이브 종료는 그 시점에 **스트림을 닫는다.** 응답 없는 단말 하나 때문에 방송을 붙들고 있을 이유가 없다 — 단말에도 자체 종료 경로가 있다.

늦게 도착한 응답은 **`job_id`로 걸러 버린다.**

## 4. 단말 쪽에도 방어를 넣었다

`iot_radio_slave` 커밋 `71b5d63`.

서버가 순서를 바꾸면 이 경로는 거의 쓰이지 않는다. 다만 **진짜 네트워크 끊김이 정지와 겹치는 경우**는 서버가 막을 수 없어서 단말이 막는다.

### 무엇이었나

실기 로그(2026-09-02)다.

```
0ms      서버가 스트림 닫음 + LIVE_STOP 발행
3ms      단말이 정지 처리
571ms    단말이 다시 접속       ← 정지했는데
2252ms   404를 받고 포기
```

재시도 루프가 **「정지하라고 했나?」를 한 순간에만** 확인했고, 정지는 그 확인을 3ms 지나서 도착했다.

이번에는 mount가 사라져 404로 끝났지만, **한 대만 정지시킨 경우에는 mount가 살아 있어 소리가 되살아난다.**

### 상태 보고도 뒤집혀 있었다

```
+22ms      STATUS  state=IDLE  live=OFF            ← 맞는 보고
+45ms      STATUS  state=LIVE  live=RECONNECTING   ← 덮어씀
+30.2초    STATUS  state=IDLE  live=OFF            ← 주기 보고로 겨우 정상화
```

**서버가 정지를 확인해 놓고 30초 동안 방송 중으로 보게 된다.** 이것도 같이 고쳤다.

### 실기 확인 (2026-09-03)

같은 경합이 다시 일어난 회차를 잡았고, 재접속하지 않았다.

```text
304074  LIVE_STOP job_id=94 수신
304076  HTTP stream closed by server        ← 2ms 차이. 같은 경합이다
304077  [LIVE] stop session=94
304090  STATUS  state=IDLE live=OFF
304116  command stream stopped by request   ← 재접속 없이 종료
```

**수정 전이라면 여기서 `retry 1/3` 뒤 571ms에 다시 붙었다.** 3회 모두 재접속·상태 역전이 없었다.

같이 잰 값이다. 편차가 20ms 안쪽이다.

| | 3회 |
|---|---|
| `LIVE_START` → 준비 완료 | **2,250 / 2,272 / 2,302 ms** |
| `LIVE_STOP` → `LIVE_RESULT` | **1,482 / 1,485 / 1,485 ms** |

**§3의 권고 값(준비 30초, 종료 10초)은 실측의 10배 이상 여유가 있다.**

## 5. 요약

### 판단 기준

| 무엇 | 신호 | 성공 |
|---|---|---|
| **라이브 시작** | `LIVE_READY` | `ok=true code=OK`. **단, 방송 성공 확정이 아니다** — `LIVE_RESULT ok=false`가 뒤따를 수 있다 |
| **라이브 종료** | `LIVE_RESULT` | `ok` 무관하게 **왔으면 끝난 것** |
| **파일 완료** | `FILE_RESULT` | `ok=true code=OK` |
| **응답 없음 확인** | STATUS `state`/`busy`/`live` | 주기 30초. 보조용 |
| **단말 사망** | LWT `state=OFFLINE` | 기다릴 필요 없음 |

전부 `job_id`로 맞춰 보고, 다르면 버린다.

**이미 종료 처리한 `job_id`의 메시지는 늦게 와도 버린다**(§2.5). 특히 `LIVE_STATS`는 정지 뒤에 한 번 더 도착할 수 있고, 이것을 「방송 중」으로 읽으면 정지 직후 되살아나 보인다.

### 대기 시간

**서버가 설정으로 가질 값은 셋이다**(§3.4). 「라이브 시작 대기」는 설정이 아니라 계산 결과다.

| 설정 | 기본 | 단말에 전달 |
|---|---|---|
| **라이브 준비 제한** | **30초** | **예** — `LIVE_START.ready_timeout_sec` |
| **라이브 종료 대기** | **10초** | 아니오 |
| **파일 대기** | **120초** | 아니오 |

```text
라이브 시작 대기 = 라이브 준비 제한 + 5   ← 서버가 계산. 설정으로 두지 말 것
```

`+5`는 단말 펌웨어 상수다. 별도 설정으로 두면 어긋난다.

**타임아웃은 상한이지 고정 대기가 아니다.** 모두 응답하면 그 자리에서 끝나므로, 넉넉히 잡아도 정상 동작에서는 비용이 없다.

### 순서

| | |
|---|---|
| 라이브 종료 | `LIVE_STOP` → 응답 대기 → **그다음** 스트림 닫기 |
| 대기 중 | mount와 source 유지 |
| 한 대만 정지 | 스트림을 닫지 않는다 |
