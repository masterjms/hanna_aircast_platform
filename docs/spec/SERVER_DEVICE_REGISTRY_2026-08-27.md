# 서버 구현 지시서: 단말 등록과 마을 배정

단말 하나하나를 서버에 등록하고, 어느 마을 방송을 듣게 할지 정하는 부분이다.

TLS 전환(`SERVER_TLS_HOST_HANDOFF_2026-08-23.md`)에서 분리했다. 그쪽은 "어디에 어떻게 붙는가"이고 이 문서는 "붙은 단말이 누구인가"라 성격이 다르다.

**아직 확정이 아니다.** `village_id` 형식은 양쪽 다 정하지 못했고, 아래는 단말 쪽 의견과 그 근거다. 최종은 서버가 정한다.

## 1. 무엇이 무엇을 식별하는가

먼저 이것부터 맞춰야 나머지가 풀린다. **세 계층이고, 각각 다른 것을 가리킨다.**

| 계층 | 키 | 가리키는 것 | 정하는 주체 | 바뀌나 |
|---|---|---|---|---|
| 전체 | 없음 (`all`) | 전 단말 | 고정 | 안 바뀜 |
| 마을 | `village_id` | **같은 방송을 듣는 묶음** | 서버 배정 | **한 번 정하면 안 바뀜** |
| 단말 | **MAC** | 그 기계 한 대 | 공장에서 자동 | 절대 안 바뀜 |

topic도 이 셋을 그대로 따른다.

```text
iotradio/all/cmd                        전체 방송
iotradio/village/<village_id>/cmd       마을 방송
iotradio/device/<mac_nocolon>/config    그 한 대
```

### 사람에 대한 것은 topic에 넣지 않는다

이름, 주소, 번지, 전화번호는 **서버 DB에만 둔다.** topic에도 단말에도 들어가지 않는다.

그래야 주민이 이사하거나 이름이 바뀌어도 **DB 한 줄만 고치면 되고** 단말은 손대지 않는다. 개인정보가 브로커를 지나다니지 않는 효과도 같이 얻는다.

**주소는 DB, 방송은 topic.** 이 한 줄이 아래 내용 전부의 기준이다.

## 2. village_id

### 2.1 단말이 이 값을 쓰는 방식

- `iotradio/device/<mac_nocolon>/config`의 retained 메시지로 받는다.
- 받은 값을 `iotradio/village/<village_id>/cmd` topic에 그대로 끼워넣어 구독한다.
- STATUS 발행 시 그대로 되돌려준다.

**단말은 값의 의미를 해석하지 않는다.** 자리수나 구성 규칙을 알 필요가 없다. 그래서 **형식은 서버가 정하면 된다.**

### 2.2 단말이 받는 자리수 (2026-08-27 반영 완료)

**단말은 8~16자리 숫자를 모두 받는다.** 서버가 몇 자리로 정하든 펌웨어를 다시 건드리지 않는다.

예전에는 8자리 고정이었는데 그건 첫 시험에 쓴 숫자이지 설계 결정이 아니었다. **서버가 형식을 정하는 데 단말이 걸림돌이 되지 않도록** 먼저 열어 두었다.

| | |
|---|---|
| 허용 | 숫자 8~16자리 |
| 미배정 | **전부 `0`** (자리수 무관). 이 값이면 마을 topic을 구독하지 않는다 |
| 거절 | 숫자가 아니거나 범위 밖. 로그를 남기고 이전 값을 유지한다 |

미배정 판정은 특정 문자열과 비교하지 않고 **"전부 0인가"** 로 한다. `00000000`이든 `000000000000`이든 같게 다룬다.

topic에 들어가는 값이므로 `/`, `+`, `#`는 쓸 수 없다. 숫자만 쓰면 안전하다.

### 2.3 한 village_id에 단말이 여러 대인 것은 정상이다

`village_id`는 위치가 아니라 **"같은 방송을 듣는 묶음"** 이다. 이름 때문에 주소처럼 읽히지만, 배정 기준은 주소가 아니라 **"이 단말들이 같은 방송을 받아야 하는가"** 하나다.

| 상황 | 배정 |
|---|---|
| 같은 마을에 스피커 여러 대, 같은 방송 | **전부 같은 값** (10대든 100대든) |
| 같은 리 안에서 서로 다른 방송 (마을회관 / 경로당) | 연번을 다르게 (`...2101`, `...2102`) |

**연번은 "단말 번호"가 아니라 "방송 그룹 번호"다.** 같은 마을 단말 3대에 `01`, `02`, `03`을 주면 마을 방송이 세 갈래로 갈라져서, 마을 하나에 방송 한 번 하려고 서버가 topic 세 개에 발행해야 한다.

**단말을 구분하려고 `village_id`를 나눌 필요는 없다.** 개별 단말은 MAC으로 유일하게 지정되고, 그 경로(`device/<mac_nocolon>/config`)가 이미 있다.

### 2.4 의견: 법정동코드(10) + 마을 연번(2) = 12자리

```text
4684033021 01
──────────┬─ ─┬
 법정동코드   그 리 안의 마을 번호
```

법정동코드는 **시도(2) + 시군구(3) + 읍면동(3) + 리(2)** = 10자리이고, **마지막 2자리가 `리`다.** 마을 방송은 원래 리 단위로 운영되므로 행정 코드 단위와 운영 단위가 그대로 맞는다.

예: `4684033021` = 전라남도 무안군 청계면 월선리.

뒤 2자리 연번은 **한 리에 방송 그룹이 둘 이상일 때**를 위한 것이다. 대부분 `01`이고 필요할 때만 늘린다.

- 시도 코드에 `00`이 없으므로 전부 `0`인 미배정 값과 충돌하지 않는다.
- 코드값은 행정안전부 공식 자료를 기준으로 한다. 받는 곳과 자동으로 채우는 방법은 2.5 참고.

### 2.5 코드는 사람이 치지 않는다 — 주소 검색 API를 붙일 것

**등록 화면에서 운영자가 법정동코드를 직접 입력하게 만들지 말아달라.** 10자리 숫자를 손으로 치면 반드시 틀리고, 틀린 값은 "방송이 안 온다"로만 나타나 원인을 찾기 어렵다. 단말 MAC을 바코드로 찍게 만든 것과 같은 이유다.

행정안전부 주소 검색 API를 쓰면 **주소 한 번 검색으로 세 가지가 한꺼번에 채워진다.**

```text
운영자가 주소를 검색
   |
   +-- roadAddr   -> DB 주소 (도로명, 정본)
   +-- jibunAddr  -> DB 주소 (지번, 구주소)
   +-- admCd (10) -> village_id 앞 10자리
```

운영자가 고르는 것은 **뒤 2자리 연번뿐**이고, 대부분 `01`이다.

- 실시간 주소정보 조회(검색API): https://www.data.go.kr/data/15057017/openapi.do
- 주소정보 API 연계 안내: https://business.juso.go.kr/jst/jstRoadNmAddrApiSearch

#### 구주소와 도로명주소를 같이 쓰는 문제도 여기서 풀린다

농촌에서는 주민이 지번(구주소)으로 부르고 공문서는 도로명으로 오는 일이 흔하다. **위 API는 두 표기를 같이 돌려주므로 둘 다 DB에 저장하면 된다.** 어느 쪽으로 검색해도 같은 단말을 찾는다.

도로명 전환은 **주소 표기 방식**을 바꾼 것이지 법정동이라는 구역 단위를 없앤 것이 아니다. 법정동코드는 지금도 행정안전부가 현행으로 관리한다(폐지분 포함 20,560건).

#### 확인해야 할 것: admCd가 법정동코드인가

juso 문서는 이 필드를 **"행정구역코드"** 라고만 부른다. **법정동코드인지 행정동코드인지 실제 응답으로 확인해달라.** 농촌은 리 단위까지 내려가야 하므로 이게 갈리면 마을 전체가 엉뚱한 id를 받는다.

행정동코드로 나온다면 `admCd`를 쓰지 말고 법정동코드 원본 자료로 매핑한다.

- 법정동코드 목록조회: https://www.code.go.kr/stdcode/regCodeL.do
- 행정안전부_행정표준코드_법정동코드 (API): https://www.data.go.kr/data/15077871/openapi.do

목록에 **법정동코드(주민)** 과 **법정동코드(지적)** 두 종류가 있고 현행/폐지 필터가 따로 있다. 어느 쪽을 기준으로 할지도 같이 정해달라.

### 2.6 형식보다 중요한 것: 한 번 배정한 값은 바꾸지 않는다

어떤 형식으로 정하든 **이 규칙은 같이 정해두는 게 좋다.**

행정구역은 통합·분리로 코드가 바뀐다. 그때 `village_id`를 따라 바꾸면 **그 지역 전 단말을 재설정**해야 하고, 서버의 과거 방송 이력도 그 시점에서 끊긴다.

앞 10자리는 **배정 시점에 사람이 알아보라고 넣는 값이지 실시간 조회 키가 아니다.** 행정 코드가 바뀌면 서버 DB의 주소 속성만 갱신하고 ID는 그대로 둔다.

이걸 명시해두지 않으면 개편이 있을 때마다 "코드가 바뀌었으니 ID도 바꾸자"는 논의가 반복된다.

### 2.7 대안: 순수 일련번호

`00000001`, `00000002` … 로 가는 방법도 있다. 지금 쓰고 있는 방식이고, **행정구역 변경과 무관해서 절대 틀릴 일이 없다.**

대신 값만 봐서는 위치를 알 수 없어, 마을이 늘어나면 로그를 볼 때마다 DB를 조회해야 한다. **운영 규모가 작게 유지될 계획이면 이쪽이 더 단순하다.**

## 3. 단말 등록 정보 — 가정집 하나하나

단말은 가정집에 설치된다. `village_id`는 **월선리까지만** 내려가고, 그 아래(어느 집인지)는 **MAC이 이미 해결하고 있다.** 번지를 ID에 넣지 않는다.

### 3.1 왜 번지를 ID에 넣지 않는가

| | |
|---|---|
| 주소는 바뀐다 | 도로명 전환, 지번 분할·합병이 실제로 일어난다. ID가 따라 바뀌면 단말을 다시 설정해야 한다 |
| 한 집에 두 대일 수 있다 | 안채와 창고에 각각 달면 번지가 같아 ID가 겹친다 |
| MAC은 이미 유일하다 | 공장에서 자동으로 붙는다. 번지는 사람이 친다 — 없애려던 오타 경로다 |

**주소는 ID가 아니라 DB 속성이다.** 그래야 이사·개축·행정구역 개편에 ID를 안 건드린다.

### 3.2 등록 항목

**키는 MAC이다.** 생산에서 화면의 바코드/QR로 찍어 넣는다(`PRODUCTION_PROVISIONING_SPEC.md` §3). 나머지는 전부 이 행에 붙는 속성이다.

| 항목 | 필수 | 용도 |
|---|---|---|
| **MAC** | **키** | 단말 식별. `client_id`와 같은 값 |
| **표시 이름** | **사실상 필수** (3.3 참고) | 모니터링·개별 방송에서 누구인지 고르는 값 |
| `village_id` | 방송에 필요 | 마을 방송을 받으려면 배정돼야 한다 |
| 도로명주소 | 선택 | 주소 검색 API가 자동으로 채움 |
| 지번주소(번지) | 선택 | 같이 자동으로 채움. 현장 출동 시 실제로 찾아가는 값 |
| **상세주소(동/호)** | 선택 | **사람이 입력하는 유일한 주소 항목** (3.2.1) |
| 전화번호 | 선택 | 연락 |
| 특이사항 | 선택 | 설치 위치, 접근 방법 등 자유 메모 |
| 단말 모델/버전 | 자동 | QR에 이미 들어 있다. 사람이 칠 필요 없음 |

**강제 입력은 MAC 하나뿐이다.** 나머지를 비워도 등록은 된다. 생산 라인에서 바코드만 찍고 넘어갈 수 있어야 하기 때문이다.

#### 3.2.1 상세주소(동/호) 입력칸을 두어야 한다

주소 검색 API는 **건물까지만** 돌려준다. 다세대·다가구라 한 건물에 세대가 여럿이면 그 아래는 채워지지 않는다.

```text
검색 결과   무안군 청계면 OO로 12          <- 여기까지 자동
사람 입력   201호                         <- 여기부터 수동
```

우편번호 검색에서 "상세주소를 입력하세요" 칸이 따로 뜨는 것과 같다. **주소 항목 중 사람이 치는 것은 이것뿐이다.**

API 응답의 **`bdKdcd`(공동주택 여부)** 로 이 칸을 띄울지 정하면, 단독주택을 등록할 때 빈 칸이 걸리적거리지 않는다.

**`village_id`에는 영향이 없다.** 201호도 101호도 같은 건물이고 같은 리이므로 **같은 마을 방송을 듣는다.** 한 건물에 단말 두 대가 있고 둘 다 같은 값을 받는 것이 정상이다(2.3).

동/호가 필요한 이유는 방송 라우팅이 아니라 **목록 표시**다. 한 건물에 두 대면 주소가 똑같이 나와서, 목록만 보고는 어느 것이 201호인지 알 수 없다.

### 3.3 표시 이름 — 비어 있으면 MAC을 쓴다

개별 단말에 방송하려면 **운영자가 목록에서 누구인지 골라야 한다.** 그렇다고 이름을 필수 입력으로 막으면 생산 등록이 멈춘다 - 그 자리에서 주민 이름을 알 수 없는 경우가 대부분이다.

**규칙은 하나다.**

```text
표시 이름 = 이름이 있으면 이름, 비어 있으면 MAC
```

| 상태 | 목록 표시 |
|---|---|
| 이름을 넣었을 때 | `홍길동집` |
| 비워 뒀을 때 | `58e6c5f2cc74` |

마을이나 호수를 조합해 이름을 만들지 않는다. 그렇게 하면 같은 마을에 같은 호수가 또 생겼을 때의 중복 처리, 마을이 아직 배정되지 않았을 때의 예외까지 서버가 전부 만들어야 한다. **MAC은 항상 있고 항상 유일하므로 그 경우들이 없다.**

- **입력을 막지 않는다.** 생산에서는 바코드만 찍고 지나간다.
- **목록은 항상 읽힌다.** 빈 칸이 생기지 않는다.
- **나중에 이름을 채우면 그때부터 이름이 보인다.**

이름 길이는 화면 정렬을 위해 **10글자 안팎**으로 제한하는 것을 권한다.

### 3.4 이름이 없어도 개별 방송은 된다

MAC이 표시되므로 **비워 둔 단말에도 개별 방송은 된다.** 다만 그 MAC이 누구 집인지는 운영자가 따로 알아야 한다.

**즉 이름 입력은 "방송을 가능하게 하는 조건"이 아니라 "운영을 쉽게 만드는 값"이다.** 그래서 필수로 걸 이유가 없다.

목록에 이름과 함께 **주소를 같이 보여주면** 이름이 비어 있어도 어느 집인지 짐작이 된다.

### 3.5 등록 화면 흐름 (권장)

```text
1. 바코드/QR 스캔        -> MAC, 모델, 버전이 한 번에 들어감
2. 그 집 주소를 검색      -> 도로명·지번(번지)·법정동코드가 한 번에 들어감
3. 상세주소(동/호)        -> 공동주택일 때만. 선택
4. 연번 선택             -> 대부분 01. village_id 완성
5. 이름/전화/특이사항     -> 선택. 비워도 저장됨
```

**사람이 직접 치는 것은 2번의 검색어, 3번, 4번의 두 자리, 5번뿐이다.** 나머지는 스캔과 검색으로 채워진다.

#### 번지도 사람이 치지 않는다

2번에서 검색하는 것은 **그 가정집의 주소**다. 그 응답 하나에 **집 주소(도로명·번지)와 마을 코드가 같이 들어 있다** - 번지를 알면 그 번지가 속한 리도 아는 것이기 때문이다.

```text
운영자가 "월선리 123-4"를 검색
   |
   +-- roadAddr   무안군 청계면 OO로 12        -> 그 집 도로명주소
   +-- jibunAddr  무안군 청계면 월선리 123-4   -> 그 집 번지
   +-- admCd      4684033021                  -> 월선리 = village_id 앞 10자리
```

**한 집씩 등록할 때마다 주소를 한 번 검색하면, 그 집 주소와 마을 배정이 같이 끝난다.** 마을 코드를 따로 찾아 넣는 단계가 없다.

`PRODUCTION_PROVISIONING_SPEC.md` §3.2.2에 QR 문자열을 쪼개는 방법이 있다. **앞 5개만 해석하고 뒤는 무시하도록** 만들어 두면 나중에 QR 항목이 늘어도 서버가 깨지지 않는다.

### 3.6 등록되지 않은 MAC

`history.txt`에 이미 적혀 있는 요건이다.

> 서버에서 등록이 되지 않은 단말기 MAC 이 접속이 되면 거절해야 한다

이건 브로커 ACL과는 다른 층이다. ACL은 "이 계정이 이 topic을 쓸 수 있는가"를 보고, 이쪽은 "이 MAC이 우리가 아는 단말인가"를 본다. **미등록 단말은 접속은 되더라도 방송 대상 목록에 넣지 않는 것으로 충분하다** — 브로커에서 끊으려면 단말마다 계정을 나눠야 해서 운영이 무거워진다.
