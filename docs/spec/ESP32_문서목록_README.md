# 이 폴더의 문서

MQTT + Icecast 기반 마을 방송 단말(ESP32-P4 + C6)의 사양이다.

문서는 **누가 보는가**로 나뉜다. 서버 팀에 넘기는 것, 우리가 보는 것, 지나간 기록.

---

## 서버에 넘길 문서 — 6개

| # | 문서 | 답하는 것 |
|---|---|---|
| 1 | `SERVER_COMM_MQTT_ICECAST_HTTP_SPEC_2026-08-14.md` | **무엇을 주고받나** — topic, 페이로드 필드, QoS, retain, 에러 코드, ACL(§2.1) |
| 2 | `SERVER_TLS_HOST_HANDOFF_2026-08-23.md` | **어디에 어떻게 붙나** — 인프라, URL 구조, 인증서, 브로커 계정(§5.2), 접근 제어(§5.1) |
| 3 | `SERVER_DEVICE_REGISTRY_2026-08-27.md` | **붙은 단말이 누구인가** — `village_id` 형식, 단말 등록 항목, 주소 검색 API |
| 4 | `SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md` | **단말별 브로커 계정** — username = 단말 MAC, password 8자. **확정.** 서버 재량은 §5 |
| 5 | `SERVER_VILLAGE_STREAM_URL_POLICY_2026-08-21.md` | **마을 배정이 어떻게 전달되나** — CONFIG topic 분리, `stream_url` 발행 정책 |
| 6 | `DEVICE_REGISTRATION_FLOW_SPEC_2026-08-29.md` | **등록 화면을 어떻게 만드나** — 사전등록·생산·설치·운영 네 그룹, 화면 구성, 1차 범위 |

**1번이 통신 계약의 기준이다.** 2~5는 1번을 각 방향으로 파고든 문서다.

**6번은 등록 흐름의 정본이다.** 서버가 지금 만들 화면 넷(마을 관리 / 단말 관리 / 단말 상세 / 등록 모드)이 거기 있다. **처음이면 6번부터 읽으면 구성이 보인다.**

### 부분만 필요한 것

| 문서 | 서버가 볼 곳 |

| `PRODUCTION_PROVISIONING_SPEC.md` | **§3.2.2** QR 문자열 쪼개기 · **§4.4.1** 시리얼 명령 목록 · **§4.5** `@GET` 응답 형식 · **§6** 등록 절차와 서버 작업 목록 |

나머지는 단말 UI와 시리얼 프로토콜이라 서버와 무관하다. 다만 §3의 바코드/QR이 **등록의 1단계**라 3번 문서 §3.5와 이어진다.

## 서버 회신을 기다리는 것

| 문서 | 요청 |
|---|---|
| 2번 §5.2 | **단말별 계정 발행** — username = 단말 MAC, password는 MAC별 8자 |
| 2번 §5.1 | ACL을 **`%u`** 로 (topic 목록은 1번 §2.1) |
| 3번 §4 | **12자리를 그대로 쓸지**, `admCd` 종류 확인, 미등록 MAC 처리 |
| 3번 §2.6 | **"한 번 배정하면 안 바꾼다"** 규칙 합의 |
| 4번 §5 | password 조합 방식, 브로커 계정 등록 방식 — **서버 재량이라 통보만** |
| — | 이 단말 마을 배정 (지금 `00000000`) |

**3번 §4에 결정 항목이 표로 모여 있다.** 그 표만 회신받아도 된다.

**막혀 있는 것은 없다.** `village_id`는 기본값(12자리)이 있고 나머지는 서버가 정하면 된다.

## 새 내용을 어디에 적나

같은 내용을 두 곳에 적으면 **반드시 한쪽이 먼저 낡는다.** 실제로 STATUS `state` 표와 LWT 설명이 양쪽에 있었고 2026-08-25에 걷어냈다.

- **선 밖으로 나가는 것** → 서버 사양서
- **선 안에서 벌어지는 것** → 장치 사양서

양쪽에 다 해당하면 **한쪽에 적고 다른 쪽에서는 가리킨다.**
