[xWIFI 통신 사양]

PC 서버와 ESP32-C6/P4 단말 간 통신은 MQTT 제어, Icecast 실시간 오디오, HTTP 파일 다운로드 세 채널로 나뉜다. MQTT가 제어를 맡고, 여기서 트리거된 나머지 두 채널이 실제 오디오/파일 데이터를 나른다. 1차는 LAN 데모 기준으로 전부 평문(MQTT 1883, HTTP)이며, TLS·인증·nginx 전환은 2차에서 진행한다.

이 문서는 1차 LAN 데모 기준 확정본이다. 양산 적용 버전이 아니며, 실서버(WAN, TLS 적용) 조건에서는 재검증이 필요하다.

이전에 채널별로 따로 있던 문서를 이 한 파일로 통합했다. 아래 두 문서는 더 이상 갱신하지 않고 이력 참고용으로만 남겨둔다.

ESP32-P4&C6_Icecast작업/ESP32_Icecast_연동가이드_1차.md — Icecast 브링업 검증 절차는 이 문서에 포함하지 않았으므로 계속 이 문서를 참고

1. 전체 아키텍처

  채널          프로토콜/포트                  용도                        트리거
  제어          MQTT 1883 (평문, 1차)         방송 시작/중지, 파일 전송     상시 연결(재접속 포함)
                                             명령, 상태/결과 보고
  실시간 오디오  Icecast HTTP GET :8000/live   마이크 실시간 방송 수신       MQTT LIVE_START 수신 후 ESP가 접속
  파일 다운로드  HTTP GET :9002                사전 녹음 파일(mp3 등) 방송   MQTT FILE_START의 https_url

1-1. LIVE 흐름

  서버 -- LIVE_START(MQTT) --------> ESP-C6
  ESP -- LIVE_READY(MQTT, status=0,reason=0) --> 서버
  ESP -- GET http://<PC_IP>:8000/live (Icecast, 프레이밍 없는 순수 바이트 스트림)--> 수신/재생
  서버 -- LIVE_STOP(MQTT) ---------> ESP

1-2. FILE 흐름

  서버 -- FILE_START(MQTT, https_url/size/sha256 포함) --> ESP-C6
  ESP -- GET https_url (일반 HTTP 정적 파일) --> 다운로드 (SDIO로 P4 전달)
  ESP -- FILE_END 또는 FILE_ABORT(MQTT) --> 서버

  LIVE_START의 codec/frame_ms/sample_rate는 실제 Icecast 스트림 파라미터와 반드시 일치해야 한다. 서버(FFmpeg) 쪽
  설정이 바뀌면 이 값도 같이 바꿔야 한다.

3. 채널 A — MQTT 제어

3.1 Topic 구조

  개별 단말 명령 : iotradio/device/<mac_nocolon>/cmd  (server → device, QoS 1, retain false)

  마을/그룹 단위 명령 : iotradio/village/<village_id>/cmd  (server → device, QoS 1, retain false)

  전체 단말 명령 : iotradio/all/cmd  (server → device, QoS 1, retain false)
  
  명령 처리 결과 (LIVE_READY, FILE_END, FILE_ABORT) :
   iotradio/device/<mac_nocolon>/result  (device → server, QoS 1, retain false)

  STATUS + LIVE_STATS + LWT가 전부 이 토픽 하나로 온다. type 필드로 구분해야 한다
   iotradio/device/<mac_nocolon>/status  (device → server, QoS 상황별, retain false)
    
  iotradio/all/config  (server → device, QoS 1, retain true)
    전체 단말 공통 설정. §3.5 참고. PC측 발행 구현됨(control.bat 메뉴 7), ESP32측 구독/적용은 진행 예정.

3.2 CMD 메시지 (서버 → 단말)

- LIVE_START

  {
    type: LIVE_START,
    job_id: 13,
    codec: opus,
    frame_ms: 40,
    sample_rate: 16000,
    record_flash: 0,
    file_name: live-demo.lopus,
    ready_timeout_sec: 30
  }

  필드                타입         필수    비고
  type               string       예     LIVE_START
  job_id             number       예     P4 라이브 세션 ID (기존 session_id, 260820부터 job_id로 통일)
  codec              string       권장   현재 opus 고정
  frame_ms           number       권장   0/과도한 값이면 40으로 보정. FFmpeg -frame_duration과 반드시 일치
  sample_rate        number       권장   0이면 16000으로 보정
  record_flash       number/bool  권장   1이면 P4 녹음 저장
  file_name          string       권장   녹음 저장 파일명
  ready_timeout_sec  number       권장   1~60 범위 밖이면 30으로 보정. 외부 AMP 모델은 AMP 전원 ON+안정화 대기 시간보다 충분히 크게 설정할 것(§3.3 LIVE_READY 참고)

C6가 수신하면 P4에 LIVE_CTRL_START를 전달하고, P4가 인트로음 재생과 준비를 마치면 C6가 LIVE_READY를 publish한다. status=0,reason=0이면 C6가 채널B(Icecast) 스트림 수신을 시작한다.

파일 다운로드/방송 중이거나 기존 LIVE가 진행 중이면 거절하고 LIVE_READY status=3 reason=8로 응답한다.

- LIVE_STOP

  { type: LIVE_STOP, job_id: 13 }

job_id 일치 검사는 강하지 않다. 서버는 반드시 현재 송출 중인 job_id로 보내야 한다.

- FILE_START

  {
    type: FILE_START,
    job_id: 38,
    size: 131900,
    resume_offset: 0,
    sha256: 97dff9352cc772b4cc5da29244d6fb44275f80f1ff778cb06509209a9496533d,
    https_url: http://192.168.0.5:9002/file-1782956366.mp3,
    file_name: file-1782956366-W.mp3,
    store_flash: 1,
    autoplay: 1
  }

  필드             타입         필수   비고
  type            string       예     FILE_START
  job_id          number       예     결과 응답에 그대로 echo (기존 cmd_id, file_id는 260820부터 삭제 — job_id 하나로 통일)
  size            number       예     0이면 거절
  resume_offset   number       아니오 기본 0
  sha256          string       권장   64 hex, P4 검증용
  https_url       string       예     필드명은 https_url이지만 1차 LAN 테스트에선 http://...:9002/... 사용
  file_name       string       권장   P4 저장/표시 파일명
  store_flash     bool/number  권장   P4 저장 여부
  autoplay        bool/number  권장   수신 후 자동 방송 여부

파일 처리 중이면 FILE_ABORT reason=BUSY, 라이브 방송 중이면 FILE_ABORT reason=PREEMPTED_BY_LIVE로 응답한다.

- FILE_STOP

  { type: FILE_STOP, job_id: 100 }

job_id는 권장 필드다(생략하면 현재 진행 중인 파일 방송 전체를 중지 요청한 것으로 처리). 진행 중인 다운로드뿐 아니라, 다운로드가 끝나고 P4가 autoplay로 재생 중인 상태도 이 명령으로 중단시킬 수 있다.

응답은 두 갈래다:
- 실제로 중단시킬 파일 방송이 있었다면 → 기존과 동일하게 FILE_ABORT reason=USER_CANCEL
- 중단시킬 파일 방송이 이미 없거나(끝났거나) 요청한 job_id가 현재 진행 중인 것과 다르면 → FILE_STOP_RESULT reason=NOT_ACTIVE

  { type: FILE_STOP_RESULT, ver: 267, job_id: 100, status: 1, reason: NOT_ACTIVE }

  필드    의미
  status  0=처리됨(사실상 FILE_ABORT/USER_CANCEL로 옴), 1=처리할 파일 방송 없음
  reason  NOT_ACTIVE: 현재 파일 다운로드/재생 없음 또는 요청 id 불일치

서버는 FILE_STOP을 보낸 뒤 FILE_ABORT(USER_CANCEL) 또는 FILE_STOP_RESULT(NOT_ACTIVE) 둘 다 올 수 있다는 걸 감안해서 처리해야 한다 — 둘 다 "요청 처리 완료"로 보되, 후자는 애초에 멈출 게 없었다는 뜻으로 구분해서 사용자에게 보여주면 된다.

3.3 RESULT 메시지 (단말 → 서버)

Topic: iotradio/device/<mac_nocolon>/result, QoS 1.

- LIVE_READY

  { type: LIVE_READY, ver: 267, job_id: 13, device: 58:e6:c5:f2:cc:74, status: 0, reason: 0 }

**단말에 보내는 `file_name` 에는 한글을 넣지 않는다**(2026-08-27 사양 §11.2 반영).

단말은 받은 이름에서 `0-9 A-Z a-z - _` 외의 **바이트**를 전부 `_` 로 바꾼다. UTF-8 한글은 글자당 3바이트라 `___` 가 되고, **바이트 길이가 같은 다른 제목끼리 구분이 사라진다** — 단말 저장소에 밑줄만 늘어선 파일이 남는다.

    산불방재 안내.mp3  →  ___________________-<epoch>-W.mp3

그래서 서버는 화면용 이름(한글 가능)과 단말용 이름을 나눈다. 단말에는 ASCII 만 보내고 `file_id` 를 붙여 되짚을 수 있게 한다(`file/service.py` 의 `device_file_name`).

    notice.mp3        →  notice-73.mp3
    공지 notice.mp3   →  notice-73.mp3
    산불방재 안내.mp3 →  file-73.mp3

epoch 와 `-W` 는 단말이 붙이므로 서버가 미리 붙이지 않는다. 한글 제목은 서버 DB 가 들고 있고, 단말은 `job_id` 로 응답하므로 이력에서 제목을 이어 붙일 수 있다.

**MQTT client_id 는 단말의 MAC(콜론 없는 소문자)이어야 한다**(2026-08-26 확정, 기존 사양 누락분).

    OK   58e6c5f2cc74
    NG   iotradio-58e6c5f2cc74

브로커 ACL 이 `%c`(client_id) 치환으로 "자기 토픽에만 발행" 을 강제하기 때문이다. client_id 가 토픽의 MAC 과 다르면 발행·구독이 **조용히 거부**된다(에러 응답이 아니라 무시). 운영 브로커는 `allow_anonymous false` 이므로 계정도 필요하다:

    username  xwifi-device
    password  서버 구축 시 발급 (scripts/setup-mqtt-users.sh)

LAN 데모는 `allow_anonymous true` 에 ACL 이 없어 두 항목 모두 필요 없었다 — 운영 전환에서 처음 드러났다.

**결과 메시지는 2026-08-27 신형식이 기준이다** — `SERVER_COMM_MQTT_ICECAST_HTTP_SPEC_2026-08-14.md` §5.4 를 따른다(2026-08-30 반영).

  · 성패는 `ok` 불리언 하나가 정한다. `code` 는 사유일 뿐 판정을 뒤집지 않는다.
  · `FILE_RESULT` 가 FILE_END/FILE_ABORT/FILE_STOP_RESULT 셋을 대체했다.
  · 라이브는 `LIVE_READY`(준비) + `LIVE_RESULT`(종료) — 정상 종료가 `ok=true code=STOPPED_BY_SERVER` 로 오므로 서버가 "내가 STOP 을 보냈던가"를 기억할 필요가 없다.
  · OTA 는 `OTA_PROGRESS`(진행, 25% 단위) + `OTA_RESULT`(최종 1회).
  · STATUS 의 `live`(OFF/PLAYING/RECONNECTING)가 무음 감지 신호다. 숫자 `reason` 은 없다.
  · 서버는 구형식(FILE_END 등, LIVE_READY status 숫자)도 호환 수신한다 — 구버전 펌웨어와 목 단말용.

**LIVE_READY는 한 job 에 두 번 올 수 있다**(2026-08-24 단말측 확인, 기존 사양 누락분):

    1) LIVE_READY status=0             P4 오디오 출력 준비 완료 — Icecast 접속 *전*
    2) LIVE_READY status=2 reason=0x01  스트림 접속 실패로 abort (함께 STATUS state=IDLE, busy=0)

`status=0`은 "스피커 출력 준비가 됐다"는 뜻이지 "스트림을 받기 시작했다"는 뜻이 아니다. **서버는 status=0만 보고 성공으로 처리하면 안 된다** — 두 번째 메시지까지 봐야 실제 수신 여부를 알 수 있다. 접속에 실패해도 단말은 상태를 정리하고 IDLE로 복귀하며 BUSY로 굳지 않는다.

**LIVE_STATS 는 주기 telemetry다** — 서버는 tick 마다 이력을 쌓지 않고 방송·단말당 최신값 1행만 유지한다(STATUS 와 같은 정책). 쌓으면 300대 × 10초 주기에 방송 10분이 18,000 행이 되고, 화면의 단말별 응답 목록도 같은 단말이 계속 늘어난다. 반대로 LIVE_READY 같은 **결과**는 한 job 에 두 번 올 수 있고 둘 다 남아야 한다(위 참고).

**단말에는 선점 기능이 없다**(2026-08-24 명확화). §5의 `OTA > LIVE > FILE` 우선순위는 STATUS 표시용이지 선점 규칙이 아니다. 먼저 시작한 작업이 끝날 때까지 단말을 차지하며, 그 사이에 온 명령은 전부 거부된다(LIVE_START → `LIVE_READY status=3 reason=0x08`, FILE_START → `FILE_ABORT`). 파일 다운로드 중이면 긴급 실시간 방송도 거부된다. 따라서 서버는 **정지 → STATUS `state=IDLE, busy=0` 확인 → 새 명령** 순서를 지켜야 한다. 정지 후 Icecast 수신 태스크 종료에 최대 5초, P4 오디오 정리에 약 3초가 더 걸리며, **이미 끊긴 스트림을 정지할 때가 가장 오래 걸린다**. 고정 지연을 가정하지 말고 STATUS를 기다린다(단말은 상태 변경 시 주기를 기다리지 않고 즉시 발행한다). 권장 10초 안에 IDLE이 안 오면 그 단말은 건너뛰고 나머지 대상 방송을 계속 진행한다.

LIVE_READY는 P4의 실제 오디오 출력 준비가 완료된 뒤에만 발행한다(2026-08-20 명확화). 외부 AMP를 쓰는 모델은 LIVE_CTRL_START 수신 후 AMP 전원 ON + 안정화 대기 시간을 거친 뒤에야 LIVE_READY를 반환하며, 이 대기 구간 동안은 LIVE_READY를 보내지 않는다 — 이때 서버 STATUS는 state=LIVE, busy=1로 보일 수 있다(§3.4, 별도의 LIVE_READY_WAIT state는 없음). 서버는 LIVE_START 이후 ready_timeout_sec 동안만 LIVE_READY를 기다리므로, 외부 AMP 모델은 이 값을 AMP 안정화 시간보다 충분히 크게 설정해야 한다.

  status   의미
  0        READY
  1        TIMEOUT
  2        ABORT
  3        FAIL/BUSY

  reason   의미
  0x00     정상
  0x01     일반 실패/중단
  0x03     timeout
  0x08     busy

서버는 status=0,reason=0일 때만 채널B(Icecast) 송출 준비 완료로 판단한다. status=3,reason=8(BUSY)은 자동 재시도하지 않고 사용자에게 표시한 뒤 수동 재시도를 받는다.

- FILE_END

  성공: { type: FILE_END, ver: 267, job_id: 38, verify_ok: true }
  실패: { type: FILE_END, ver: 267, job_id: 38, verify_ok: false, fail_reason: SHA256_FAIL }

  fail_reason 후보: SHA256_FAIL / STORAGE_FAIL / BAD_FIELD / NO_PSRAM / DL_FAIL

- FILE_ABORT

  { type: FILE_ABORT, ver: 267, job_id: 38, last_offset: 0, reason: BUSY }

  reason 후보: PREEMPTED_BY_LIVE / BAD_FIELD / USER_CANCEL / NO_PSRAM / BUSY / NET_ERROR / STORAGE_FAIL / CREDIT_TIMEOUT

CREDIT_TIMEOUT은 서버/HTTP 다운로드 자체의 실패가 아니라, C6가 받은 파일 데이터를 SDIO로 P4에 전달하려 할 때 P4 쪽 수신 여유(credit)가 일정 시간 안에 확보되지 않아 전달을 포기한 경우다(P4가 다른 처리로 바쁘거나 SDIO 큐가 막힌 상황). 서버는 다른 reason과 동일하게 처리하면 된다 — 파일 전송 상태를 clear하고 사용자가 다시 시도하게 한다.

BUSY 수신 시 서버 내부 파일 전송 상태를 반드시 clear한다. 자동 무한 재시도는 금지하며, 사용자가 다시 시도해야 처음부터 재전송한다.

3.4 STATUS / LWT / LIVE_STATS

Topic: iotradio/device/<mac_nocolon>/status (전부 동일 토픽, type 필드로 구분).

STATUS는 단말 상태를 주기적으로 체크하기 위한 메시지다. 발행 트리거는 4가지다(2026-08-20 정리):

- 최초 STATUS: MQTT 연결 직후 바로 발행하지 않는다. retained CONFIG 수신, 또는 10초 대기 중 먼저 발생하는 시점에 QoS 1로 발행한다(브로커에 retain된 CONFIG가 없어도 10초 뒤엔 기본값으로 발행 — §운영서버 개요의 "브로커 데이터 유실 시 CONFIG 복구"와 맞물리는 동작).
- CONFIG 적용 직후 STATUS: QoS 1 고정.
- 주기 STATUS: status_interval_sec 주기. QoS는 CONFIG event_qos를 따름(기본 0).
- 상태 변경 즉시 STATUS(신규): state 값이 바뀌면 주기를 기다리지 않고 즉시 1회 발행한다 — 서버가 단말 상태를 최대한 실시간에 가깝게 파악하기 위함. QoS는 CONFIG event_qos를 따름.

  { type: STATUS, device: 58:e6:c5:f2:cc:74, village_id: 00000001, wifi: 1, mqtt: 1, ip: 192.168.0.21, rssi: -39, state: LIVE, busy: 1, reason: 0, config_version: 3 }

  state (2026-08-20 개정)   의미
  IDLE                     대기 상태
  LIVE                     Icecast 실시간 방송 준비/재생 중(외부 AMP 안정화 대기 구간 포함 — §3.3 LIVE_READY 참고)
  FILE                     HTTP 파일 다운로드/전송 중 또는 P4 파일 방송 재생 중
  RF                       P4 RF 모듈 방송 수신/재생 중
  OTA                      온라인 OTA 진행 중
  OFFLINE                  LWT 또는 네트워크 단절 상태(아래 참고)

  상태 우선순위: OTA > LIVE > FILE > RF > IDLE.

  (기존 LIVE_READY_WAIT는 삭제됨 — LIVE_READY 발행 전 "준비 중" 구간도 이제 state=LIVE로 통합된다. 서버가 "송출 준비 중"과 "실제 송출 중"을 구분해야 하면 LIVE_START 발행 시각과 LIVE_READY 수신 여부로 애플리케이션 레벨에서 추적한다.)

  RF는 서버가 명령으로 켜고 끄는 상태가 아니다 — P4의 RF 모듈이 자체적으로 동작하고, 서버는 STATUS로 관측만 한다. RF 수신 중에 LIVE_START/FILE_START가 오면 단말이 어떻게 반응하는지는 위 우선순위(RF가 LIVE/FILE보다 낮음)상 서버 명령이 우선될 것으로 추정되나, 명시적으로 확인된 사항은 아니라서 §6에 별도로 표시해뒀다.

- LWT(OFFLINE): 단말이 직접 publish하는 상태가 아니다. 단말이 MQTT 연결 시 이 status 토픽에 LWT(Last Will)를 등록해두면, 전원 차단/Wi-Fi 단절/비정상 리셋 등으로 연결이 끊겼을 때 **broker가** 그 LWT payload를 QoS 1로 대신 publish한다. 서버는 이 메시지를 수신하면 해당 단말을 OFFLINE으로 표시한다.

  { type: STATUS, device: 58:e6:c5:f2:cc:74, village_id: 00000001, wifi: 0, mqtt: 0, state: OFFLINE }

  정상 재부팅/OTA처럼 의도된 종료 흐름에서는 LWT가 발행되지 않을 수 있다(단말이 스스로 정상 종료한 것이라 broker가 "비정상 단절"로 보지 않음) — 이 경우 OTA_STATUS의 진행 상황과, 재접속 후 다시 오는 STATUS를 함께 기준으로 판단해야 한다.

- LIVE_STATS : 방송 중(P4 live_audio_task)에서 약 10초 주기(CONFIG live_stats_interval_sec 따름). QoS는 CONFIG event_qos를 따름(기본 0) — 2026-08-21 정정, 이전엔 QoS0 고정으로 잘못 기재됨.

  { type: LIVE_STATS, ver: 267, job_id: 13, p4_buffer_ms: 2120, underrun_count: 1, decode_error_count: 0, rx_seq_last: 1162, rec_overflow: 0 }

  필드                 의미
  p4_buffer_ms         P4 지터 버퍼에 남은 오디오 시간(ms). 1000~2500ms면 안정권
  underrun_count       버퍼 고갈로 재버퍼링/은닉 발생 누적 횟수. 계속 증가 시 끊김 의심
  decode_error_count   Opus 디코드 오류 횟수 (현재 항상 0)
  rx_seq_last          P4 기준 마지막 처리 sequence. 40ms 기준 10초당 약 250 증가해야 정상
  rec_overflow         녹음 overflow 여부

3.6 OTA 업데이트

단말측(P4+C6) 상세 설계는 별도 사양서(ESP32측 ONLINE_OTA_UPDATE_SPEC_2026-08-14.md, ONLINE_OTA_SERVER_TEST_SPEC_2026-08-15.md)를 따른다. 여기서는 서버가 알아야 할 메시지/토픽만 요약한다.

배포 파일은 USB 업데이트와 동일한 IOT_RADIO.pkg 하나로 통일. 서버는 이 파일을 파일서버(9002)의 update/ 경로에 올려두고 URL/size/sha256만 명령에 실어 보낸다 — pkg 내부 구조는 P4가 해석한다.

흐름(2026-08-20 간소화, ESP32측 확정): 서버는 OTA_START만 보낸다. OTA_APPLY는 더 이상 사용하지 않는다 — 단말이 다운로드→검증→적용→재부팅까지 전부 자동으로 진행한다. 서버는 OTA_STATUS로 진행 상황을 지켜보다가, 재부팅 후 재접속된 STATUS의 펌웨어 버전으로 최종 성공 여부를 판단한다(이 판단 방식 자체는 기존과 동일).

  { type: OTA_START, job_id: 1001, pkg_version: 2, url: http://192.168.0.5:9002/update/IOT_RADIO.pkg, size: 7340032, sha256: (64 hex) }

  { type: OTA_STATUS, ver: 267, job_id: 1001, device: 58:e6:c5:f2:cc:74, target: PKG, state: DOWNLOADING, progress: 42, reason: OK, received: 3080192, total_size: 7340032 }

  state 후보: ACCEPTED(OTA_START 수락) / PREPARE(OTA 모드 진입, P4 자원 준비) / DOWNLOADING(C6 다운로드 + C6→P4 전달 중) / VERIFYING(P4가 sha/header/entry 검증 중) / COMPLETED(다운로드+검증 완료 — 이 보고 직후 단말이 네트워크를 끊고 자동으로 적용+재부팅 시작) / FAIL(실패, OTA 모드 진입 후 실패면 최종 FAIL 보고 후 재부팅)

  reason: 정상 진행 중엔 OK. 실패 시 후보: BAD_FIELD / BUSY / NO_MEMORY / DL_FAIL / SHA256_FAIL / PKG_INVALID / C6_WRITE_FAIL / P4_WRITE_FAIL / MODEL_MISMATCH

  received/total_size: OTA_STATUS에 추가된 필드 — 지금까지 받은 바이트 수 / pkg 전체 크기. progress(%)와 함께 다운로드 진행률 표시에 사용.

QoS: OTA_START는 QoS 1 권장, retain false(단말 재접속 시 과거 OTA 명령 재실행 방지). OTA_STATUS는 중간 상태(ACCEPTED/PREPARE/DOWNLOADING/VERIFYING)만 CONFIG의 event_qos를 따르고, 최종 상태(COMPLETED/FAIL)는 event_qos 설정과 무관하게 항상 QoS 1로 고정 — 네트워크 종료/재부팅 직전에 보내는 마지막 보고라 PUBACK을 반드시 기다려야 하기 때문.

OTA는 LIVE/FILE/RF 방송과 동급의 최상위 배타 상태다. 방송 중 OTA_START가 오면 거절(BUSY), 반대로 OTA가 PREPARE~VERIFYING 구간(아직 네트워크가 살아있는 동안)일 때 LIVE_START/FILE_START가 오면 단말이 BUSY로 거절한다. COMPLETED 이후로는 단말이 곧바로 네트워크를 끊으므로 이 구간 자체가 사실상 없다.

실서비스 배포 전에는 pkg 서명(코드 사이닝) 적용이 필수다 — sha256은 전송 중 손상 여부만 확인할 뿐 정품 여부는 증명하지 못한다. 1차 내부망 테스트는 서명 없이 진행 가능.

PC 서버 구현 완료: control.bat 메뉴 8(OTA_START). files/update/IOT_RADIO.pkg의 size/sha256을 자동 계산하고 job_id를 ota_counter.txt로 증가 관리한다. (기존 메뉴 9 OTA_APPLY는 프로토콜 간소화로 삭제됨.) 실제 pkg 파일로 ESP32와의 종단 테스트는 아직 진행 전.

4. 채널 B — Icecast 실시간 오디오

  항목           값
  프로토콜       일반 HTTP GET 스트리밍 (WebSocket 아님, TLS 아님 — 1차)
  URL           http://192.168.0.5:8000/live
  컨테이너/코덱   Ogg / Opus
  비트레이트      24 kbps
  채널           mono (1ch)
  샘플레이트      16000 Hz
  content_type  application/ogg
  수신 인증      없음 (source123은 FFmpeg→Icecast 송출용이며 ESP와 무관)

ESP는 TCP 소켓을 열고 GET /live HTTP/1.1 + Host 헤더를 보낸 뒤, 응답 헤더 수신 후 바디를 스트림으로 계속 읽는다. Content-Length 없이 끝나지 않는 스트림이며, 프레이밍 없는 순수 바이트 스트림이다

재생 지터 버퍼는 1.5초 프리버퍼링(38 frame)을 목표로 하고, 65 frame(2.6초) 도달 시 고수위 trim으로 50 frame까지 서서히 낮추며, 최대 3초(75 frame, #define)를 하드캡으로 둔다. 최초 정책 설계는 ESP32_지터버퍼_정책_최종전달.txt 참고 — 단 프리버퍼/trigger/target 값은 burst 대응 튜닝을 거치며 25/62/45에서 38/65/50으로 조정됐다. 이 문서의 값이 최신이다.

서버 쪽에서도 두 가지를 튜닝했다: FFmpeg page_duration을 기본 1초에서 40ms(-page_duration 40000)로 낮춰 Ogg page 단위로 뭉쳐 나가던 burst를 줄였고(Icecast_시작.bat), Icecast queue-size를 100KB에서 16KB(약 5.5초)로 낮춰 느린 리스너의 백로그가 무한정 쌓였다 한꺼번에 터지는 걸 막았다(icecast.xml). 이 조정들로 1차 LAN 데모 기준 severe underrun 없이 안정화됐음을 확인했다.

이 값들은 1차 LAN 데모 기준 확정값이며, 양산 적용 버전이 아니다. 실서버(WAN/TLS) 조건에서는 지연·지터 특성이 달라질 수 있어 재검증이 필요하다 — §8 참고.

브링업 검증 절차(연결→데이터→소리→버퍼링→안정화→TLS전환 6단계)는 이 문서에서 다루지 않는다 — ESP32-P4&C6_Icecast작업/ESP32_Icecast_연동가이드_1차.md 참고.


5. 채널 C — HTTP 파일 다운로드

  항목        값
  용도        MQTT FILE_START가 지시한 사전 녹음 파일(mp3 등)을 ESP가 다운로드
  URL         http://192.168.0.5:9002/<file> (FILE_START의 https_url 필드 값 그대로)
  방식        일반 HTTP GET, 정적 파일 응답 (Icecast와 무관한 별도 서버/포트)
  인증        없음
  무결성 검증  FILE_START의 size/sha256을 P4가 다운로드 후 검증

이 9002 포트 서버는 1차 LAN 검증/데모 전용이다. 필드명은 https_url을 유지하되 1차엔 평문 http:// 값을 넣는다.

흐름: FILE_START 수신 → C6가 https_url로 다운로드 → SDIO로 P4 전달 → P4가 size/sha256 확인 → store_flash/autoplay 조건에 따라 저장/자동재생 → C6가 FILE_END/FILE_ABORT를 MQTT result로 publish.

6. BUSY / 우선순위 정책 (채널 간 공통)

- LIVE 진행 중에 FILE_START 수신 → FILE_ABORT reason=PREEMPTED_BY_LIVE
- FILE 처리 중에 LIVE_START 수신 → LIVE_READY status=3 reason=8(BUSY)
- 어느 쪽이든 BUSY/실패 응답 수신 시 서버는 자동 재시도하지 않는다. 내부 상태를 clear하고 사용자에게 표시하며,
  사용자가 다시 버튼을 눌러야 새 job_id로 재전송한다.
- RF(§3.4 참고)는 서버 명령으로 시작/중지하는 상태가 아니라 P4가 자체적으로 켜고 끄는 상태다. RF 수신 중 LIVE_START/FILE_START가 오면 단말이 어떻게 응답하는지(BUSY 거절 여부)는 아직 확정된 사항이 아니다 — §3.4의 상태 우선순위(OTA>LIVE>FILE>RF>IDLE)상 RF보다 LIVE/FILE이 우선이라 서버 명령이 받아들여질 것으로 추정되나, ESP32측 확인 필요.


7. 서버(PC) 구현 체크리스트

7-1. MQTT CMD payload 1024 bytes 미만 유지.
7-2. LIVE_READY status=0,reason=0 확인 후에만 실제 Icecast 송출 시작(또는 이미 송출 중이면 유지).
7-3. LIVE_READY status=3,reason=8(BUSY)은 자동 재시도 금지, 사용자 표시.
7-4. FILE_ABORT reason=BUSY 수신 시 서버 내부 파일 전송 상태 clear 필수.
7-5. LIVE_STATS는 status 토픽으로 오므로 type 필드로 STATUS와 구분.
7-6. 파일 다운로드는 Icecast(8000)와 분리된 별도 HTTP 서버 포트(9002) 사용, AWS 운영 서버와 무관.
7-7. LIVE_START의 frame_ms/sample_rate는 FFmpeg 송출 설정과 항상 일치시킬 것.
7-8. QoS 1 메시지는 MQTT 특성상 중복 도착할 수 있으므로, job_id 기준으로 중복 처리(같은 걸 두 번 처리하지 않도록) 방지 로직 필요.


8. 2차 예정 (현재 미구현)

CONFIG(§3.5)와 OTA(§3.6)는 양쪽 다 구현되어 더 이상 2차 항목이 아니다(OTA는 PC측 구현 완료, 실 pkg 종단 테스트만 남음).

기타 2차 검토 항목

- Icecast → nginx WSS 브리지 + TLS 전환, ESP 공개 CA bundle 복귀 (ESP32_Icecast_연동가이드_1차.md, TLS·nginx 전환 단계)
- 파일 다운로드를 nginx HTTPS 표준으로 편입 (현재 9002 평문은 1차 한정)
- MQTT → MQTTS, broker/client 인증
- live_stats 별도 토픽 분리 여부, STATUS/LWT retain 정책(서버 대시보드 요구사항에 따라)
- village별/device별 CONFIG 오버라이드 (1차에서는 불필요 판단)
- LIVE 지터버퍼/Icecast 튜닝(§4)은 1차 LAN 데모 기준으로 완료·확정됐다. 실서버(WAN, TLS 적용 후) 조건에서 동일한 burst/underrun 검증을 재실행해야 하며, 양산 적용 전 필수 항목이다.
- 마을별 Icecast stream_url 분리 — ESP32측과 정책 확정(2026-08-21, `xWIFI_마을별_stream_url_정책_260821.md` 참고). LIVE_START에 `stream_url` 필드가 추가될 예정이며(없으면 기존 고정 `/live`로 fallback), 세션마다 다른 Icecast mount에 분리한다 — 경로는 `/live/<job_id>`(2026-08-24 서버측 확정: 마을 여러 곳을 한 방송으로 묶는 다중 대상이 생겨 경로에 마을을 담을 수 없게 됐다. 단말은 문자열을 그대로 쓰므로 단말 동작에는 영향 없음). `stream_url`은 서버가 완성된 URL 문자열을 내려주고 단말은 그대로 접속만 하므로 scheme/host/port 변경(도메인 적용, TLS 전환 등)은 펌웨어 수정 없이 가능하다. **2026-08-24 단말 펌웨어 반영 완료**(`ESP32_회신_LIVE_START_stream_url_반영완료_260824.md`) — 단말은 받은 문자열을 파싱 없이 그대로 쓰고, 없거나 비면 기존 고정 mount로 fallback한다. **단말은 스트림이 끊겨도 재접속하지 않는다**(2026-08-24 단말측 정정 — 최초 회신의 "3초 주기 재접속"은 개발용 경로였고 제품 모델에서는 비활성이다). 단절을 감지하면 P4에 정지를 전달하고 `LIVE_READY status=2`를 발행한 뒤 `STATUS state=IDLE, busy=0`으로 돌아가며, **그 방송은 그 단말에서 끝난다.**

  따라서:
  - 방송 시작부터 종료까지 Icecast source가 **끊김 없이** 유지돼야 한다. 방송 중 mount/source를 잠깐이라도 재시작하는 구성은 동작하지 않는다.
  - 순간적인 단절도 회복되지 않는다. 재방송이 필요하면 서버가 **새 job_id로 다시 시작**해야 한다.
  - 서버는 오디오가 끊긴 방송을 붙들지 않고 직접 끝낸다(`LIVE_UPLINK_GRACE_SEC`, 기본 30초). 방치하면 화면은 ON AIR인데 소리는 안 나가고 대상 단말이 겹침 검사에 묶여 재방송까지 막힌다. Icecast가 먼저 mount를 지우기 전에 서버가 `LIVE_STOP`을 보내야 단말이 오류가 아닌 정상 종료로 정리하므로, `icecast.xml`의 `source-timeout`(60초)은 이 유예시간보다 크게 잡는다.

  ⚠ 실측(2026-08-24): 소스가 데이터를 멈추면 Icecast는 `source-timeout` 뒤 mount를 조용히 제거하며(청취 시 404), **서버측 소스 객체는 여전히 연결됨으로 보인다.** Icecast에 판단을 맡기면 서버가 그 사실조차 모른다.

  단말측 제약 두 가지(서버가 발행 전에 지킨다):
  - `stream_url` **512바이트 이하**. 초과 시 단말은 잘라 쓰지 않고 방송을 거절한다.
  - **`https://` 만 지원**(2026-08-29 정정). 단말 운영 빌드는 http 를 거절한다 — `LIVE_READY ok=false code=BAD_FIELD` 로 방송이 시작되지 않는다. 포트는 붙이지 않는다(443). 서버는 nginx 가 `/live/` 를 Icecast 로 프록시한다. 서버측 동적 mount 생성·소스 연결은 구현·검증 완료(2026-08-24) — LIVE_START 발행 전에 mount를 세우고 종료 시 닫는다.
