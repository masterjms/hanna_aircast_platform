# ESP32 정정 수신: 스트림 단절 시 단말은 재접속하지 않는다

**수신**: 단말측 → 서버측, 2026-08-24
**정정 대상**: `ESP32_회신_LIVE_START_stream_url_반영완료_260824.md` §1.1
**서버 반영**: 완료 (아래 §3)

---

## 1. 무엇이 정정됐나

최초 회신의 다음 내용이 **틀렸다**:

> "스트림이 끊기면 단말은 같은 stream_url로 3초 주기 재접속을 시도합니다."

재접속 루프(`ICECAST_RECONNECT_MS` 3초)는 `icecast_client_task`에 있는 개발용 경로이며 제품 모델(HY/JH) 모두 비활성이다. 실제 운영 경로인 `icecast_stream_task`는 `icecast_stream_once()`를 **1회만** 호출하고 끝난다.

### 실제 동작

```text
스트림 단절 감지
  → 재접속 시도 없음
  → P4 에 LIVE_CTRL_STOP (reason = DISCONNECT 또는 TIMEOUT)
  → LIVE_READY status=2 발행
  → STATUS state=IDLE, busy=0
  → 그 방송은 종료
```

| 항목 | 최초 회신 | 실제 |
|---|---|---|
| mount 유지가 필요한 이유 | 재접속이 다시 붙도록 | 순간 단절만으로 방송이 끝나므로 |
| 방송 중 순간 단절 | 자동 회복 | **회복 안 됨. 방송 종료** |
| 방송 중 source 재시작 | 가능 | **불가. 해당 방송 종료** |

재방송이 필요하면 서버가 **새 job_id로 다시 시작**해야 한다.

`stream_url` 반영 자체는 회신 내용 그대로 유효하며, 경로 형식은 단말이 파싱하지 않으므로 서버 문서(`/live/<job_id>`)대로 진행하면 된다. `https://`는 TLS 전환 이후 지원.

## 2. 서버측에서 확인한 사실 (실측, 2026-08-24)

이 정정이 왜 중요한지는 Icecast 동작과 겹쳐 봐야 드러난다.

```text
소스가 오디오를 멈춤
  → source-timeout(당시 10초) 뒤 Icecast 가 mount 를 제거 (청취 시 404)
  → 단말은 스트림이 끊김 → 재접속 안 함 → 그 방송 종료
  → 그런데 서버측 소스 객체는 여전히 "연결됨"으로 보인다
```

즉 **Icecast 에 판단을 맡기면 서버는 방송이 죽은 사실조차 모른다.** 화면에는 ON AIR 인데 소리는 안 나가고, 대상 단말은 겹침 검사에 묶여 재방송까지 막힌다.

브라우저 업링크(`useMicUplink`)도 끊기면 재연결하지 않고 "방송을 다시 시작해 주세요"를 띄운다 — **양쪽 모두 회복 경로가 없다.**

---

## 3. 서버 반영 내용

1. **오디오 워치독** — 마지막 오디오 바이트 이후 `LIVE_UPLINK_GRACE_SEC`(기본 30초)이 지나면 서버가 방송을 끝낸다(`LIVE_STOP` 발행 → source 종료 → 이력 종료 처리). "한 번도 안 붙음"과 "붙었다 끊김"을 같은 잣대로 잰다 — 결과가 같기 때문이다.

   > 이전 구현은 "붙었다 끊긴 방송은 재연결 여지가 있으므로 끄지 않는다"였다. 그 전제가 이 정정으로 사라져 함께 바꿨다.

2. **`icecast.xml` source-timeout 10 → 60초** — Icecast 가 먼저 mount 를 지우면 단말은 오류로 끝난다. 서버가 `LIVE_STOP` 을 먼저 보내 정상 종료시키기 위해, source-timeout 은 워치독 유예시간보다 **반드시 크게** 둔다.

3. **방송 중 source 재시작 없음** — 코드 전수 확인 결과 source 를 닫는 지점은 모두 의도된 종료(사용자 중지 · 워치독 · 발행 실패 롤백)뿐이다. 중간 재시작 경로는 없다.

### 검증

| 시나리오 | 결과 |
|---|---|
| 오디오 멈춤 → mount 생존 (source-timeout 60) | 40초까지 살아있음 확인 |
| 업링크 한 번도 안 붙음 | 유예시간 뒤 자동 종료 |
| 업링크 붙었다 끊김 | 오디오 중단 후 유예시간에 자동 종료 |

---

## 4. 남은 확인 필요

- **정상 중지 때도 `LIVE_READY status=2`가 오는가** — 서버가 `LIVE_STOP` 을 먼저 보내고 source 를 닫는데, 실물 단말 로그에서 중지 직후 `status=2`가 관측됐다. 이것이 `LIVE_STOP` 처리 결과인지 source 종료를 단절로 본 것인지에 따라 화면에서 "실패"로 표시할지가 갈린다.
