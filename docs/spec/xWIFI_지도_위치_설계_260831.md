## 1. 개념 정리 — 코드는 구역이고, 좌표는 점이다

먼저 헷갈리기 쉬운 세 가지를 가른다. **이 구분이 이 문서 전체의 기준이다.**

| 값 | 무엇인가 | 어디까지 내려가나 | 용도 |
|---|---|---|---|
| **법정동코드** (10자리) | 행정 구역 코드 | **리까지** (번지 표현 불가) | 마을 속성, 경계 도형과의 조인 키 |
| **주소** (도로명·지번·동/호) | 그 건물이 어디인가 | 건물·호수까지 | 사람이 찾아가는 값, 좌표의 원천 |
| **좌표** (위경도, WGS84) | 지도 위의 점 | 건물 출입구 | **지도 마커는 이것만 쓴다** |

### 1.1 법정동코드는 10자리다

```text
46 840 330 21
─┬ ─┬─ ─┬─ ─┬
시도 시군구 읍면동 리
```

행정표준코드관리시스템(code.go.kr) 기준. 도시 지역은 리가 없어 마지막 2자리가 항상 `00`이라 8자리처럼 보이지만, **우리 고객은 농촌이라 리 2자리가 살아있는 것이 핵심**이다 — 마을방송은 리 단위로 운영된다.

### 1.2 흔한 오해 두 가지 (실제로 나왔던 것)

**"마지막 두 자리는 같은 건물의 단말을 구분한다"** — 아니다. 이는 village_id 12자리(법정동코드 10 + 연번 2) 설계의 연번이 와전된 것이다. 레지스트리 사양 §2.3: **연번은 "단말 번호"가 아니라 "방송 그룹 번호"다.** 단말 구분은 MAC이 이미 하고 있고, 한 건물에 단말 두 대가 같은 값을 받는 것이 정상이다(§3.2.1).

**"단말마다 법정동코드가 다르다"** — 거의 아니다. 법정동코드는 리까지만 내려가므로, 같은 리 안의 단말은 마을과 **같은 코드**를 갖는다. 그래서 단말에 코드를 따로 받을 실익이 없다 — 단말에 저장할 것은 주소와 좌표다(§2).

### 1.3 village_id 와 위치 정보는 별개다

village_id 는 MQTT topic 에 들어가는 **방송 그룹 식별자**이고(현재 순수 일련번호 운용 중), 법정동코드·주소·좌표는 **DB 속성**이다. 지도 기능이 들어와도 village_id 체계는 건드리지 않는다.

## 2. 데이터 모델

### 2.1 저장 항목

| 대상 | 추가 컬럼 | 채워지는 방법 |
|---|---|---|
| **마을** (villages) | `b_code`(법정동코드 10), 도로명주소, 지번주소, `lat`/`lng` | 마을 등록 시 주소 검색 1회 |
| **단말** (devices) | 도로명주소, 지번주소, 상세주소(동/호), `lat`/`lng` | 단말 상세에서 주소 검색 1회. **전부 선택 입력** |

- villages 에는 `lat`/`lng` 컬럼이 이미 있다. `b_code` 와 주소 필드를 추가한다.
- 단말 상세주소(동/호)는 사람이 치는 유일한 주소 항목이다(레지스트리 사양 §3.2.1) — 검색 API 가 건물까지만 주기 때문.

### 2.2 단말 위치의 기본값 — 복사가 아니라 fallback

**단말 좌표가 비어 있으면 화면이 마을 좌표를 대신 쓴다.**

```text
마커 좌표 = COALESCE(device.lat/lng, village.lat/lng)
```

마을 값을 단말 행에 **복사해 두지 않는다.** 복사하면 마을 주소를 나중에 고쳤을 때 낡은 사본이 단말들에 남는다. fallback 이면 마을만 고쳐도 미입력 단말이 전부 따라오고, 단말 위치를 입력하는 순간 그 값이 저장되어 자기 좌표로 표시된다.

## 3. 주소 입력 파이프라인 — 카카오 로컬 API 1콜

### 3.1 확정: 카카오 하나로 간다

카카오 로컬 「주소로 좌표 변환」 응답에 필요한 것이 전부 들어 있다(공식 문서 확인, 2026-08-31):

```text
운영자가 "월선리 123-4" 입력
  → 카카오 주소검색 1콜:
      address_name   도로명주소 + 지번주소
      b_code         법정동코드 10자리
      x, y           경도, 위도 — 처음부터 WGS84
  → 전부 DB 저장. 여기서 끝 — 이후 지도를 몇 번 열어도 재호출 없음
```

**juso.go.kr 검색·좌표 API 는 신청하지 않는다** (예전 계획 폐기). 이유:

| | 카카오 로컬 | juso.go.kr |
|---|---|---|
| 주소 + 법정동코드 + 좌표 | **1콜** | 검색 + 좌표 **2개 API 각각 신청** |
| 좌표계 | **WGS84** (지도에 바로) | UTM-K → 변환 단계 필요 |
| 지도 표시와의 키 | **같은 앱 키** | 별도 |
| 발급 | 즉시 | 운영용은 심사 대기 |

쿼터는 주소 변환 일 100,000건, 지도 SDK 일 300,000건 무료 — 우리는 등록·수정 때만 호출하므로 문제가 되지 않는다.

### 3.2 지오코딩은 입력 시 1회, 결과는 DB 가 정본

법정동코드→좌표 변환 같은 것은 **존재하지 않는다** — 코드는 구역이라 점이 나오지 않는다. 좌표는 주소에서 나오고(지오코딩), **등록·수정하는 순간 1회** 호출해 DB 에 저장한다. 지도 화면은 DB 만 읽는다.

### 3.3 발급 후 확인할 것

- [ ] 농촌 주소(월선리 실주소)에서 `b_code` 가 **리 단위까지**(마지막 2자리 ≠ 00) 오는가 — 검증 스크립트로 확인
- [ ] 산간 지번(산 번지, `mountain_yn`)도 좌표가 나오는가

## 4. 지도 대시보드 설계

### 4.1 기능 목록과 확인 결과 (2026-08-31)

| # | 기능 | 판정 | 비고 |
|---|---|---|---|
| 1 | 대시보드에 카카오맵 | 가능 | JS SDK |
| 2 | 마을 영역(리 경계) 표시 | **조건부** | §4.2 — 경계 데이터는 별도 확보 |
| 3 | 단말 위치 마커 | 가능 | |
| 4 | 마커 클러스터러 | 가능 | 공식 라이브러리 `libraries=clusterer` |
| 5 | 마커 클릭 → 단말 상태 | 가능 | CustomOverlay + 우리 API |
| 6 | 권한별 표시 범위 | 가능 | 기존 VillageScope 가 백엔드에서 강제 |
| 7 | **리스트 패널** (지도 옆 단말 목록, 목록↔마커 연동) | 가능 | §4.5 — 추가 API 없음, 같은 데이터의 다른 표현 |

### 4.2 마을 영역 — 경계 좌표는 카카오가 주지 않는다

카카오맵이 주는 것은 **그리기 도구(Polygon)뿐**이다. "이 법정동코드의 경계가 어디인가"라는 좌표 데이터는 정부 배포본에서 가져온다.

```text
주소기반산업지원서비스 「구역의 도형」 다운로드 (무료, 법정 리 경계 포함)
  → 우리 마을들의 b_code 로 해당 리 경계만 추출
  → GeoJSON 변환 + 좌표 단순화 (리 하나 수 KB 수준)
  → 우리 서버가 정적 파일로 제공 (런타임 외부 호출 0, 브라우저 캐시)
  → kakao.maps.Polygon 으로 그림
```

**여기서 b_code 가 조인 키다** — 마을을 등록하면 그 코드의 리 경계가 자동으로 그려지는 구조. 변환은 스크립트 1회성 작업이고, 행정구역 개편 때만 갱신한다.

#### 우리가 쓸 레이어는 TL_SCCO_LI 다 (2026-08-31 사이트에서 직접 확인)

「구역의 도형」 SHP 안에는 레이어가 여러 개 있고, 그중 **법정구역리(`TL_SCCO_LI`)** 가 우리 것이다.

| 레이어 | 코드 자리수 | 예시 |
|---|---|---|
| 법정구역시도 `TL_SCCO_CTPRVN` | 2 | `36` 세종특별자치시 |
| 법정구역시군구 `TL_SCCO_SIG` | 5 | `36110` 세종특별자치시 |
| 법정구역읍면동 `TL_SCCO_EMD` | **8** | `36110101` 반곡동 |
| **법정구역리 `TL_SCCO_LI`** | **10** | `3611025021` 원리 |
| 행정동 `TL_SCCO_GEMD` | 10 | `3611025000` 조치원읍 |

**리 레이어의 `리코드` 10자리가 카카오 `b_code` 와 같은 값이다** — 조인이 그대로 된다.

> §1.2 의 "8자리" 오해가 여기서 풀린다. **읍면동 레이어의 코드가 실제로 8자리**여서 그렇게 알려진 것이고, 리까지 내려가면 10자리다. 마지막 2자리는 **리**이지 단말 구분이 아니다.

### 4.3 성능 — 300대는 걱정할 규모가 아니다

```text
단말 1대 지도용 데이터(mac, 별칭, 좌표, online, live) ≈ 150 bytes
× 300대 = 45KB → gzip ≈ 8KB        ← 지도 타일 이미지 한 장보다 작다
```

- 지도 배경 타일은 카카오 CDN 이 서빙한다 — 우리 서버 부담 0
- DB 는 인덱스 걸린 300행 SELECT 하나
- 단말 목록 화면이 이미 5초 폴링으로 같은 규모를 받고 있다 — 같은 부하다
- **클러스터러는 네트워크가 아니라 브라우저 렌더링·가독성 최적화다.** 데이터는 다 내려받고 화면에서 묶는다. 한 마을에 수십 대 몰릴 때 마커 겹침을 푸는 UX 용으로 쓴다

### 4.4 최적화 — 싸고 효과 확실한 것만 한다

1. **지도 전용 경량 엔드포인트** `GET /api/dashboard/map` (API 설계 §7 예약됨) — 지도에 필요한 필드만
2. **상세는 클릭할 때** — 마커 클릭 시 그 단말 하나만 `GET /api/devices/:mac`
3. **마커 재사용** — 폴링마다 전부 재생성하지 않고 상태 바뀐 것만 갱신 (브라우저 부담의 관건)
4. **경계 폴리곤은 정적 파일 + 장기 캐시**

이 구조로 3,000대까지 버틴다. 만 대 단위가 되면 그때 화면 영역만 조회(bounds 쿼리)를 붙인다 — 지금 설계하지 않는다.

### 4.5 리스트 패널 — 지도 옆에 단말 목록

카카오 샘플(「키워드로 장소검색하고 목록으로 표출하기」)과 같은 배치다: **왼쪽 목록 + 오른쪽 지도.**

```text
┌──────────────┬──────────────────────────┐
│ 단말 목록      │                          │
│ ① 홍길동집 ●  │        [지도]             │
│ ② 회관앞  ●   │     마커 · 클러스터        │
│ ③ 창고    ○  │      · 리 경계            │
│  (오프라인 위로 │                          │
│   정렬 등)     │                          │
└──────────────┴──────────────────────────┘
```

**핵심: 추가 API 가 아니다.** 목록과 마커는 `GET /api/dashboard/map` 응답 **한 벌을 두 가지로 그린 것**이다. 데이터를 두 번 받지 않는다.

양방향 연동 규칙:

| 조작 | 반응 |
|---|---|
| 목록 항목 hover/클릭 | 해당 마커 강조 + 지도 이동(panTo) + 인포윈도우 |
| 마커 클릭 | 목록에서 해당 항목으로 스크롤 + 강조 |
| 목록 필터(마을·상태) | 마커도 같이 필터 — 같은 데이터라 자동으로 일치한다 |

연동에 필요한 것은 **공유 상태 두 개뿐**이다: `selectedMac`(클릭 고정), `hoveredMac`(마우스오버). 이 상태를 목록·지도의 공통 부모가 들고, 양쪽은 그것을 읽고 쓰기만 한다.

운영 가치: 지도는 "어디가 문제인가"를 보여주고, 목록은 "무엇이 문제인가"를 보여준다. 오프라인 단말을 목록 위로 정렬해 두면, 관리자는 목록에서 문제를 집고 지도에서 위치를 확인하는 흐름으로 일한다.

### 4.6 "기능이 너무 집약된다"는 걱정 — 구조로 푼다

우려가 맞다. 지도·마커·클러스터·폴리곤·목록·연동·폴링·권한을 **한 컴포넌트에 넣으면 반드시 괴물이 된다.** 해법은 기능을 줄이는 게 아니라 **역할별로 쪼개고, 지도 컴포넌트는 "그리기"만 하게 유지**하는 것이다.

```text
DashboardMapPage (컨테이너)
 ├─ useMapData()        폴링 · /api/dashboard/map 호출 — 데이터는 여기 한 곳
 ├─ selectedMac / hoveredMac   공유 상태 두 개
 │
 ├─ DeviceListPanel     목록 그리기만. 데이터·선택 상태는 props 로 받는다
 └─ MapView             카카오맵 래퍼. 마커·클러스터러·인포윈도우 그리기만
     └─ VillagePolygons 리 경계 GeoJSON 그리기만 (3차에 추가되는 별도 조각)
```

지켜야 할 경계선:

- **MapView 는 API 를 모른다.** 폴링·권한·필터는 전부 바깥(컨테이너·백엔드)의 일이고, MapView 는 받은 배열을 그릴 뿐이다. 그래야 기능이 늘어도 지도 코드가 안 자란다.
- **권한(#6)은 프론트 기능이 아니다.** 백엔드 VillageScope 가 이미 걸러서 주므로 지도·목록에는 권한 코드가 한 줄도 없다.
- **연동(#5, §4.5)은 상태 두 개다.** 목록과 지도가 서로를 직접 호출하지 않고, 부모의 `selectedMac`/`hoveredMac` 를 통해서만 만난다.
- **폴리곤은 별도 조각이다.** 마커 로직과 섞이지 않으므로 3차에 붙이거나 빼도 나머지가 영향받지 않는다.

이렇게 나누면 "기능 7개"가 실제로는 **작은 조각 5개 + 상태 2개**가 된다.

### 4.7 마커 이름 툴팁 (2026-09-02)

마커에 마우스를 올리면 단말 별칭(없으면 MAC)을 CustomOverlay 하나로 띄우고, 그 하나를 위치만 옮겨 재사용한다.

**깜빡임의 원인은 세 겹이었다.** 커서를 마커에 올려둔 채 가만히 있어도 이름이 빠르게 깜빡였다.

1. **툴팁이 핀과 겹쳐 있었다.** `yAnchor: 1.15`는 오버레이 높이의 1.15배만큼 위로 올리는데, 툴팁 높이가 ~26px이라 좌표에서 약 30px 위 — 핀(40px)의 몸통 한가운데였다. 커서가 툴팁에 가려지면 마커에 `mouseout`이 걸리고, 툴팁이 사라지면 다시 `mouseover`가 걸린다.
2. **`pointer-events: none`이 내용에만 걸려 있었다.** SDK가 만드는 바깥 래퍼 div는 그대로 커서를 받았다. `clickable: false`는 지도 클릭·드래그를 통과시킬 뿐, DOM 마우스 이벤트를 없애지 않는다.
3. **호버할 때마다 전 마커에 `setZIndex`를 다시 줬다.** 값이 그대로여도 매번 불러서 커서 아래 마커가 불필요하게 다시 그려졌다.

**고친 방식**

- 앵커를 `yAnchor: 1`(오버레이 아래끝 = 핀 끝)로 두고, 핀 위로 올리는 것은 CSS `transform: translateY(-46px)`가 한다. 글자 길이에 따라 툴팁 높이가 달라져도 핀과의 간격이 일정하다(핀 40px + 여백 6px).
- 툴팁을 붙일 때 `el.parentElement.style.pointerEvents = 'none'`으로 래퍼까지 통과시킨다.
- `setZIndex`는 값이 실제로 바뀔 때만 부른다.
- **벗어남 판정에 유예를 둔다(`HOVER_CLEAR_DELAY_MS` 140ms).** 들어올 때는 즉시 알리고, 나갈 때만 잠깐 기다렸다가 그 사이 다시 들어오면 없던 일로 한다. 위 셋을 고쳐도 지도가 다시 그려지는 순간 `mouseout`이 튈 수 있어서, "커서가 마커 위에 있는 동안 이름이 유지된다"를 이 유예가 보장한다.

폴링(2초)으로 `pins` 배열이 매번 새로 와도 툴팁을 다시 그리지 않는다 — 지금 떠 있는 (mac, 문구)를 기억해 두고 실제로 달라진 것만 손댄다.


### 4.8 마을 경계 폴리곤 (2026-09-03, 4단계)

**데이터**: 행정안전부 「구역의 도형」 SHP 의 `TL_SCCO_LI`(리 경계) 레이어. 속성은 `LI_CD`(법정동코드 10자리) · `LI_KOR_NM` 뿐이라 `villages.b_code` 와 그대로 조인된다. 시도별 zip 이므로 **마을이 있는 시도만** 받으면 된다(b_code 앞 2자리로 판단).

**이용조건 (2026-09-03 확인)**

| 단계 | 조건 |
|---|---|
| 취득 | 신청 + 이용목적 심사 (도로명주소법 시행령 §46, 시행규칙 §53) |
| 이용 | **공공누리 제1유형(출처표시)** — 상업적 이용·변형·재배포 허용 |

출처 표시가 제1유형의 유일한 의무라, 경계를 그린 지도에 `마을 경계 : 행정안전부 주소정보제공`을 띄운다(`MapView` 의 `.map-credit`). 승인에는 만료일이 있다(예: 2026-10-01) — 만료 후 이미 받은 데이터를 계속 쓸 수 있는지는 미확인이므로, 다시 받아야 할 상황이면 만료 전에 받아둔다.

**좌표계**: 원본은 EPSG:5179(UTM-K)인데 **`.prj` 파일이 없다.** 좌표계를 코드에서 직접 지정해야 한다(「도로명주소 공간데이터 활용가이드」 확인). 지도 SDK 가 위경도를 받으므로 WGS84(EPSG:4326)로 재투영해서 저장한다.

**저장 위치 — 리포가 아니라 DB**

`villages.boundary` (JSONB, GeoJSON geometry). PostGIS 를 쓰지 않는다: 그리기만 하고 공간 질의는 하지 않는다.

리포에 커밋하지 않는 이유는 세 가지다. ① 고객마다 다른 데이터다(판매 형태가 고객당 서버 한 벌). ② 원본이 월별로 갱신돼 커밋하면 이력이 계속 부풀어 오른다. ③ 필요한 건 등록된 마을 몇 개뿐인데 원본은 시도당 수천 개다(전남광주통합특별시 기준 2,552개). 인증서·`.env` 를 리포에 두지 않는 것과 같은 이유다.

**투입 경로**: `scripts/import_boundaries.py` 를 담당자 PC 에서 돌린다. 서버에 파일을 올릴 필요가 없다 — 로컬에서 변환까지 끝내고 `PATCH /api/villages/{id}` 로 밀어 넣는다. `--dry-run` 으로 무엇이 들어갈지 먼저 볼 수 있다.

```
pip install pyshp pyproj
python scripts/import_boundaries.py --shp ".../12000/TL_SCCO_LI"     --server https://hanna-aircast.co.kr --user admin --dry-run
```

**단순화**: Douglas-Peucker, 허용 오차 기본 `2e-5`도(약 2m). 마을 경계를 보는 축척에서 2m 는 화면에 안 보이는데 점 수는 크게 준다(실측: 월선리 531점 → 278점, 11.2KB). 도형 계산이 틀리면 경계가 조용히 일그러지므로 `ring_area`·`simplify`·`shape_to_geometry` 는 테스트로 고정했다(`backend/tests/test_core.py`).

**고리 처리**: SHP 는 바깥 고리와 구멍을 `parts` 로 나눠 담고, 섬이 있으면 바깥 고리가 여러 개다. 넓이 부호로 가른다 — 음수(시계방향)면 바깥 고리, 양수면 앞선 바깥 고리의 구멍. 바깥 고리가 둘 이상이면 MultiPolygon 이다(실측: 2,552개 중 404개가 섬을 가진다).

**응답 크기**: 도형은 지도 API(`GET /api/dashboard/map`)로만 내려간다. 마을 목록(`GET /api/villages`)에는 `has_boundary` 불리언만 실린다 — 목록 행마다 수십 KB 가 붙으면 마을 관리 화면이 느려진다.

**렌더링**: `MapView` 가 마을 id 별로 카카오 `Polygon` 을 만들어 재사용한다. 폴링마다 같은 도형이 다시 오므로 형태와 점 수로 만든 지문을 비교해 바뀐 것만 다시 그린다. **폴리곤에는 리스너를 달지 않고 z-index 를 0 으로 둔다** — 폴리곤이 커서를 가로채면 그 위 마커에 `mouseout` 이 걸려 §4.7 의 깜빡임이 되살아난다.


### 4.9 클러스터러 · 줌 · 목록 패널 (2026-09-03, 3단계)

**클러스터러**: SDK 를 `libraries=clusterer` 로 로드하고 `MarkerClusterer` 에 마커를 넣는다. 마커는 `map` 을 직접 받지 않는다 — 클러스터러가 확대 수준에 따라 붙이고 떼어낸다. 마커가 생기거나 움직이거나 사라지면 `redraw()` 를 부른다(클러스터러는 `setPosition` 을 스스로 알지 못한다).

`minLevel: 5`. 카카오 level 은 1 이 가장 가깝고 14 가 전국이다. 5 이상(=더 멀리)에서만 묶고, 그 안에서는 항상 개별 핀이다. 묶는 기준은 픽셀 거리(`gridSize` 기본 60px)라, level 5 에서도 실제로 겹치는 핀만 묶인다. 클릭하면 SDK 가 한 단계 확대해 묶음을 푼다.

**줌 컨트롤**: `ZoomControl` 을 오른쪽에 붙였다. 휠·더블클릭으로도 되지만 태블릿이나 마우스 없는 환경에서는 이게 유일한 수단이다.

**선택 시 확대**: 목록이나 마커에서 단말을 고르면 `SELECT_LEVEL`(3, 건물·골목이 보이는 축척)까지 확대하고 그 단말을 가운데로 가져온다. 이미 그보다 가까이 보고 있으면 축척은 그대로 두고 위치만 옮긴다 — 사용자가 잡아둔 축척을 멀어지는 쪽으로 바꾸지 않는다. `setLevel(level, {anchor})` 로 목표점을 화면에 고정한 채 확대한 뒤 `panTo` 한다(순서를 바꾸면 확대 중 목표점이 화면 밖으로 튄다). 확대 수준이 `CLUSTER_MIN_LEVEL` 보다 가까우므로 선택하면 묶음도 자연히 풀린다.

**목록 패널 정돈 (§4.5 보완)**: 구분선은 마을 묶음 사이에만 둔다. 단말 사이에 줄을 그으면 목록이 표처럼 무거워지고, 어차피 마을 머리말이 묶음을 말해 준다. 단말 행 높이는 29px(전 40px)로 줄였다. 전용 클래스(`.vlist__*`)를 두고 인라인 스타일을 걷어냈다.

**패널 높이 고정**: 왼쪽 칼럼을 세로 flex 로 쌓아 타일 → 단말 목록 → 이상단말 순으로 두고, **단말 목록만 남는 높이를 차지해 그 안에서 스크롤**한다. 단말·마을이 늘어도 페이지가 길어지지 않고 타일과 이상단말은 제자리에 있다(실측: 5개 마을 40대에서 페이지 높이 = 뷰포트, 목록만 스크롤). 이상단말 표도 180px 안에서 스크롤한다.

### B. 구역의 도형 (마을 경계, 4단계에서 필요)

**2단계 MVP 에는 필요 없다.** 마커·목록만 먼저 갈 것이므로 A 만 있으면 착수된다. 4단계에서 쓴다 — 이용조건과 좌표계는 §4.8 참고.

1. https://business.juso.go.kr 접속
2. 상단 **[주소정보 자료제공] > [주소정보 다운로드]**

4. 데이터 구분 목록에서 **「구역의 도형」(SHP)** 선택 → 날짜(전체/월별) 선택
5. 오른쪽 **장바구니 → [신청하기]**

- 「공개하는 주소」는 즉시 다운로드지만 **「제공하는 주소」는 신청 방식**이다. 로그인·승인 소요 시간은 계정이 없어 확인하지 못했다 — 신청하면서 확인한다.
- 문의: 1588-0061 (7번)

기능 7개를 한 방에 붙이면 §4.6 의 괴물이 된다. 단계마다 **그 자체로 쓸모 있는 화면**이 나오게 자른다.
