xWIFI 운영서버 구성 개요

1차 LAN 데모(MQTT+Icecast+파일다운로드, `xWIFI_통신_사양_최종_260813.md`)가 끝났다. 다음 단계는 이걸 실제 AWS 서버(`iot_radio.co.kr`, 단일 인스턴스) 위에서 수백 대 규모 단말을 운영할 수 있는 체계로 확장하는 것이다. 이 문서는 전체 틀만 잡는다 — 각 항목의 상세 사양(API, DB 스키마, 화면 구성 등)은 이후 단계에서 순차적으로 정리한다.

이 문서는 서버·웹 쪽 신규 구성이다. 단말(ESP32) 쪽 MQTT/Icecast/파일다운로드 프로토콜 자체는 1차 사양을 그대로 쓰고, 여기서는 그 위에 얹히는 인증/운영/관리 계층만 다룬다.

전체 구조

```
[PC/태블릿 브라우저] --HTTPS--> [웹 프론트 (대시보드)]
                                      |
                                      v
                                [백엔드 API] --MQTTS--> [MQTT 브로커] <--MQTTS-- [ESP32 단말들]
                                      |
                                      v
                                  [DB] (단말 목록/이력/설정)

[ESP32 단말들] --HTTPS(Icecast)--> 실시간 오디오 (1차: 공개, 인증 없음)
[ESP32 단말들] --HTTPS(파일서버)--> 파일 다운로드 (만료 토큰 URL)
```

AWS 인스턴스 하나 안에 MQTT 브로커, 백엔드 API, DB, 파일 스토리지가 같이 올라간다. 수백 대 규모면 이 구성으로 충분하고, 별도 서버 분리나 클러스터링은 필요 없다고 본다.

판매 형태(확정): 고객마다 이 시스템을 통째로 복제해서 각자 독립된 AWS 서버/브로커/DB를 갖는다(A안). 여러 고객이 서버 하나를 같이 쓰는 멀티테넌트 구조가 아니므로, `iotradio/all/cmd` 같은 전역 토픽이 고객 간에 섞일 위험은 없다 — 별도의 테넌트 분리 설계는 필요 없음.

보안 모델

- TLS: 웹(HTTPS), MQTT(MQTTS/8883), 파일다운로드(HTTPS) 전부 적용. 인증서는 기존 `iot_radio.co.kr` 것 재사용. 단, ESP32가 NTP로 시간 동기화되기 전이면 인증서 유효기간 검증이 실패할 수 있어, 부팅 초기 시간 동기화 순서를 챙겨야 함(Codex 확인 필요).
- MQTT 인증: 단말 공용 계정 하나 + client-id(`iotradio-<mac>`) 기반 ACL로 각 단말이 자기 토픽에만 쓸 수 있게 제한 (A안, 앞서 합의).
- nginx 리버스 프록시 관련: MQTT(TCP)는 일반 nginx HTTP 리버스 프록시로 넘길 수 없음. nginx `stream{}` 모듈(TCP 프록시)을 쓰거나, MQTT 브로커의 TLS 포트를 직접 노출해야 함. HTTPS(웹/파일서버)는 기존 방식대로 http 리버스 프록시로 처리 가능.
- Icecast 스트림: 1차는 인증 없이 공개. 필요해지면 이후 추가.
- 파일 다운로드: 매번 새로 발급되는 URL에 만료 토큰을 심어서, 시간 지나면 무효화.
- 웹 로그인: 비밀번호 해싱 + 세션/토큰 기반.
- 역할별 권한 분리(확정, 필수 기능): 한 업체(A안 기준 서버 1대)가 내부적으로 마을 단위(3~10개 등)로 나눠 운영하는 경우를 지원한다. 계정에 역할(전체관리자/마을관리자)과 담당 village_id(복수 가능) 범위를 부여하고, 백엔드가 모든 API 응답(단말 목록/대시보드/이력/지도)과 방송 제어 요청을 그 범위로 필터링한다. MQTT/단말 프로토콜은 전혀 안 바뀐다 — 이미 있는 village_id/`iotradio/village/<id>/cmd` 위에 웹 애플리케이션 레벨 권한 체크만 얹는 구조. 전체관리자만 300대 전체를 본다.
- 개인정보 처리: 관리자 계정 등 개인정보를 다루게 되면 개인정보보호법 관련 검토가 필요할 수 있음 — 지금은 설계하지 않고 관리 포인트로만 남겨둠. 실제 개인정보 수집 범위가 정해지는 시점에 법률 검토 필요.

기능 영역

| 영역 | 핵심 기능 | 비고 |

| 로그인 | 관리자 인증, 역할별 권한 분리(전체관리자/마을관리자) | 마을관리자는 담당 village_id 범위만 조회/제어 가능 |
| 단말 관리 | 등록/수정/삭제, 목록 조회, 마을/구역 배정 | MAC, 별칭, 소속 마을/구역. village_id는 서버가 자동 부여(§ID 체계) |
| 방송 제어 | LIVE_START/STOP, FILE_START/STOP | 개별/마을/구역/전체 대상 선택(권한 범위 내에서만) |
| 파일 라이브러리 | 업로드/관리, 문장→MP3 변환(TTS, 다국어) | FILE_START용 파일. 녹음/실시간 부담 줄이는 용도. 1차: AWS Polly, 한/영/일/중 외 다수 언어 |

| 대시보드 | 요약 타일(온라인/오프라인/방송중/미배정 수), 단말 상태 목록, 진행 중 방송 패널, 이상 상태 알림, 지도 뷰 | STATUS/LIVE_STATS 집계, 지도는 카카오맵 |
| 설정 | CONFIG 발행 (주기 등) | 지금 control.bat 메뉴 7을 웹으로 대체 |
| 자동방송 스케줄 | 월/요일/시각 조건별 예약 방송 | 최대 10개 등록, 방송 중이면 스킵 |
| 펌웨어 업데이트(OTA) | 단말 펌웨어를 원격으로 배포 | 기존 파일서버(9002) 인프라 재사용. 전용 명령 OTA_START/OTA_APPLY/OTA_STATUS (ESP32측 확정, ONLINE_OTA_UPDATE_SPEC_2026-08-14.md) |
| 비용 조회 | 마을별/전체 AWS 사용 비용 확인 | 일 1회 배치 갱신. 마을별은 사용량 기반 추정치, 전체 실비용(Cost Explorer API)은 super_admin 전용 |

TTS(문장→MP3)는 ESP32/MQTT 쪽 변경 없이 파일 라이브러리 위에 얹는다. 텍스트 입력 → 언어/보이스 선택 → 미리듣기 → 방송하기(파일 저장 + FILE_START 발행) 흐름. 1차는 AWS Polly로 진행하고, 한국어 외에 영어/일본어/중국어를 포함해 Polly가 지원하는 다수 언어를 그대로 선택 가능(호출 파라미터만 다름, 구조 변경 없음). 한국어 품질이 부족하면 이후 Naver Clova 등으로 교체 검토.

자동방송 스케줄은 백엔드에 스케줄러(예: 1분마다 조건 체크)를 두고, 규칙(월/요일/시각/파일)이 현재 시각과 맞으면 그 파일로 FILE_START를 발행한다. 예: "1,2,3월 + 토요일 + 오전10시,오후4시 + 파일A" 같은 규칙을 최대 10개까지 등록. 이미 방송 중이면 그냥 건너뛴다 — 이건 새로 만들 필요 없이 기존 BUSY 정책(FILE_ABORT reason=BUSY, 자동 재시도 금지)을 그대로 재사용하면 된다. 규칙마다 대상(개별/마을/전체)도 방송 제어와 동일하게 선택하게 할지는 이후 상세 설계에서 확정.

펌웨어 업데이트(OTA)는 ESP32측이 확정한 설계를 그대로 따른다(PC/서버는 명령 발행 + 파일 서빙만 담당, 상세 로직은 단말 쪽 사양서 참고).

- 배포 파일은 USB 업데이트와 동일한 `IOT_RADIO.pkg` 포맷을 그대로 씀(P4_APP/P4_UI/C6_APP 등 항목을 선택적으로 포함). 서버는 이 파일을 기존 파일서버(9002) 인프라에 올려두기만 하면 됨.
- 명령은 FILE_START 재사용이 아니라 전용 3종: `OTA_START`(job_id/url/size/sha256/targets) -> `OTA_APPLY`(다운로드/검증 완료 후 실제 적용 개시, 별도 승인 단계) -> `OTA_STATUS`(단말이 진행 상태를 보고: ACCEPTED/PREPARE/DOWNLOADING/DOWNLOAD_DONE/WAIT_APPLY/WRITING_C6/WRITING_P4/READY_REBOOT/DONE/FAIL). 전부 QoS 1 고정.
- 다운로드/검증과 실제 flash 적용을 분리 — OTA_APPLY 이후에만 실제 쓰기가 시작되고, 그 직전에 단말이 MQTT/Icecast/HTTP 등 네트워크를 전부 끊는다. 즉 OTA_APPLY 이후로는 서버가 추가 상태를 못 받고, 재부팅 후 재접속된 STATUS의 펌웨어 버전으로 최종 성공 여부를 판단해야 함.
- OTA는 LIVE/FILE/RF 방송과 동급의 최상위 배타 상태로 취급됨 — 서버 쪽 UI도 OTA 진행 중인 단말엔 방송 버튼을 막아주는 게 자연스러움.
- 펌웨어 진위 검증(서명)이 실서비스 배포 전 필수 항목으로 못박혀 있음 — sha256만으론 무결성만 확인되고 정품 여부는 증명 안 되기 때문. 서버 측에선 pkg를 만들 때 private key로 서명하는 빌드 단계가 필요해짐(2차, 방식 확정은 ESP32측과 협의).
- 롤백/부트루프 방지(ESP-IDF OTA rollback 기능 활용, self-check 후에만 VALID 처리)는 1차 안전 요구사항으로 이미 반영됨 — 현장 벽돌 방지.

서버 자체 모니터링/알림 (간단한 방안)

- 백엔드에 `/health` 같은 상태 확인 endpoint를 두고 DB/MQTT 브로커/Icecast가 살아있는지 체크
- AWS CloudWatch로 인스턴스 기본 지표(CPU/디스크/메모리) 알람 설정 + SNS로 이메일/SMS 알림 — AWS 네이티브라 별도 도구 설치 없이 콘솔에서 몇 개 알람만 걸면 됨
- 외부 무료 업타임 모니터링(UptimeRobot 등)으로 `/health`를 주기적으로 확인하는 것도 손쉬운 보완책

DB 백업/복구 (간단한 방안)

- 자체 EC2에 Postgres를 직접 올리는 대신 **AWS RDS(관리형 Postgres)** 사용을 추천 — 자동 일일 백업 + 특정 시점 복구(PITR)가 설정 하나로 켜짐, 별도 백업 스크립트를 만들 필요가 없음
- 비용/구성을 최대한 단순하게 유지하고 싶어서 EC2에 직접 두는 쪽을 택하면, 매일 `pg_dump`로 덤프떠서 S3에 올리는 cron 하나로 대체 가능(수 줄짜리 스크립트)

MQTT 브로커 데이터 유실 시 CONFIG 복구

MQTT의 retain은 브로커 재시작에는 안전하다(mosquitto `persistence` 설정으로 실측 확인됨 — 강제 종료 후 재시작해도 CONFIG 값 보존). 다만 브로커가 완전히 초기화/재설치되어 persistence 데이터 자체가 사라지면 얘기가 다르다 — 이땐 retain된 CONFIG(village_id 배정 포함)가 전부 사라지고, 재접속하는 단말은 전부 펌웨어 기본값(village_id="00000000", 미배정)으로 돌아간다.

retain은 어디까지나 "전달 캐시"이고 진짜 정본은 서버 DB이므로, 백엔드에 **브로커 상태와 DB를 맞추는 재발행(reconciliation) 로직**을 넣어야 한다 — 백엔드 기동 시 1회, 또는 주기적으로 DB에 저장된 단말별 배정 정보를 CONFIG로 다시 발행해서, 브로커가 비어있는 상태를 자동으로 복구한다. 지금은 백엔드가 없어(control.bat이 대신) 이 복구가 수동이다.

위치 체계 및 ID 발급

- village_id: DB 자동 일련번호. 기존 펌웨어 포맷(8자리 문자열, `"00000001"`) 그대로 유지하며 서버가 순서대로 발급. 단말까지 전달되는 유일한 위치 식별 값.
- zone(구역, 건물/공원 등): 마을 하위 개념이지만 DB 안에만 존재. MQTT/펌웨어엔 안 실림 — 구역 단위 방송은 서버가 해당 구역 소속 단말 MAC 목록을 조회해서 각 단말 개별 토픽으로 나눠 발행.
- 단말 자체 식별자는 MAC을 그대로 사용(추가 device_id 불필요).
- 실제 도로명주소/건물명 등은 village/zone 레코드에 참고용 필드로만 저장 — ID를 만드는 재료가 아니라 관리자 화면에 보여주는 설명 텍스트.
- village_id는 펌웨어에 미리 굽지 않는다. 모든 단말은 동일 펌웨어로 출하하고, MAC 기반으로 접속하면 서버가 등록 여부를 판단한다. 미등록 단말은 STATUS(MAC 기준 토픽이라 마을 배정 전에도 옴)로 대시보드에 "미배정 단말"로 표시되고, 관리자가 마을/구역을 배정하면 서버가 CONFIG(retain)로 village_id를 내려준다. 접속 시 자동 수신되므로 재설치/이설 시에도 재작업이 대시보드 재배정만으로 끝난다. **CONFIG를 통한 village_id 전달/적용은 실제 ESP32와 테스트 완료(2026-08-13) — 서버가 고정값("00000001")을 CONFIG로 내려주고 단말이 받아 STATUS에 반영하는 것까지 확인됨.** 단말별로 다른 값을 배정하는 실사용 흐름은 대시보드 구현 단계에서 이어감.

주소 입력 UX: 시/도 + 시/군/구는 드롭다운(고정 목록)으로 표준화하고, 상세주소는 관리자가 **카카오 주소검색 API 사용 또는 수동 직접 입력 중 선택**할 수 있게 한다. 실제 주소는 참고/표시용일 뿐 ID를 만드는 재료가 아니므로, 어느 쪽을 택하든 시스템 동작에는 영향 없음 — 편의를 위한 선택권 제공.

지도 뷰: 카카오 주소검색 API로 입력하면 위도/경도가 같이 딸려오므로 별도 지오코딩 없이 카카오맵에 바로 표시 가능. 단말 위치에 마커를 찍고 상태별로 색을 구분한다(정상=초록, 방송중=파랑, 오프라인/이상=빨강, 미배정=회색). 마커 클릭 시 별칭/MAC/마을·구역/최근 상태 팝업. 좌표가 없는 단말(수동 입력을 택한 경우)은 지도에 안 뜨고 별도 "위치 미입력" 목록으로 표시.

기술 스택 (제안, 확정 아님)

- 백엔드: Node.js(Express) 또는 Python(FastAPI) + MQTT 클라이언트
- DB: Postgres, 가능하면 AWS RDS(관리형)로 — 백업/복구가 자동으로 딸려옴
- 프론트: React 기반 대시보드
- MQTT 브로커: 기존 Mosquitto 유지, TLS+인증 설정만 추가

온프레미스 전환 대비

지금은 AWS(A안, 고객별 독립 서버)로 진행하지만, 나중에 특정 고객 현장에 AWS 없이 자체 HW를 설치/운영해야 하는 경우가 생길 수 있다. 전환 비용을 낮추려면 지금 AWS로 구축하는 단계에서부터 아래 원칙을 지키는 게 좋다 — 개발 방식이 크게 바뀌는 것도 아니고, 나중에 급하게 다시 설계하는 것보다 훨씬 싸게 먹힌다.

핵심 원칙: MQTT 브로커/Icecast/파일서버/백엔드는 원래부터 AWS 전용 서비스가 아니라 그냥 리눅스 프로세스이므로 그대로 이식된다. 실제로 갈아끼워야 하는 건 DB(RDS)·백업·모니터링 3곳뿐이다.

| 영역 | AWS 버전 | 온프레미스 대체 | 비고 |
|---|---|---|---|
| DB | RDS(관리형 Postgres) | 로컬 Postgres 직접 설치 | `pg_dump`/`pg_restore`로 마이그레이션 |
| DB 백업 | RDS 자동 스냅샷/PITR | cron + `pg_dump` → 로컬/NAS(또는 그대로 S3, 인터넷만 되면 가능) | |
| 모니터링 | CloudWatch + SNS | Prometheus+Grafana 또는 Uptime Kuma(자체 호스팅) | `/health` 엔드포인트를 찌르는 방식은 동일 |
| TTS(Polly), 카카오 지도/주소 API | 그대로 사용 | — | REST API 호출일 뿐 호스팅 위치와 무관. 완전 폐쇄망(인터넷 자체가 없는 현장)일 때만 로컬 TTS 검토 |

지금 단계에서 준비해둘 것:

1. 컨테이너화(Docker Compose) — 백엔드/DB/MQTT/Icecast/파일서버를 컨테이너로 묶어서, EC2든 물리서버든 동일한 명령으로 기동되게 한다. 전환 비용을 가장 크게 줄이는 항목.
2. DB 접속정보를 환경변수로 완전 분리(`DATABASE_URL` 등) — RDS/로컬 Postgres 전환이 설정값 하나로 끝나게.
3. 파일 저장을 처음부터 로컬 디스크 기준으로 설계 — S3를 원본 저장소로 쓰지 않고 지금처럼 로컬 디렉토리 기준으로 가면 스토리지 전환 자체가 필요 없어짐.
4. 모니터링을 `/health` 엔드포인트 기준으로 설계(§서버 자체 모니터링/알림에 이미 반영) — 뒷단 감시 도구만 바뀌고 백엔드 코드는 그대로.
5. 배포 절차를 스크립트/문서로 남기기 — 1번(컨테이너화)이 되면 자연히 해결됨.

전환 시 별도로 검토해야 할 것(소프트웨어 설계로 해결 안 되는 인프라 문제):

- 네트워크: 물리 서버는 보통 NAT 뒤에 있어 공인IP가 없음 — 포트포워딩+DDNS, 또는 역방향 터널(Cloudflare Tunnel 등, MQTT는 TCP라 지원 여부 사전 확인 필요), 또는 완전 폐쇄망(외부 접근 자체가 불필요한 경우)
- TLS 인증서: 공인IP/DDNS가 있으면 서브도메인 발급 + Let's Encrypt로 동일하게 처리. 완전 폐쇄망이면 사설 CA 자체 서명 + ESP32에 해당 CA 루트 배포 필요(§보안 모델의 "ESP 공개 CA bundle" 관련 항목과 반대 방향 케이스)

대략적인 운영 비용 (고객 1곳당, 어림값)

아래는 정확한 견적이 아니라 규모감을 잡기 위한 어림 계산이다. 실제 판매 가격 산정 전에는 AWS 계산기(calculator.aws)로 다시 확인해야 한다.

| 항목 | 내용 | 월 비용(어림) |
|---|---|---|
| EC2 | t3.small~medium (MQTT+백엔드+Icecast+파일서버) | 약 2~4만원 |
| RDS(Postgres) | db.t3.micro급, 자동 백업 포함 | 약 2~3만원 |
| 데이터 전송(egress) | 아래 계산 참고 | 사용 패턴에 따라 수천원~수만원 |
| AWS Polly(TTS) | 안내문 위주 사용 | 거의 무시 가능(월 1천원 미만) |
| 카카오 주소/지도 API | 무료 티어로 충분할 것으로 예상 | 0원 예상(상용 판매 시 무료티어 약관 재확인 필요) |

**합계 어림: 월 10만원 정도면 여유 있게 커버되는 수준.** 데이터 전송량(=실시간 방송을 얼마나 오래/자주 켜두는지)이 제일 큰 변수.

데이터 전송비 계산 기준: 24kbps(현재 설정) 스트림 기준, 단말 1대가 1시간 들으면 24,000bit/s ÷ 8 = 3,000byte/s × 3600초 ≈ 10.8MB. **100대 × 1시간 = 약 1.08GB**, AWS egress 단가 약 $0.09~0.13/GB 기준 약 100~150원. 이 방송을 매일 한 달 내내 반복해도(30일 × 1.08GB = 32.4GB) 월 약 4천~6천원 수준 — 안내방송처럼 짧게 여러 번 쓰는 용도면 데이터 전송비가 예산에서 차지하는 비중은 작다.

비용 조회 기능

관리자가 마을별/전체 단위로 AWS 사용 비용을 확인할 수 있어야 한다. 다만 AWS 청구는 계정 전체 단위로만 나오고 "이 마을이 오늘 얼마 썼는지"를 AWS가 직접 쪼개주지 않으므로, 두 갈래로 나눠서 제공한다.

- 전체 실비용(참고용): 백엔드가 AWS Cost Explorer API로 계정 전체의 일별 비용(EC2/RDS/데이터 전송/Polly 등 합산)을 가져와 저장한다. 실측치라 정확하지만 마을 단위로는 쪼갤 수 없다 — super_admin 전용 참고 지표.
- 마을/단말별 추정 비용(배분): DB에 이미 쌓이는 실제 사용 이력(broadcast_events/device_events 기준 방송 시간 × 대상 단말 수)에 위 데이터 전송비 계산식(24kbps 기준)을 적용해 마을별 사용 비중을 추정한다. AWS가 확인해준 값이 아니라 내부 계산 추정치이므로 화면에 "추정치"임을 명시한다.

갱신 주기는 하루 1회(예: 매일 새벽 배치)로 충분하다 — 데이터 전송비 자체가 등락이 크지 않아 실시간 갱신은 비용/복잡도만 늘린다. 배치가 전날 사용 이력을 집계해서 마을별 추정치 + (전체 행에 한해) 실비용을 함께 저장하고, 화면은 이 저장된 값을 조회만 한다(요청마다 재계산하지 않음).

권한은 기존 역할별 권한 분리를 그대로 따른다 — village_admin은 자기 담당 마을의 추정 비용만 보고, super_admin은 전체 실비용 + 마을별 추정 비용을 모두 본다.

이후 진행 순서

1. 기술 스택 확정
2. MQTT 브로커 TLS/인증/ACL 상세 설정
3. DB 스키마 설계 (단말/이력/설정 테이블) — 1차 완료, xWIFI_DB_스키마_260815.md 참고
4. 백엔드 API 명세 — 1차 완료, xWIFI_API_설계_260815.md 참고
5. 프론트 화면별 상세 설계 (와이어프레임) — 1차 완료, xWIFI_화면_설계_260815.md 참고
6. 파일 다운로드 만료 토큰 방식 상세 설계
7. 단말 등록/village_id 동적 배정 흐름 상세 설계 (Codex와 조율 필요)
8. 대규모 방송 시작 정책 설계: LIVE_START 후 LIVE_READY를 얼마나/몇 % 기다렸다가 방송을 시작할지, BUSY/오프라인 단말 제외 처리, 단말별 STATUS timeout 판단 기준
9. OTA — 단말측 설계(OTA_START/APPLY/STATUS, 서명, 롤백)는 ESP32측에서 확정됨(2026-08-14). 서버 쪽 남은 일: pkg 빌드/서명 파이프라인, 배포 대상 선택 UI, OTA 진행 중 방송 버튼 잠금
10. CloudWatch 알람/SNS, RDS 백업 설정 — 실제 AWS 계정에 적용 (담당자 진행)
11. 백엔드 기동/주기 실행 시 DB→MQTT CONFIG 재발행(reconciliation) 로직 — 브로커 데이터 유실 시 자동 복구
12. 역할별 권한(전체관리자/마을관리자) DB 스키마 및 API 필터링 설계 — 확정된 필수 기능

배포는 담당자가 직접 진행하거나 명시적 접근 권한을 받은 뒤 진행한다 — 이 프로젝트 원칙(운영 서버 직접 접근 금지)은 이 단계에서도 유지한다.
