# xWIFI 관리자 계층 설계 (2026-09-08)

관리자 권한을 2계층(최고·마을)에서 4계층(최고·시도·시군·마을)으로 넓힌다. 이 문서는 그 결정과 데이터 모델, 권한 규칙의 정본이다. 문제점 리스트 21번 탭의 역할표(최고·중간·일반·게스트)를 **대체**한다 — 게스트 역할은 두지 않는다.

관련: [운영서버 구성 개요](xWIFI_운영서버_구성_개요_260813.md) · [DB 스키마](xWIFI_DB_스키마_260815.md) · [API 설계](xWIFI_API_설계_260815.md) · [화면 설계](xWIFI_화면_설계_260815.md) · [지도·위치 설계](xWIFI_지도_위치_설계_260831.md)

## 1. 핵심 결정

**권한은 조직 트리를 따른다. 주소는 트리의 입력값이 아니다.**

처음에는 법정동코드 앞자리(시도 2자리 · 시군구 5자리)로 관할을 자동 결정하는 안을 검토했다. 마을을 만들 때 주소만 넣으면 어느 군청·도청 소속인지 저절로 정해지므로 사람이 입력할 것이 없다는 장점이 있었다. 그러나 다음 시나리오에서 깨진다.

> 새로 영입한 라라마을은 주소상 루루군(강원)에 있다. 그런데 루루군청이 아니라 기존 고객인 금산군청(충남)이 관리하기로 구두 약속했다.

주소로 관할을 정하면 이 마을은 금산군청 계정에 영영 보이지 않는다. 보이게 하려면 주소를 거짓으로 넣어야 하고, 그러면 지도 폴리곤과 MQTT 토큰이 거짓이 된다. 지방 소도시에서 이런 위탁·겸임은 예외가 아니라 흔한 일이다.

그래서 **지리(주소)** 와 **관할(누가 관리하나)** 을 분리한다.

| | 지리 | 관할 |
|---|---|---|
| 저장 | `villages.b_code` | `villages.organization_id` |
| 정하는 것 | 주소 검색 | 사람 (기본값은 주소로 제안) |
| 쓰는 곳 | 지도 폴리곤, MQTT 토큰 | 권한 범위 |
| 바뀌는 때 | 행정구역 개편 | 위탁·이관 |

주소는 마을을 **만들 때 기관을 제안**하는 편의 기능으로만 남는다. 진실은 `organization_id` 하나다.

## 2. 역할

| `role` | 표시 | 범위 근거 | 계층 |
|---|---|---|---:|
| `super_admin` | 최고 관리자 | 전체 | 3 |
| `sido_admin` | 시·도 관리자 | 소속 기관의 하위 기관 트리 | 2 |
| `sigungu_admin` | 시·군 관리자 | 소속 기관 | 1 |
| `village_admin` | 마을 관리자 (이장) | `user_villages` (지금과 같음) | 0 |

「군청」이 아니라 「시·군」인 이유: 나주시처럼 시청이 관할하는 농촌이 있다. 기관 이름은 자유 텍스트라 「금산군청」「나주시청」으로 쓰면 된다.

계층 숫자는 "누가 누구를 관리하나"의 순서다. 자기보다 낮은 계층의 계정만 만들고 고칠 수 있다.

## 3. 데이터 모델

```
organizations
  id, name, level ('sido' | 'sigungu'), parent_id → organizations, jurisdiction_code, created_at

villages.organization_id  → organizations  (NULL 허용, ON DELETE RESTRICT)
users.organization_id     → organizations  (NULL 허용, ON DELETE RESTRICT)
user_villages             → 그대로 (village_admin 전용)
```

```
                 ┌─────────────┐
                 │ 충남도청 (sido)│
                 └──────┬──────┘
          ┌─────────────┴──────────────┐
   ┌──────┴──────┐              ┌──────┴──────┐
   │ 금산군청(sigungu)│              │ 논산시청(sigungu)│
   └──────┬──────┘              └──────┬──────┘
     ┌────┴────┬──────────┐            │
  금산마을   계곡마을   라라마을(주소는 강원)   …
```

규칙:

- `level='sigungu'` 기관의 `parent_id` 는 `level='sido'` 기관이거나 NULL 이다. `sido` 는 `parent_id` 가 항상 NULL 이다. 두 단계뿐이라 재귀 질의를 쓰지 않는다.
- `jurisdiction_code` 는 시도 2자리 또는 시군구 5자리 법정동코드 앞자리다. **제안용**이다 — 마을을 만들 때 `b_code` 와 가장 길게 일치하는 기관을 기본값으로 띄운다. 권한 판정에는 쓰지 않는다. NULL 이면 제안에서 빠질 뿐이다.
- `villages.organization_id` 가 NULL 인 마을(주소 없는 시험 마을 등)은 최고 관리자만 본다. 주소가 없어 8자리 옛 토큰을 쓰는 지금 규칙과 같은 선이다.
- 기관은 소속 마을·계정이 하나라도 있으면 지울 수 없다(`ORGANIZATION_IN_USE`). 먼저 옮기거나 지운다.
- `users.organization_id` 는 `sido_admin`·`sigungu_admin` 에만 있다. `village_admin` 은 `user_villages`, `super_admin` 은 둘 다 없다. 역할과 맞지 않는 값은 API 가 거부한다.

## 4. 범위 산출

로그인·요청마다 `VillageScope`(마을 id 집합)를 만든다. **이 아래 계층은 바뀌지 않는다** — 조회 필터, 겹침 검사, MQTT 발행 직전 2중 방어가 전부 이 집합만 본다.

| 역할 | 마을 집합 |
|---|---|
| `super_admin` | 전체 (`all_villages=True`) |
| `sido_admin` | `organization_id = 내 기관 OR organization_id IN (parent_id = 내 기관인 기관들)` |
| `sigungu_admin` | `organization_id = 내 기관` |
| `village_admin` | `user_villages` |

기관이 NULL 인 시도·시군 관리자는 빈 범위다. 담당 마을 없는 마을 관리자와 같은 상태이고 화면 경고도 같다.

## 5. 권한 매트릭스

원칙: **운영은 관할 전체에, 구조 변경은 출발지와 도착지가 모두 내 관할일 때만, 계정은 나보다 낮은 계층만.**

| | 이장 | 시·군 | 시·도 | 최고 |
|---|---|---|---|---|
| 단말 상태·이상단말·지도·이력 조회 | 내 마을 | 관할 | 관할 | 전체 |
| 방송 시작·중지·스케줄·파일함 | 내 마을 | 관할 | 관할 | 전체 |
| 전체(`all`) 대상 방송 | ✗ | ✗ | ✗ | ○ |
| 비용 조회 (API 미구현) | 내 마을 | 관할 | 관할 | 전체 |
| 구역 추가·수정·삭제 | 내 마을 | 관할 | 관할 | 전체 |
| 단말 별칭·위치 수정 | 내 마을 | 관할 | 관할 | 전체 |
| 단말 마을 이동 | ✗ | 관할 안에서 | 관할 안에서 | 전체 |
| 마을 추가·수정·삭제 | ✗ | 관할 안에서 | 관할 안에서 | 전체 |
| 마을의 관리 기관 변경 | ✗ | ✗ | 하위 기관 사이 | 전체 |
| 계정 생성·수정·기간·삭제 | ✗ | 이장 | 시·군, 이장 | 전체 |
| 기관 생성·삭제 | ✗ | ✗ | ✗ | ○ |
| 신규 단말 등록 (MQTT 계정 발급·재발급) | ✗ | ✗ | ✗ | ○ |
| 미배정 단말 조회·배정 | ✗ | ✗ | ✗ | ○ |
| 단말 삭제 | ✗ | ✗ | ✗ | ○ |
| OTA · CONFIG 설정 | ✗ | ✗ | ✗ | ○ |

「계정은 낮은 계층 전부」로 둔다 — 시·도가 이장 계정까지 만들 수 있다. 「바로 아래 계층만」으로 좁혀도 지켜지는 것이 없고, 군청 계정이 없는 도청이 이장을 등록해야 하는 경우가 실제로 있다.

`all` 대상 방송을 최고 관리자에 묶는 이유: 시·도 관리자가 관할 전체에 방송하려면 `village` 대상에 관할 마을 전부를 넣으면 된다. `all` 은 "시스템의 모든 단말"이고 그건 개발자만 눌러야 한다.

## 6. 구조 변경 규칙

### 6.1 단말의 마을 이동

정당한 동작이다. 단말은 실제로 옮겨 달리고 설치 때 마을을 잘못 고르기도 한다.

- 출발 마을과 도착 마을이 **모두** 관할 안이어야 한다. 군을 넘는 이동은 도청이나 최고 관리자가 한다.
- 화면은 **확인 대화상자**다. 드래그 앤 드롭을 쓰지 않는다. 마을이 바뀌면 단말의 CONFIG(village_id 토큰)가 다시 내려가고 ACL 이 재생성되며 어느 마을의 긴급방송을 받을지가 바뀐다. 태블릿에서 손가락이 미끄러져 옆 마을에 떨어지는 일에 확인 없이 일어나서는 안 된다. 드래그는 지도 핀 위치(장식 정보)에만 쓴다.
- 백엔드는 이미 `update_device` 가 CONFIG 재발행·ACL 재생성까지 한다. 추가되는 것은 출발 마을 관할 검사뿐이다.

### 6.2 마을의 관리 기관 변경

정당한 동작이다. 라라마을이 그 예다.

- 출발 기관과 도착 기관이 모두 관할 안이어야 한다. 시·도 관리자는 자기 하위 기관 사이에서만, 도를 넘는 이동은 최고 관리자가 한다.
- 이것도 확인 대화상자다.
- `b_code`·`village_code`·폴리곤·단말 CONFIG 는 **아무것도 바뀌지 않는다.** 단말은 누가 관리하는지 모르고 알 필요도 없다.

### 6.3 주소 수정은 관할 변경이 아니다

마을 주소를 잘못 넣은 것을 고치는 것은 `b_code` 수정이다. 관할은 그대로다. 지도 설계 §1.3 대로 `village_code` 도 고정이다. 주소를 처음 넣어 옛 8자리 토큰이 12자리로 바뀌는 경우만 단말 CONFIG 가 다시 내려간다(지금과 같음).

## 7. 시나리오: 라라마을

1. **영입.** 최고 관리자가 마을을 만든다. 주소를 넣으면 `b_code` 는 루루군 코드로 정확히 들어가고 폴리곤도 실제 위치에 그려진다. 관리 기관 칸은 주소로 제안할 기관이 없어 비어 있고, 드롭다운에서 **금산군청**을 고른다. 루루군청 기관은 만들지 않는다.
2. **다음 날 금산군청 직원 로그인.** 범위가 `organization_id = 금산군청` 으로 풀리므로 라라마을이 바로 보인다. 금산군청 계정 전부, 앞으로 만들 계정도 마찬가지다.
3. **1년 뒤 루루군청이 직접 하기로 함.** 최고 관리자가 기관 「루루군청」을 강원도청 아래에 만들고 라라마을의 관리 기관을 바꾼다. 한 번의 변경으로 금산군청 전 계정에서 사라지고 루루군청 전 계정에 나타난다. 단말은 아무것도 모른다.
4. **루루군청 계정을 마을보다 먼저 만들면** 빈 범위로 로그인된다. 담당 마을 없는 마을 관리자와 같은 상태다.

결과 하나를 명시한다: 라라마을은 **충남도청 관리자에게 보이고 강원도청 관리자에게는 보이지 않는다.** 관할은 조직 트리를 따르지 지리를 따르지 않는다. "자기 땅에 있는 마을은 다 봐야 한다"는 요구가 생기면 그것은 관할이 아니라 **조회 전용 지리 범위**라는 별개 개념이며, 이번에는 넣지 않는다.

## 8. 진행 중 방송의 가시성

기존 결함(현행 문서 README 8번)을 이 작업에서 같이 고친다. 지금은 `target_scope=village` 이고 `target_ids` 에 담당 마을이 직접 들어 있을 때만 보였다. `device`·`zone`·`all` 대상은 마을을 바로 알 수 없어 보수적으로 감췄고, 그래서 마을 관리자가 자기 단말 몇 대에 시작한 방송이 진행 중 목록에서 안 보이는 일이 있었다. 계층이 늘면 더 자주 드러난다.

새 규칙: **대상 단말의 소속 마을 중 하나라도 내 범위면 보이고, 보이면 중지할 수 있다.**

| `target_scope` | 판정 |
|---|---|
| `village` | 대상 마을 중 하나라도 범위 안 |
| `zone` | 구역의 마을이 범위 안 |
| `device` | 대상 단말의 마을 중 하나라도 범위 안 |
| `all` | 범위가 비어 있지 않으면 보인다 |

"보이면 중지할 수 있다"는 기존 방침의 연장이다 — 다중 마을 방송은 관련된 모든 관리자가 봐야 중지도 할 수 있다. `all` 방송을 마을 관리자가 중지하면 전체가 멈춘다. 이는 의도한 동작이다. 자기 마을 스피커에서 나가는 소리를 멈출 권한은 누구에게나 있어야 한다.

## 9. 화면

- **사이드바**: 메뉴마다 최소 계층을 둔다. 설정·OTA 는 최고, 마을 관리·계정 관리·기관 관리는 시·군 이상(기관 관리는 최고). 역할 표시 문구가 넷이 된다.
- **계정 관리**: 역할 드롭다운에 내가 만들 수 있는 역할만 나온다. 시도·시군 역할이면 기관 선택, 이장이면 담당 마을 체크박스. 목록에 기관 열이 추가된다.
- **마을 관리**: 관리 기관 드롭다운. 주소를 고르면 `b_code` 로 제안 기관을 자동 선택하되 바꿀 수 있다. 시·군 관리자에게는 자기 기관으로 고정된다. 목록에 기관 열이 추가된다.
- **기관 관리** (최고 관리자): 이름·수준·상위 기관·관할 코드. 소속 마을 수·계정 수를 같이 보여 삭제 가능 여부를 알 수 있게 한다.
- **단말 관리**: 배정 대화상자는 지금 그대로다. 관할 밖 마을은 드롭다운에 애초에 나오지 않는다(마을 목록이 범위 필터를 탄다).
- **대시보드**: 바뀌지 않는다. 마을 목록이 범위를 따라 늘고 줄 뿐이다.

## 10. 마이그레이션 0015

- `organizations` 생성
- `villages.organization_id`, `users.organization_id` 추가 (NULL, RESTRICT)
- `users.role` CHECK 제약에 `sido_admin`, `sigungu_admin` 추가

기존 데이터는 그대로 유효하다. 기존 `super_admin`·`village_admin` 계정과 마을은 아무 변경 없이 지금과 똑같이 동작한다. 기관은 필요할 때 만든다.

## 11. 이번에 넣지 않는 것

- 조회 전용 지리 범위 (§7)
- 마을별 비용 조회 API (현행 문서 README 5번) — 매트릭스의 「비용 조회」 행은 API 가 생기면 그 규칙을 따른다
- 특례시의 구 단위 기관 — `level='sigungu'` 에 `jurisdiction_code` 5자리로 표현할 수 있으므로 별도 수준을 두지 않는다
- 시·도 관리자가 하위 기관을 직접 만드는 것 — 기관 생성은 최고 관리자만. 필요해지면 권한만 연다
- 계정별 파일함 분리 (문제점 28번) — 파일함은 전체 공용으로 유지. 계층별 분리가 필요하면 별도 설계
