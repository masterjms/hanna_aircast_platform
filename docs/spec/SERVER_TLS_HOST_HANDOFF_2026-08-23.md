## 1. 인프라 구성 (확정)

**AWS EC2 인스턴스 1대**에 다음을 모두 올린다.

```text
- MQTT 브로커 (mosquitto 등), mqtts 리스너 (기본 8883)
- Icecast, https로 노출 (nginx 리버스 프록시 등으로 TLS 종단)
- 파일 다운로드 서버, https로 노출 (nginx 등)
```

ALB/NLB/ACM 같은 AWS 관리형 로드밸런서 인증서 방식은 쓰지 않는다. MQTT는 TCP 패스스루가 필요해 구성이 늘어나고, 지금 규모(단일 서버, 소규모 커뮤니티 방송)에는 과하다. EC2 인스턴스에 직접 인증서 파일을 두고 mosquitto/nginx 양쪽에 물리는 방식으로 간다.

- 실제 도메인 확정 및 DNS 설정(해당 EC2로 연결).
- 보안그룹에서 mqtts(8883), https(443 또는 지정 포트) 오픈.

## 2. URL 구조 (확정: 서브도메인 없이 단일 도메인 + path)

`live.xxxxxx.co.kr`, `file.xxxxxx.co.kr` 같은 서브도메인 방식은 쓰지 않는다. **도메인 하나 + path**로 서비스를 구분한다.

이유:

- 서브도메인 방식은 와일드카드 인증서(`*.xxxxxx.co.kr`)가 필요하고, Let's Encrypt로 와일드카드를 받으려면 DNS-01 인증(도메인 등록업체 API 키를 서버에 넣어 TXT 레코드 자동 생성)이 필요해 설정이 한 단계 늘어난다. 단일 도메인 + path 방식은 일반 인증서 + HTTP-01 인증으로 충분하다.
- 지금은 모든 서비스가 EC2 한 대에 몰려 있어(§1) 서브도메인으로 나눠도 실질적으로 같은 IP를 가리킨다. 서브도메인이 유리해지는 시점은 나중에 Icecast/파일서버를 다른 서버로 분리할 때다 — 지금은 아니다.

`xxxxxx.co.kr`로 확정됐다고 가정한 예시:

```text
[MQTT]
mqtts://xxxxxx.co.kr:8883
(경로 없음. 토픽은 iotradio/device/<mac_nocolon>/cmd 등으로 MQTT 프로토콜 안에서 별도로 오간다)

[Icecast 실시간 방송 - 지금 테스트 중인 고정 mount, icecast_base_url 기본값]
https://xxxxxx.co.kr/live

[Icecast 실시간 방송 - 다음 단계 마을별 mount, 서버가 LIVE_START.stream_url로 매번 완성해서 전달]
https://xxxxxx.co.kr/live/00000001/9      (마을 00000001, job_id 9)
https://xxxxxx.co.kr/live/all/9           (전체 방송, job_id 9)

[파일 다운로드 - 서버가 FILE_START.https_url로 매번 완성해서 전달]
https://xxxxxx.co.kr/file/notice-1780000001-W.mp3
```

포트 표기: mqtts는 `:8883`을 명시(기존 코드 관례), https 쪽(Icecast/파일)은 nginx가 443으로 받아 내부적으로 지금 테스트 포트(8000, 9002)로 프록시하므로 클라이언트가 보는 URL에는 포트를 붙이지 않는다.

## 3. 인증서 (확정: Let's Encrypt)

**CA는 Let's Encrypt로 확정한다.** EC2 인스턴스에서 certbot으로 발급/자동 갱신한다.

- 도메인 하나에 인증서 1개를 발급해서 mosquitto(mqtts)와 nginx(https, Icecast/파일서버) **양쪽에 동일하게 적용**한다. 서비스별로 다른 CA/인증서를 쓸 이유가 없다.
- certbot 자동 갱신을 반드시 cron/systemd timer로 설정한다. Let's Encrypt 인증서는 유효기간 90일이라, 갱신이 안 되면 만료 시 모든 단말이 한꺼번에 연결 실패한다.
- mosquitto/nginx 설정 모두 **체인 전체(`fullchain.pem`)**를 물린다. 리프 인증서만 물리면 중간 인증서가 빠져서 단말이 신뢰 경로를 완성하지 못할 수 있다.
- 단말은 Let's Encrypt 루트 **ISRG Root X1과 X2 두 장**만 담은 커스텀 번들을 쓴다. X2는 Let's Encrypt가 ECDSA 인증서를 그쪽에서 발급하기 때문에 필요하다 — X1만 두면 서버가 ECDSA로 받는 순간 붙지 못한다. CA가 안 바뀌는 한(리프가 90일마다 갱신돼도) 단말 쪽 재작업은 없다.
- 이것은 **CA 제한이지 서버 인증서 pinning이 아니다.** Let's Encrypt가 발급한 다른 도메인의 정상 인증서도, URL이 그 도메인이면 검증을 통과한다. 서버 한 곳만 허용하려면 별도 조치가 필요하다.

## 4. URL 발행 방식 변경

- `LIVE_START.stream_url`, `FILE_START.https_url`을 지금처럼 `http://192.168.0.x` 테스트값이 아니라 실제 `https://` URL로 발행하도록 서버 로직 반영.
- `SERVER_VILLAGE_STREAM_URL_POLICY_2026-08-21.md` §7에 이미 남겨진 미해결 사항(서버측 동적 mount 생성 로직, 마을/전체 방송 mount 분리)도 이 시점에 같이 처리하는 게 자연스럽다 — 지금 PC 테스트 구성(`Icecast_시작.bat`, 고정 mount)은 그대로 못 쓴다.

## 5. 단말에 최종 전달해야 할 값

**단말이 저장하는 것은 host 하나뿐이다.**

```text
server_host = <host>       예: hanna-aircast.co.kr
```

`mqtts://<host>:8883`과 fallback Icecast URL은 **단말이 이 host로 조립한다.** scheme·포트·경로는 코드에 고정돼 있다.

LIVE/FILE/OTA가 실제로 쓰는 URL은 저장값이 아니라 **각 MQTT 명령이 매번 완성된 형태로 내려주는 값**이다(`LIVE_START.stream_url`, `FILE_START.https_url`, `OTA_START.url`).

host는 단말 NVS에 남으므로 최종 확정 전까지는 여러 번 안 바뀌는 게 좋다(바뀔 때마다 단말 재설정 필요).

## 5.1 브로커 접근 제어 (2026-08-26 추가)

이 문서를 처음 쓸 때 빠져 있던 항목이다. 서버가 알아서 넣었고 그 판단은 맞았지만, 사양에 없어서 단말이 모르고 만들었다가 통합 시점에 두 번 막혔다.

- **계정은 단말마다 다르다.** username이 그 단말의 MAC이다(§5.2). ACL은 **`%u`**(비밀번호로 증명된 값)로 건다.
- **`client_id`는 콜론 없는 소문자 MAC이다.** 접두사를 붙이지 않는다. username과 같은 값이라 브로커 로그와 topic이 그대로 대조된다.
- **허용할 topic 목록은 `SERVER_COMM_MQTT_ICECAST_HTTP_SPEC_2026-08-14.md` §2.1에 있다.** 특히 `iotradio/village/<village_id>/cmd`는 MAC이 아니라 서버가 배정한 값이 들어가서 `%u`로도 잡히지 않는다 — 별도 규칙이 필요하다.

**ACL로 막힌 발행·구독은 에러가 아니라 조용히 버려진다.** 단말은 정상으로 보이고 서버에만 안 나타난다. 규칙을 조일 때는 위 목록과 대조해야 한다.

## 5.2 브로커 계정 id / pw (2026-08-27 추가)

2026-08-26에 서버에서 계정을 발급받아 단말에 반영했고, **연결까지 확인됐다**. 아래는 그 값을 정리한 것과 한 가지 변경 요청이다.

### 확정된 방식 (2026-08-30 갱신)

> **공유 계정에서 단말별 계정으로 바뀌었다.** 아래가 최신이고, 상세는 `SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md`에 있다.

| 항목 | 값 | 결정 주체 |
|---|---|---|
| **username** | **콜론 없는 소문자 MAC** — `client_id`와 같은 값 | 확정 |
| **password** | **MAC별 랜덤 8자.** 서버가 발행하고 DB에 보관 | **서버** |
| client_id | 콜론 없는 소문자 MAC | 확정 |

- **단말마다 계정이 다르다.** 하나가 뚫려도 그 단말 하나로 끝난다. ACL은 `%c`(주장하는 값)가 아니라 **`%u`**(비밀번호로 증명된 값)로 건다.
- **현장에 나가 있는 단말이 없으므로 일괄로 바꾼다.** 공유 계정을 남겨 둘 이행 기간이 필요 없다.
- **password 문자 집합**: `a-z A-Z 0-9 # $ % ^ & * - _ + = ? . ~`. **`@`는 쓰지 않는다** — 시리얼 프로토콜이 요청의 끝을 `@END`로 판정하므로 값 안에 들어가면 전송이 잘린다.
- **8자인 이유**: 예외적으로 단말 화면에서 손으로 칠 수 있어야 한다. 터치가 없어 버튼으로 글자를 하나씩 고른다.

  아래 범위는 단말이 받아들이는 한계다. 8자는 그 안에 넉넉히 든다.

  | | 한계 |
  |---|---|
  | username | 최대 63자 |
  | password | 최대 127자 |
  | 문자 | ASCII 표시 가능 문자만 (`0x20`~`0x7E`) |

  범위 밖 값은 **생산·현장 시리얼 설정에서 거절되어 단말에 들어가지 않는다.**

### 변경 요청: 단말별 계정으로

현재 발급받은 계정은 전 단말이 공유하는 `xwifi-device` 하나다. **단말별 계정으로 바꿔달라.**

**username은 그 단말의 MAC이다.** 지금 `client_id`로 쓰고 있는 값과 같으므로 새로 만들 것이 없다 — 등록 화면이 스캔한 MAC을 그대로 쓴다.

> 이전 판에서 `iotradio-device`로 이름만 바꿔 달라고 요청했었다. **그 요청은 철회한다.** 공유 계정 자체를 없애므로 이름을 정할 일이 없어졌다.

**password는 MAC마다 다른 값을 서버가 발행한다.** 생산 등록 화면이 그 값을 받아 시리얼로 단말에 넣는다.

지금 붙은 단말이 개발용 1대뿐이라 **바꾸는 비용이 거의 없다.** 발행 절차와 ACL은 `SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md` §2에 있다.

### 왜 8자인가 (요청 아님, 판단 근거)

**예외적으로 단말 화면에서 비밀번호를 손으로 칠 일이 있다.** 터치가 없어 버튼으로 글자를 하나씩 고르므로 길면 실용적이지 않다.

**짧아도 되는 이유는 password가 단말에만 있고 브로커가 해시로 보관하기 때문이다.** 온라인 추측은 브로커가 감당할 수 있는 횟수를 한참 넘고, 오프라인 공격은 password 파일이 새어야 성립한다.

**뚫려도 그 단말 하나다.** 계정이 단말마다 다르므로 하나가 새도 나머지는 그대로다 — 공유 계정에서 길이를 늘리는 것보다 이쪽이 실제 방어다.

## 6. 참고

- **`village_id` 형식과 단말 등록 항목은 이 문서에 없다.** `SERVER_DEVICE_REGISTRY_2026-08-27.md`로 옮겼다 — 이 문서는 "어디에 어떻게 붙는가"이고 그쪽은 "붙은 단말이 누구인가"라 성격이 다르다.
- 단말은 host 외 다른 부분은 바꾸지 않는다 — scheme(`mqtts://`, `https://`)과 URL 경로 구조는 이미 단말 코드에 고정돼 있다.
- TLS 적용 이후 단말은 평문(`mqtt://`, `http://`)으로 폴백하지 않는다. 인증서 문제가 있으면 연결 실패로 처리되니, 3절의 인증서 요건(Let's Encrypt, 자동 갱신, 전체 체인)을 꼭 지켜달라.
