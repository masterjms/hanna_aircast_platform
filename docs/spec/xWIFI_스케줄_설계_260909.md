# xWIFI 자동방송 스케줄 설계 (2026-09-09)

관련: [운영서버 구성 개요](xWIFI_운영서버_구성_개요_260813.md) · [DB 스키마](xWIFI_DB_스키마_260815.md) · [API 설계](xWIFI_API_설계_260815.md) · [화면 설계](xWIFI_화면_설계_260815.md) · [관리자 계층 설계](xWIFI_관리자_계층_설계_260908.md)

## 1. 핵심 결정

**규칙 하나만 저장하고 실행 날짜는 계산한다 — cron 과 같다.**

"매월 2일 09:00" 은 DB 에 한 줄이다. 1월 2일, 2월 2일 … 은 어디에도 저장하지 않는다. 실행기는 매분 "지금 이 1분 안에 걸리는 규칙이 있나"를 계산하고, 화면의 예정표는 "앞으로 7일 안에 걸리는 회차가 몇 번인가"를 계산한다. 둘 다 같은 함수(`app/modules/schedule/rules.py`)를 부르므로 **예정표에 보이는 것과 실제로 나가는 것이 어긋날 수 없다.**

미리 펼쳐서 넣지 않는 이유: 규칙을 고치면 열두 줄을 다 고쳐야 하고, "언제까지 펼쳐 둘 것인가"에 답이 없다. 저장되는 것은 **지난 것뿐**이다 — 실제로 걸린 회차의 기록(`schedule_runs`).

단말 프로토콜은 바뀌지 않는다. 실행 시점에 기존 `FILE_START` 를 그대로 쏜다.

## 2. 규칙

| `repeat` | 추가 값 | 뜻 |
|---|---|---|
| `daily` | — | 매일 |
| `weekly` | `weekdays` 0=일 … 6=토 | 매주 그 요일 |
| `monthly` | `month_days` 1~31 | 매월 그 날. **그 날이 없는 달은 건너뛴다**(31일 → 30일까지인 달) |
| `yearly` | `year_dates` [{month, day}] | 매년 그 날. 2월 29일은 윤년에만 |

시각은 **하나**(`fire_time`, 분 단위). 시각을 둘 원하면 규칙을 둘 만든다(화면 목업 기준 — 옛 스펙의 `times[]` 는 버렸다). 모든 시각은 **Asia/Seoul** 이다. DB 의 `fire_time` 은 timezone 없는 TIME 이고 그 값이 곧 한국 시각이다.

## 3. 대상

| `target_scope` | `target_ids` | 실행 시 |
|---|---|---|
| `village` | 마을 id (하나) | 그 마을 전 단말 |
| `device` | MAC 목록 | 그 단말들 |
| `organization` | 기관 id | **실행 시점에** 기관(자기 + 바로 아래 기관)의 마을로 펼친다 |

`organization`(화면의 「군청관할 / 시청관할」)은 저장할 때 마을 목록으로 풀지 않는다. 실행할 때 풀어야 **나중에 영입한 마을이 자동으로 들어간다.** 실행기가 `village` + 구체 마을 id 로 펼쳐 방송을 걸므로 `broadcast_events` 와 이력·겹침 검사는 지금 그대로다 — `organization` 은 `schedules` 표 안에만 존재한다.

방송 대상의 `zone`·`all` 은 스케줄에 없다. 화면 흐름이 「마을 → 단말」이라 구역이 끼지 않고, 전체 방송은 최고 관리자가 기관을 골라 관할 전체로 걸면 된다.

## 4. 데이터 모델 (마이그레이션 0016)

```
schedules
  id, repeat, weekdays[], month_days[], year_dates(jsonb), fire_time(time)
  file_id, target_scope, target_ids(jsonb), store_flash, enabled, created_by, created_at

schedule_runs
  id, schedule_id (CASCADE), fire_at(timestamptz), status, reason, event_id (SET NULL), created_at
  UNIQUE (schedule_id, fire_at)
```

`schedule_runs.status`: `pending`(처리 중) → `started`(방송 걸림, `event_id`) | `skipped`(이번 회차만 못 나감, `reason`) | `failed`(예외, `reason`).

옛 `months[] + weekdays[] + times[]` 는 매월 15일·매년 3월 1일을 표현할 수 없어 갈아엎었다. 표에 데이터가 없어 이행은 없다.

## 5. 실행기

`app/tasks/schedule_runner.py`. APScheduler 에 1분 간격 job 으로 붙는다(CONFIG 재조정·계정 만료와 같은 스케줄러).

```
tick(매분)
  → 켜진 규칙 읽기
  → 창 [floor(now) − 유예, floor(now) + 1분) 의 실행 시각 계산
  → schedule_runs INSERT (pending)      ← 유니크 충돌 = 이미 처리됨 → 물러남
  → now − fire_at > 유예(120초) 이면 skipped(늦음)
  → organization 이면 마을로 펼침
  → start_file_broadcast(scope=super_admin, triggered_by=NULL, schedule_id=…)
  → ApiError(겹침·온라인 없음·파일) → skipped + 사유 / 그 밖의 예외 → failed
```

**중복 실행 방지의 실체는 코드가 아니라 `UNIQUE(schedule_id, fire_at)` 다.** INSERT 를 방송보다 먼저 하므로 서버가 재시작해도, 같은 분에 tick 이 두 번 돌아도, 워커가 둘이어도 한 회차는 한 번만 나간다. 대신 INSERT 직후 프로세스가 죽으면 그 회차는 `pending` 으로 남고 나가지 않는다 — 마을 방송에서는 두 번 나가는 것보다 한 번 빠지는 것이 낫다.

창에 유예만큼 과거를 포함하는 이유: tick 이 밀려 한 분을 건너뛰어도 그 회차가 다음 tick 의 창에 들어온다. 이미 처리한 회차는 유니크가 걸러 준다.

**재시도는 하지 않는다.** 마을 방송은 시각이 의미다. 10:00 안내를 10:07 에 내보내는 것은 사고이고, 재시작 뒤 밀린 회차가 한꺼번에 터지는 것은 더 큰 사고다. 유예를 넘긴 회차는 `skipped(N초 늦어 건너뜀)` 으로 기록만 남기고, 화면의 「최근 결과」가 그걸 보여준다.

이미 방송 중인 단말과 겹치면(`BROADCAST_OVERLAP`) 그 회차는 건너뛴다. 진행 중인 방송을 절대 끊지 않는다 — 운영서버 개요의 원안 그대로다.

## 6. 권한

관리자 계층 설계의 `VillageScope` 를 그대로 탄다. 규칙만 셋이다.

| | 규칙 |
|---|---|
| 보기 | 대상이 내 범위와 **하나라도** 겹치면. 진행 중 방송 가시성과 같은 판정 |
| 수정·삭제·켜기끄기 | 대상 **전체**가 내 범위 안일 때만 (`editable`) |
| 만들기 | 대상이 내 범위 안. `organization` 은 내 관할 기관이어야 |

방송 중지는 "보이면 멈춘다"가 맞지만 그건 긴급 제어다. 군청이 건 관할 전체 스케줄을 이장이 지우면 안 된다. 수정할 때 대상을 바꾸는 경우도 새 대상 전체가 내 범위여야 한다 — 남의 마을로 옮겨 놓고 손을 떼는 일을 막는다.

상한은 **시스템 전체 100개**(`SCHEDULE_MAX`). 원안 10개는 단일 고객 전제였고 도청 관할이면 부족하다. 1분 tick 이 100개를 평가하는 것은 부담이 아니다.

## 7. API

```
GET    /api/schedules                         내 범위와 겹치는 스케줄 (editable, next_fire_at, last_run 포함)
POST   /api/schedules
PATCH  /api/schedules/:id                     enabled 만 보내면 켜기·끄기
DELETE /api/schedules/:id
GET    /api/schedules/occurrences?from&to     [from, to) 의 예정 회차 — 서버가 규칙에서 계산. 최대 31일
GET    /api/schedules/:id/runs                최근 실행 결과 30건
```

`POST`/`PATCH` 검증: 매주인데 요일이 비면 거절(영영 안 나가는 규칙), 종류에 안 맞는 값은 비워 저장(나중에 종류를 바꿨을 때 옛 값이 튀어나오지 않게), 초는 버림, 요일·날짜는 중복 제거·정렬.

## 8. 화면

목업(2026-09-09) 그대로. 라이브러리는 **react-day-picker v9 + date-fns** 둘뿐이다 — 매년 날짜를 달력에서 고르는 데만 쓴다. 요일·날짜 격자, 오전/오후·시·분 선택, 기관→마을 트리, 7일 예정표는 직접 그린다(각각 작고, FullCalendar 는 200KB 급인데 예정표는 글자 들어간 표다).

**추가·수정 위자드** (모달 2쪽):

1. 어디에 — 기관→마을 트리. 내 계층부터 시작(군청 계정이면 자기 군청이 뿌리, 이장이면 마을만). 기관 노드를 고르면 「관할 전체」
2. 어느 단말에 — 고른 마을의 단말 체크, 기본 전체. 기관을 골랐으면 비활성
3. 언제 — 매일·매주·매월·매년 버튼 + 상세(요일 격자 / 1~31 격자 / 달력) + 오전·오후·시·분
4. 무엇을 — 파일함 목록 + MP3 올리기 + TTS 로 만들기(기존 TTS 모달 재사용, 만든 파일이 바로 선택됨)
5. 확인 — 「앞으로 **매주 월·수 오전 9:00**마다 **안내.mp3**을 **계곡마을 모든 단말**에 방송합니다」 → 스케줄 확정 / 이전으로

**스케줄 페이지**: 오늘 방송 일정 카드 / 관할 전체 스케줄 목록(언제·어디에·무엇을·다음 실행·최근 결과·끄기/수정/삭제, 볼 수만 있으면 「조회만」) / 7일 예정표. 오늘 일정과 예정표는 `occurrences` 를 KST 날짜로 묶어 그린다.

## 8a. 파일과의 관계

스케줄이 쓰는 파일은 파일함에서 지울 수 없다(`FILE_IN_USE`). 파일이 사라진 스케줄은 걸릴 때마다 조용히 실패하기 때문이다. 거절할 때 어느 스케줄인지 이름을 대 주고, 파일함 목록의 삭제 버튼도 미리 비활성으로 둔다(`FileOut.schedule_labels`).

방송 이력은 반대다. 0017 부터 `broadcast_events.file_id` 는 `ON DELETE SET NULL` 이고 파일명은 이력이 따로 들고 있어, 방송한 파일도 지울 수 있다.

## 9. 이번에 넣지 않는 것

- 매월 「말일」 — 목업에 없다. 필요하면 `month_days` 에 `-1` 같은 특수값으로 넣는다
- 시작·종료 기간(「10월까지만」) — 규칙을 끄거나 지우는 것으로 대신한다
- 실시간 방송 스케줄 — 마이크가 필요해 자동화가 성립하지 않는다
- 라이브 방송 중 스케줄 우선순위 — 겹치면 건너뛴다. 끊지 않는다
