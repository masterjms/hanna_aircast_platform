# 브로커 운영 확인 요청 — 2026-09-01

단말 쪽에서 드리는 질문 **넷**입니다. 전부 서버 결정 사항이라 단말에서는 확인할 방법이 없습니다.

**1번만 결정이고 나머지 셋은 확인입니다.** 1번은 지금 정하면 비용이 없고, 미루면 현장 작업이 됩니다. 나머지는 단말 동작에 영향이 없으니 늦어져도 됩니다.

질문마다 **최소 대안**을 적었습니다. 의견 없으시면 그대로 가도 되고, 다르게 하실 이유가 있으면 그쪽이 맞습니다.

---

## 1. 브로커 비밀번호의 **원본**이 어디에 있습니까?

`SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md` §2.1은 계정 등록 방식을 **서버 재량**으로 열어 뒀습니다(§5). **그 판단은 지금도 유효합니다.**

다만 같은 절이 근거로 든 성질 하나가 나중에 발을 묶습니다.

> **mosquitto는 password를 해시로 저장하므로 브로커가 뚫려도 평문이 나오지 않는다.** (§2.1)

맞는 말이고 장점입니다. 그런데 **해시는 다른 브로커로 옮길 수 없습니다.**

| 비밀번호 원본이 어디 있나 | 브로커를 바꿔야 할 때 |
|---|---|
| **서버 DB에도 있다** | DB에서 새 브로커로 다시 채우면 끝. 설정 작업 |
| **mosquitto password 파일에만 있다** | **전 단말 재발행** — 케이블 들고 현장을 도는 작업 |

단말은 비밀번호를 NVS에 갖고, 바꾸려면 시리얼이나 단말 설정 화면을 거쳐야 합니다. 설치된 단말이면 사람이 찾아가야 합니다.

**계정은 한 번 발행하면 안 바뀐다**는 전제로 설계했고(공장 초기화도 계정·서버 주소는 남깁니다), 그 전제가 여기서는 비용으로 돌아옵니다.

### 확인 부탁드리는 것

1. 지금 계정 등록을 어떤 방식으로 하십니까? (`mosquitto_passwd` + 리로드 / DB 연동 인증 / 기타)
2. 서버 DB가 **비밀번호를 갖고 있습니까?** 형태는? (평문 / 암호화 / 해시만)

### 최소 대안

**서버 DB가 원본을 쥐고 있게만 해 주십시오.** 저장 시 암호화 여부와 방식은 서버 판단입니다.

지금 무엇을 바꾸자는 게 아니라 **나중에 바꿀 수 있는 상태로 두자**는 것입니다.

§2.1이 「규모가 커지면 DB 연동 인증 플러그인을 검토한다」고 적어 둔 방향으로 가면, 브로커가 그 DB에 직접 인증을 물으므로 **동기화 단계 자체가 없어집니다.** 그건 나중 얘기고 지금 필요하진 않습니다.

## 2. `iotradio/all/cmd` 발행이 관리자 전용입니까?

### 왜 묻는가

이 토픽은 **마을 배정과 무관하게 전 단말이 구독**합니다. 조립 중이거나 창고에 있는 단말도 포함됩니다.

마을 토픽(`iotradio/village/<village_id>/cmd`)은 **배정 전이면 아예 구독하지 않아서** 안전합니다. `all/cmd`만 예외입니다.

즉 **「전체 방송」이 생산 라인 위의 보드까지 갑니다.**

§2.2에서 ACL을 `%u`로 바꾸는 건 **사칭 방지**라 이것과 다른 문제입니다. `%u`로 바꿔도 이장님 계정이 `all/cmd`에 발행할 수 있으면 그대로입니다.

### 확인 부탁드리는 것

1. `all/cmd` 발행이 관리자 계정으로만 됩니까?
2. 그 제한이 **브로커 ACL에** 있습니까, 화면에서 버튼을 숨기는 방식입니까?

### 최소 대안

**ACL에서 막아 주십시오.** 화면만으로는 부족합니다 — MQTT 클라이언트를 직접 쓰면 우회됩니다.

마을 사용자에게는 `iotradio/village/<본인 마을>/cmd` 발행만 허용하고, `all/cmd`는 관리자 전용으로.

## 3. mosquitto의 `LimitNOFILE`이 얼마입니까?

### 왜 묻는가

MQTT 연결 하나가 파일 디스크립터 하나입니다. **systemd 기본 소프트 제한이 1024**라, 손대지 않았으면 **약 1,000대에서 접속이 막힙니다.**

mosquitto 자체는 제한이 없어서(`max_connections` 기본 `-1`) 이게 실질 상한이 됩니다.

**증상이 고약합니다.** 로그에 `Too many open files`가 뜨고 그 뒤 접속이 거절되는데, 단말 쪽에서는 「안 붙는다」로만 보입니다 — **계정 문제와 구분되지 않습니다.**

### 확인 부탁드리는 것

```bash
cat /proc/$(pgrep mosquitto)/limits | grep "open files"
```

### 최소 대안

목표가 1,000대를 넘으면 미리 올려 두십시오.

```ini
# /etc/systemd/system/mosquitto.service.d/limits.conf
[Service]
LimitNOFILE=65536
```

### 참고

메시지 양으로는 안 막힙니다. STATUS 30초 + keepalive 20초면 **대당 초당 0.08건**이라 10,000대에서도 800 msg/s입니다.

막히는 건 위의 fd, 그리고 **브로커 재시작 때 전 단말이 동시에 TLS 핸드셰이크를 하는 순간**입니다(mosquitto는 싱글 스레드). 인증서 갱신으로 리로드할 때가 대표적입니다.

## 4. 등록과 운영이 **같은 서버**라는 전제가 맞습니까?

### 왜 묻는가

생산 라인 등록과 이장님의 실제 방송이 같은 서버에서 겹칩니다. 분리해야 하는지 검토했고 **한 대가 맞다**고 봤습니다.

`DEVICE_REGISTRATION_FLOW_SPEC_2026-08-29.md` §6.3의 **2단계 확인이 「STATUS가 서버에 도착했는가」**입니다. 별도 등록서버에서 확인하면 그건 등록서버에 붙는다는 증명이지 실서버에 붙는다는 증명이 아닙니다.

DB만 복사하는 방식은 당일 출고 단말의 타이밍 문제와, 비밀번호가 **두 곳에 존재**하는 문제(1번과 연결)가 있습니다.

중첩 걱정은 **① 마을 배정 ② 로그인 권한 ③ `all/cmd` ACL**로 푸는 것이 맞다고 봤습니다. ①은 단말에 이미 되어 있고, ③이 질문 2입니다.

### 확인 부탁드리는 것

서버 쪽 전제도 한 대입니까? 분리를 전제로 설계 중인 부분이 있으면 알려 주십시오.

### 최소 대안

**서버 한 대.** 가르는 것은 로그인 권한과 토픽입니다.
