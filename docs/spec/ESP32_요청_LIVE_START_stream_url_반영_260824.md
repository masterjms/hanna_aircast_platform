# ESP32 요청: `LIVE_START.stream_url` 반영

**작성**: 서버측 (2026-08-24)
**대상**: ESP32-P4+C6 펌웨어 담당
**관련 문서**: `SERVER_VILLAGE_STREAM_URL_POLICY_2026-08-21.md` §5, `SERVER_COMM_MQTT_ICECAST_HTTP_SPEC_2026-08-14.md` §6

---

## 1. 요청 한 줄 요약

`LIVE_START` payload에 서버가 넣어 보내는 `stream_url` 문자열을 읽어서, 그 주소로 Icecast에 접속해 주세요. 현재는 이 필드를 무시하고 펌웨어에 박힌 고정 주소(`http://192.168.0.5:8000/live`)로 접속합니다.

이건 새 정책이 아니라, `SERVER_VILLAGE_STREAM_URL_POLICY_2026-08-21.md` §5에 "다음 단계"로 이미 합의된 항목입니다. 서버측 구현이 끝나서 진행 가능 여부와 일정을 확인드립니다.

---

## 2. 지금 무엇이 막혀 있나

서버는 실시간 방송을 시작할 때마다 **세션 전용 Icecast mount**를 만들고 그 주소로 오디오를 흘립니다.

```text
/live/<job_id>          예) /live/141
```

(2026-08-24 확정: 마을 다중 선택 방송을 지원하기 위해 경로를 `job_id` 하나로 단순화했습니다.
마을이 여러 개인 방송은 경로에 마을을 담을 수 없기 때문입니다. 단말은 어차피 문자열을
그대로 쓰므로 §3.2 규칙에는 영향이 없습니다.)

단말은 `/live` 고정 주소로 접속합니다. 서로 다른 주소라서 **단말이 접속해도 그 mount에는 오디오가 없습니다.** `LIVE_READY`는 정상적으로 오지만 스피커에서는 소리가 나지 않습니다.

실측 확인한 현재 상태(2026-08-24, 서버 ↔ 실물 단말 1대):

| 항목 | 결과 |
|---|---|
| MQTT 접속 · STATUS · LWT | 정상 |
| CONFIG 두 토픽 · `village_id` 적용 | 정상 |
| 마을 토픽 명령 수신 | 정상 |
| `FILE_START` → HTTP 다운로드 → sha256 검증 → `FILE_END` | 정상 |
| `LIVE_START` → `LIVE_READY` | 정상 |
| **실시간 오디오 수신** | **불가 (이 문서의 사유)** |

`FILE_START`는 이미 서버가 내려주는 `https_url`을 단말이 읽어서 쓰고 있고, 실물에서 동작을 확인했습니다. **`LIVE_START.stream_url`도 같은 방식으로 처리해 주시면 됩니다.**

---

## 3. 요청하는 단말 동작

### 3.1 기본 규칙

1. `LIVE_START` payload에 `stream_url`이 **있으면** 그 문자열로 접속한다.
2. `stream_url`이 **없거나 빈 문자열이면** 기존 고정 주소로 접속한다(fallback).

2번 fallback을 유지해 주시면 펌웨어와 서버를 따로 배포해도 안전합니다. 서버가 구버전이어도 단말이 동작하고, 그 반대도 마찬가지입니다.

### 3.2 `stream_url`은 파싱하지 않고 그대로 씁니다

서버가 **완성된 URL 문자열**을 내려줍니다. 단말은 scheme/host/port/path를 조립하거나 재구성하지 않고 받은 문자열을 그대로 HTTP GET 대상으로 씁니다.

`village_id`나 `job_id`로 경로를 직접 만들지 말아 주세요. 경로 구조가 나중에 바뀔 수 있고(§3.4 참고), 그때 펌웨어를 다시 굽지 않으려는 것이 이 설계의 목적입니다.

### 3.3 payload 예

```json
{
  "type": "LIVE_START",
  "job_id": 141,
  "stream_url": "http://192.168.0.41:8000/live/141",
  "codec": "opus",
  "frame_ms": 40,
  "sample_rate": 16000,
  "record_flash": 0,
  "ready_timeout_sec": 30
}
```

`stream_url` 외의 필드와 `LIVE_READY` 응답 형식은 기존 그대로입니다. 변경 없습니다.

### 3.4 서버가 보낼 수 있는 URL 형태

지금(LAN 테스트):

```text
http://192.168.0.41:8000/live/141
```

TLS 전환 후(`SERVER_TLS_HOST_HANDOFF_2026-08-23.md` 확정 사항):

```text
https://<도메인>/live/141
```

**포트가 없을 수도 있습니다.** nginx가 443으로 받아 내부 프록시하는 구성이라 클라이언트가 보는 URL에는 포트가 안 붙습니다. `https` + 포트 생략 형태를 처리할 수 있어야 합니다.

경로 구조는 서버 재량이며 바뀔 수 있습니다 — 반드시 **문자열 그대로 사용**을 전제로 잡아주세요.

### 3.5 버퍼 길이

`stream_url` 최대 길이를 넉넉히 잡아주세요. 도메인 적용 후 예시가 이 정도입니다:

```text
https://aircast.example.co.kr/live/1234567
```

**256바이트**면 충분하고, 여유를 두시려면 512바이트를 권합니다. MQTT CMD payload 전체 상한(1024B)은 서버가 발행 전에 검사해서 넘지 않게 보장합니다.

---

## 4. 왜 mount를 나누는가

`/live` 하나로 계속 쓰면 **마을별 동시 방송이 불가능**합니다.

Icecast는 mount 하나에 소스 하나만 허용합니다. 실측으로 확인했습니다 — 같은 mount에 두 번째 소스를 붙이면 `HTTP 403 Forbidden`으로 거절되고 첫 소스만 유지됩니다.

```text
마을 A 방송 시작 → /live 소스 연결 성공
마을 B 방송 시작 → /live 소스 연결 403 → 방송 시작 실패
```

마을이 여럿인 운영 환경에서 "A마을 방송 중에는 B마을이 방송을 못 한다"는 제약은 받아들이기 어렵습니다. mount를 세션마다 나누면 이 제약이 없어집니다.

부수적으로, 단말이 `LIVE_STOP`을 놓쳐 이전 mount에 계속 붙어 있어도 세션이 다르면 **다음 방송이 그 단말에 들리지 않습니다.** 고정 mount에서는 남의 마을 방송이 들릴 수 있습니다.

---

## 5. 확인 부탁드릴 것

1. `stream_url` 반영이 가능한지, 가능하다면 대략 언제쯤인지
2. §3.4의 URL 형태(https, 포트 생략, 가변 경로)를 처리하는 데 문제가 없는지
3. `stream_url` 접속이 실패했을 때 단말 동작 — 현재 `LIVE_READY status`/`reason` 중 어느 값으로 보고되는지, 아니면 별도 처리가 필요한지

3번이 특히 궁금합니다. 서버는 `LIVE_START` 발행 **전에** mount를 열어두므로 정상적으로는 접속 실패가 나지 않아야 하지만, 네트워크 문제로 실패했을 때 서버가 그 사실을 알 수 있으면 좋겠습니다.

---

## 6. 반영 전까지 서버측 임시 대응

펌웨어 반영 일정에 따라 서버가 임시로 `/live` 고정 mount를 쓰도록 설정 스위치를 둘 수 있습니다(동시 방송 포기). 다만 **§4의 이유로 임시 방편이며, 반영 후에는 스위치를 끄고 세션별 mount로 돌아갑니다.**

일정이 짧으면 임시 대응 없이 기다리는 편이 깔끔하다고 보고 있어, 1번 답변에 따라 정하겠습니다.

---

## 7. 참고: 서버측 현재 구현

이미 구현되어 목 단말로 검증 완료된 상태입니다.

- `LIVE_START` 발행 **전에** Icecast source(HTTP PUT)를 연결해 mount를 먼저 만듭니다. 단말이 접속했을 때 mount가 없어 실패하는 순서 역전이 생기지 않습니다.
- mount 경로 생성: `/live/<job_id>` (job_id 는 전역 유일).
- 방송 종료 시 source를 닫아 mount를 정리합니다. 유령 mount가 남지 않습니다.
- `SERVER_VILLAGE_STREAM_URL_POLICY_2026-08-21.md` §7에 "서버측 동적 mount 생성 로직은 별도 설계 필요"로 남아 있던 항목인데, PC 데모(`Icecast_시작.bat`, 고정 mount + 상시 소스)와 달리 신규 서버는 세션마다 mount를 만들어 붙이는 구조로 이미 만들어져 있습니다.
