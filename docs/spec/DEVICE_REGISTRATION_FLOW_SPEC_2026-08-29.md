## 1. 이 문서가 정하는 것

**단말 하나가 공장에서 만들어져 마을 가정집에서 방송을 받기까지**의 절차다.

세부는 다른 문서에 있고 여기서 반복하지 않는다.

| 알고 싶은 것 | 문서 |
|---|---|
| 시리얼 명령 형식 | `PRODUCTION_PROVISIONING_SPEC.md` §4 |
| 마을·단말 등록 항목 | `SERVER_DEVICE_REGISTRY_2026-08-27.md` |
| 계정 발행 정책 | `SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md` |

### 뼈대 — 두 가지 일이 섞여 있다

```text
케이블로 단말에 써넣는 것        서버 DB에 기록하는 것
─────────────────────────      ─────────────────────
Wi-Fi, 서버 주소, MQTT 계정      마을, 주소, 이름, 전화번호
RF 존·채널, 모델 설정            village_id 배정

→ 라인·현장에서만 가능           → 사무실에서 언제든
→ 물리 접근 필요                 → 단말이 어디 있든 상관없음
```

**이 둘을 섞지 않는 것이 이 문서의 원칙이다.** 라인 작업자는 마을·주소를 모르고, 사무실은 케이블을 꽂을 수 없다.

### 마을은 케이블이 필요 없다

`village_id`는 **MQTT retained CONFIG로 내려간다.** 사무실에서 드롭다운을 바꾸면 단말이 어디 있든 받는다.

주소·이름·전화번호는 **아예 단말에 가지 않는다.** 서버 DB에만 있다.

**그래서 「마을 배정」과 「단말 등록」이 다른 화면, 다른 시점이다.**

## 2. 전체 흐름 — 네 그룹

```text
┌─ A. 사전 등록 ──────────── 사무실 / 관리자 ─── 계약될 때
│    A1. 마을 등록
│
├─ B. 생산 ───────────────── 라인 / 작업자 ───── 제조할 때
│    B0. HW 검증           (RF 시험 단계. 서버 무관)
│    B1. RF·모델 설정      (KEY3+KEY4, 기존 방식)
│    B2. 네트워크 등록      (KEY1+KEY4)        ← 케이블. 한 대씩
│    ─────────────────────────────────────  케이블은 여기까지
│    B3. 접속 확인 (+ 방송 테스트, 옵션)        ← 배치로
│    B4. 마을 배정          ← 목적지를 알면 여기서
│    B5. 출하
│
├─ C. 설치 ───────────────── 현장 / 설치 기사 ── 납품할 때
│    C1. 현장 Wi-Fi 입력
│    C2. 방송 확인          ← 현장에서는 이것만
│
└─ D. 운영 ───────────────── 사무실 / 관리자 ─── 이후 계속
     D1. 정보 수정
     D2. 단말 교체 (A/S)
     D3. 사용 안 함 / 삭제
```

**A는 「마을 배정」보다 먼저다.** 마을이 없으면 배정할 곳이 없다.

**생산 자체는 마을 없이도 된다.** 미배정으로 만들어 두고 나중에 배정한다 — 방송 테스트(B3)도 미배정에서 된다(§C3 아래 주석).

**마을 배정 시점은 둘 중 하나다.**

| 목적지를 | 배정 시점 | 현장에서 |
|---|---|---|
| **생산 때 안다** (보통) | **B4** — 라인에서 미리 | Wi-Fi 넣고 **방송만 확인** |
| 생산 때 모른다 | 사무실에서 나중에 | 같음 |

**현장은 어느 쪽이든 하는 일이 같다** — Wi-Fi를 넣고 소리가 나는지 본다. 마을 배정은 케이블이 필요 없으므로 현장 일이 아니다.

## 3. A. 사전 등록 — 사무실

### A1. 마을 등록

계약이 되면 관리자가 마을을 만든다. **마을 배정보다 먼저다** — 생산 자체는 마을 없이도 된다(§2).

```text
마을명        월선리 마을회관
대표 주소     [주소 검색]  →  도로명·지번·법정동코드 자동
연번          01           →  village_id 완성
담당자 이름
담당자 전화
기타                       ← 마을 메모. 단말의 「특이사항」과 다른 필드다
```

`village_id`는 **마을의 속성**이지 단말의 속성이 아니다. 형식은 `SERVER_DEVICE_REGISTRY_2026-08-27.md` §2.

**원칙은 사무실에서 미리 만드는 것이다.** 작업자가 대표 주소·담당자를 모르고, 빈 값으로 만들어 두면 나중에 아무도 채우지 않는다.

**미리 안 만들어도 생산은 돈다.** 미배정으로 두고 접속 확인과 방송 테스트만 하고 넘긴다 — 그 둘은 마을이 없어도 된다(§B3). 대신 **미배정이면 마을 방송을 못 받으므로** 관리자가 언젠가 채우게 된다.

**다만 라인에서도 만들 수 있게 열어 둔다.** 마을이 아직 등록되지 않았는데 단말은 나가야 하는 경우가 실제로 생긴다. 그때 등록을 막으면 라인이 선다.

라인에서 만들 때는 **마을명과 연번만** 받고 나머지는 비워 둔다. 대신 **「정보 미완성」으로 표시**해서 사무실이 나중에 채우게 한다 — 표시가 없으면 아무도 안 채운다.

## 4. B. 생산 — 라인

### B0. HW 검증 — 등록 이전 단계

**등록에 들어오는 단말은 HW 검증을 통과한 것이다.** 라인 내부 공정이고 **서버는 관여하지 않는다.**

서버가 알아야 할 것은 **결과 하나**뿐이다.

> **정상 HW만 등록에 들어온다.**

간헐적으로 불량이 섞여 들어올 수는 있다. 그때는 수리로 뺀다 — 등록까지 됐다면 서버에서 「사용 안 함」으로 내린다(§D3).

### B1. RF·모델 설정 (기존 방식)

**별도 모드에서 한다.** 등록과 무관하고 **서버는 관여하지 않는다.**

**등록 모드에서는 이 항목을 보내지 않는다.** 같은 일을 두 곳에서 하면 어느 쪽이 맞는지 알 수 없어진다.

### B2. 네트워크 등록 (KEY1+KEY4)

**서버 등록 페이지가 시리얼을 직접 연다.** Web Serial API를 쓰므로 별도 프로그램 설치가 없다.

```text
라인 PC = Chrome + 등록 페이지 + 바코드 스캐너 + USB-시리얼 케이블
```

절차:

```text
1. [포트 연결]          세션당 한 번
2. QR 스캔             MAC·모델·버전이 한 번에 들어옴
3. 서버 등록 요청       → 계정 발행, MAC 기록
4. [전송]              아래 5줄
5. @GET → 비교         §B2.2
6. @OFF                재부팅
```

#### B2.1 보내는 것 — 다섯 줄뿐

```text
> @SSID=<라인 AP>
> @PASSWORD=<라인 AP 비밀번호>
> @SERVER=hanna-aircast.co.kr
> @MQTTID=58e6c5f2cc74
> @MQTTPW=<서버 발행값>
> @END
```

**`@MQTTID`는 그 단말의 MAC이다** — 콜론 없는 소문자, `client_id`와 같은 값. 스캔한 MAC을 그대로 넣으므로 사람이 칠 것이 없다.

`@MQTTPW`는 서버가 그 MAC에 발행한 값이다(`SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md`).

**전부 「네트워크로 서버에 붙는 데 필요한 것」이다.** 하나라도 틀리면 B3에서 STATUS가 오지 않아 즉시 드러난다.

**한 번에 보낸다.** 단말은 **값이 하나라도 잘못되면 전부 거부**하므로, 나눠 보내면 어디까지 들어갔는지 알 수 없는 상태가 생긴다.

라인 Wi-Fi는 **등록 화면에 한 번 입력하고 세션 동안 유지**한다. 단말마다 치지 않는다.

#### B2.2 `@GET` 비교

| 항목 | 비교 | 잡는 것 |
|---|---|---|
| **`@MAC`** | 스캔한 MAC과 같은가 | **케이블을 옆 단말에 꽂음** |
| `@SSID` `@SERVER` `@MQTTID` | 값 그대로 | 전송 오류 |
| `@PASSWORD` `@MQTTPW` | **보낸 값이 비었으면 `NONE`, 값이 있으면 `SET`** | 들어갔는지 |

**`@MAC` 비교를 빠뜨리면 안 된다.** 여러 대를 연달아 작업할 때 케이블을 옆 단말에 꽂는 실수가 실제로 나고, 이 비교가 그것을 잡는 유일한 지점이다.

### B3. 접속 확인 (+ 방송 테스트) — 배치로 묶는다

**이것이 진짜 검증이다.**

#### 케이블은 B2까지다

```text
B2. 네트워크 등록    스캔 → 전송 → @GET 비교 → @OFF     ← 케이블. 한 대씩
────────────────────────────────────────────────────    케이블은 여기까지
B3. 접속 확인 + 방송 테스트                              ← 배치
B4. 마을 배정                                            ← 배치
```

**등록이 끝나면 단말은 서버에 붙어 있다.** 그 뒤로 케이블이 할 일이 없다.

**한 대씩 기다리지 않는다.** B2 자리는 몇 초로 끝나고, 확인은 쌓아 둔 배치를 한 번에 본다.

| | 한 대씩 | **배치** |
|---|---|---|
| B2 자리 | **30초 대기** | 몇 초 |
| 이상 검출 | 비교 대상이 없다 | **여러 대가 같이 울려 조용한 것이 띈다** |
| 실패품 | 그 자리에서 재작업 | **더미에서 찾아 다시 꽂아야 한다** |

**마지막 줄이 유일한 손해인데 작다.** 전송 오류는 `@GET`이 이미 자리에서 잡고, 개체 Wi-Fi 불량은 B0가 걸렀다. **남는 실패는 대부분 계통 문제**(서버 계정 미등록, 라인 AP)이고 **그건 배치에서 더 잘 보인다** — 여러 대가 한꺼번에 실패하면 원인이 바로 좁혀진다.

```text
@OFF → 부팅 → 라인 Wi-Fi 접속 → SNTP → MQTT 접속 → STATUS 발행
                                                    ↓
                                    서버가 그 MAC의 STATUS 수신
                                                    ↓
                                              「접속 확인」
```

**STATUS가 왔다는 것은 Wi-Fi·서버주소·MQTT 계정·ACL이 전부 맞다는 뜻이다.** 브로커가 이미 비밀번호를 검증했으므로 서버가 따로 물어볼 필요가 없다.

| 화면 표시 | 뜻 |
|---|---|
| 전송 완료 | `@GET` 비교 통과, 재부팅함 |
| **접속 확인** | **STATUS 도착. 등록 완료** |
| 시간 초과 | 기다려도 안 옴 |

**30초 안팎 걸린다.** 배치로 하므로 이 대기가 B2 자리를 잡지 않는다 — **다음 단말을 등록하는 동안 앞의 것들이 하나씩 ✓로 바뀐다.**

#### 방송 테스트 — 고정 음원 파일 하나

**서버에 테스트 음원을 하나 두고 그것만 쓴다.** 5초 미만 mp3면 충분하다. **확인하는 것은 「소리가 나오는가」뿐이라** 내용은 상관없고, 짧을수록 배치가 빨리 돈다.

```text
[테스트 방송] → 목록의 단말에 각각 FILE 방송 발행 → 줄을 따라 걸으며 듣는다
```

**단말별 topic에 N번 발행한다**(`iotradio/device/<mac>/cmd`). 100번이라도 몇 밀리초이고, **마을 배정이 없어도 닿는다** — 이 단계가 B4보다 먼저인 이유다.

> **`iotradio/all/cmd`를 쓰면 안 된다.**
>
> 라인 20대를 시험하려다 **현장에 나가 있는 전 단말이 울린다.** 배치가 아무리 커도 단말별 발행을 반복한다.

**배치는 10~20대가 적당하다.** 동시에 울려야 조용한 것이 귀에 띄는데, 너무 많으면 어느 것인지 가리기 어렵다.

#### 저장하지 않고 재생한다

```json
{ "type": "FILE_START", ..., "store_flash": 0, "autoplay": 1 }
```

**`store_flash`를 `0`으로 보낸다.** 단말은 받은 것을 메모리에서 바로 재생하고 **flash에 쓰지 않는다.** 테스트 음원이 출하되는 단말에 남지 않고, 저장 공간을 건드리지도 않는다.

`autoplay`는 `1`이어야 소리가 난다.

#### 테스트를 할지는 옵션이다

**서버는 기능만 만들고, 언제 쓸지는 라인이 정한다.**

```text
등록하면서 한 대씩  /  배치를 쌓아 한 번에  /  아예 하지 않음
```

생산 사정에 따라 달라지므로 **서버가 절차를 강제하지 않는다.** 필요한 것은 **[테스트 방송] 버튼과 켜기/끄기** 둘뿐이다.

#### 소리 판정은 서버가 기록하지 않는다

**서버는 명령을 쏜 것까지만 안다.** 소리가 났는지는 라인이 귀로 확인하고, **안 나온 단말은 그 자리에서 뺀다.**

**화면에 판정 입력을 두지 않는다.** 라인 작업 지침으로 관리한다.

#### 실패하면 — 두 가지를 나눠 본다

| 무엇이 실패했나 | 먼저 할 것 |
|---|---|
| **STATUS가 안 옴** | **재전송.** 값이 잘못 들어갔을 수 있다 |
| **소리가 안 남** (STATUS는 옴, 테스트를 켰을 때) | **재전송은 소용없다.** 아래로 가른다 |

**소리가 안 날 때는 다른 단말과 비교한다.**

| | 어디 문제인가 |
|---|---|
| 여러 대가 같이 안 남 | **서버·음원 파일·라인 인터넷** |
| **이 한 대만 안 남** | **개체 불량.** 수리로 뺀다 |

STATUS가 왔다는 것은 Wi-Fi 접속과 계정이 맞다는 뜻이므로 **전송 문제는 아니다.** 다시 보내도 달라지지 않는다.

STATUS가 계속 안 오면 개체보다 **라인 전체 문제**일 가능성이 높다 — 라인 Wi-Fi 비밀번호, 서버 상태, 인터넷 연결을 본다.

**재작업은 그 단말을 다시 스캔하면 된다.** §7 재등록 흐름으로 들어가므로 별도 버튼이 필요 없다.

### B4. 마을 배정 — 목적지를 알면 여기서

**대개 어느 마을로 갈지 알고 만든다.** 그러면 라인에서 배정까지 끝낸다.

등록 화면에서 **마을을 고르기만 하면 된다.** 서버가 retained CONFIG를 발행하고, 단말은 이미 붙어 있으므로 **그 자리에서 받는다.**

```text
마을 선택 → 서버가 device/<mac>/config 발행 → 다음 STATUS에 village_id가 실려 온다
```

**STATUS의 `village_id`가 바뀌는 것으로 확인된다.** 별도 확인 절차가 없다.

목적지를 모르면 비워 둔다. **사무실에서 나중에 배정해도 단말은 어디서든 받는다.**

### B5. 출하

라인 Wi-Fi가 단말에 남는다. **설치할 때 `@SSID`/`@PASSWORD`를 넣으면 덮어써지므로 그냥 내보내도 된다.**

고객 집에는 그 AP가 없으니 **연결 실패로 바로 드러난다.** 조용히 잘못되는 종류가 아니다.

**빼고 싶으면 지울 수 있다.** 공장 비밀번호가 단말에 남는 것이 걸리면 둘 중 하나를 쓴다.

| | |
|---|---|
| 시리얼 | `@WIFICLR` |
| 단말 화면 | 설정의 `WIFI(FACT)` 행에서 KEY4 |

**서버가 할 일은 없다.** 라인이 필요할 때 쓰면 되고, 안 써도 등록·방송에 지장이 없다.

## 5. C. 설치 — 현장

### C1. 현장 Wi-Fi 입력

케이블을 꽂고 **Wi-Fi만** 보낸다.

```text
> @SSID=<그 집 공유기>
> @PASSWORD=<비밀번호>
> @END
```

계정·서버주소는 **생산에서 넣은 것이 그대로 살아 있다.** 다시 넣지 않는다.

**MQTT 계정은 네트워크와 무관하다.** 라인 AP로 붙든 고객집 공유기로 붙든 같은 계정으로 브로커에 접속한다.

### C2. 방송 확인 — 현장에서는 이것만

설치 기사에게 요청할 것은 **소리가 나오는지 확인**하는 것뿐이다.

```text
Wi-Fi 입력 → 재부팅 → 서버에 [테스트 방송] 요청 → 소리 확인
```

**마을 배정은 현장 일이 아니다.** 라인(B4)에서 이미 했거나, 사무실에서 하면 된다. 케이블이 필요 없으므로 현장에서 할 이유가 없다.

가정집에서 하는 작업이라 **단순할수록 좋다.** Wi-Fi를 넣고 소리를 듣는 것 둘뿐이다.

### C3. 최악의 경우 — 개인 정보를 모를 때

**마을만 알면 방송은 나간다.**

| 항목 | 없어도 되나 |
|---|---|
| 상세 주소 | **없어도 됨** — 나중에 사무실에서 채운다 |
| 이름 | **없어도 됨** — 비면 MAC이 표시된다 |
| 전화번호·특이사항 | 없어도 됨 |
| **마을 배정** | **마을 단위 방송에는 필수** |

한 집에 여러 대면 상세 주소를 같게 두고 **이름으로 구분**한다.

**단말 주소가 마을 대표 주소와 달라도 된다.** 마을은 위치가 아니라 「같은 방송을 듣는 묶음」이라, 마을 대표 주소가 서울인데 단말이 부산에 있을 수 있다. 그럴 때는 **「특이사항」에 사유를 적는다**(`SERVER_DEVICE_REGISTRY_2026-08-27.md` §3.5).

> **미배정이라고 방송이 아예 안 되는 것은 아니다.**
>
> 단말은 `iotradio/device/<mac>/cmd`를 **마을과 무관하게 항상 구독**한다. 그래서 **서버가 그 단말 하나에 쏘는 방송은 미배정에서도 된다** — 생산 B3의 방송 테스트가 이것이다.
>
> 마을 배정이 필요한 것은 `iotradio/village/<village_id>/cmd`로 나가는 **단체 방송**이다.

## 6. D. 운영 — 사무실

### D1. 정보 수정

단말 상세 화면에서 마을·주소·이름·전화·특이사항을 고친다. **전부 서버 DB이므로 케이블이 필요 없다.**

### D2. 단말 교체 (A/S)

고장난 단말을 새것으로 바꿀 때, **마을·주소·이름·전화를 새 MAC으로 옮긴다.**

```text
[단말 교체]
  새 MAC 스캔  →  정보를 새 MAC으로 이전
                  헌 MAC은 「사용 안 함」으로
```

**없으면 A/S 때마다 네 항목을 손으로 다시 입력하게 된다.**

### D3. 사용 안 함 / 삭제 — 둘 다 둔다

| | 「사용 안 함」 | 「삭제」 |
|---|---|---|
| 용도 | 폐기·회수 단말 | **잘못 등록한 것** |
| MAC 기록 | 남음 | 없어짐 |
| 계정 | 유지 | 브로커에서도 제거 |
| 이력 | 남음 | 없어짐 |
| 되돌리기 | 가능 | **불가** |

**삭제를 막을 조건 셋:**

- **온라인이면 금지** — 살아 있는 단말을 지우는 것은 거의 실수다
- **마을에 배정돼 있으면 금지** — 먼저 배정을 해제한다
- **MAC을 직접 입력해 확인** — 버튼 한 번으로 지워지면 안 된다

「사용 안 함」은 조건 없이 된다. 되돌릴 수 있기 때문이다.

**「사용 안 함」 단말은 여전히 브로커에 붙는다.** 계정을 남기기 때문이다. **방송 대상 목록에서만 빼면 된다** — 접속을 막으려고 계정을 지우면 되돌릴 수 없어진다.

**삭제는 DB와 브로커를 같이 지워야 한다.** 한쪽만 지우면 「붙는데 DB에 없는 단말」이 되고, 그건 서버가 따로 찾아 고쳐야 하는 상태다(`SERVER_DEVICE_REGISTRY_2026-08-27.md` §3.6).

## 7. 이미 등록된 단말을 다시 스캔하면

**덮어쓰기를 기본으로 두지 않는다.** 라인에서 무심코 스캔한 한 번이 현장 정보를 지우면 안 된다.

```text
⚠ 이미 등록된 단말입니다

MAC          58e6c5f2cc74
마을         월선리 (468403302101)
이름         홍길동집
마지막 접속  3일 전

[다시 전송]   [취소]
```

**수정은 열어 둔다. 다만 기본값이 「유지」다.**

기존 값을 **채워서 보여주고 사람이 고친 항목만 바뀐다.** 그래서 무심코 스캔한 한 번으로는 아무것도 지워지지 않는다.

| 항목 | 재등록 시 |
|---|---|
| 마을·주소·이름·전화 | 기존 값이 채워진다. **고칠 수 있다** |
| MQTT 계정 | **재사용** — 재작업이 흔한 경우다 |
| Wi-Fi·서버주소 | 다시 넣음 |

**바뀌는 항목을 저장 전에 보여준다.** 무엇이 달라지는지 모르고 누르는 일이 없어야 한다.

### 7.1 어디서 고칠 것인가 — 재등록이 유일한 경로가 아니다

**정식 경로는 사무실(단말 상세)이다.** 마을·주소·이름·전화는 **전부 서버 DB**이고 단말에 들어가지 않는다. 마을만 retained CONFIG로 나가는데, **단말이 오프라인이어도 다음 접속에 받는다.**

| 상황 | 어디서 |
|---|---|
| 라인에서 즉시 발견 | **재등록** — 케이블이 이미 꽂혀 있다 |
| **출고 뒤 배정이 바뀜** | **사무실** — 케이블이 없다. 이 경로뿐이다 |
| 출고 뒤 주소·이름 수정 | **사무실** |
| A/S 단말 교체 | **[단말 교체]**(§D2) — 정보 수정이 아니라 **새 MAC으로 이전**이다 |

**출고 뒤에는 재등록을 할 수 없다.** 박스를 뜯어 케이블을 꽂아야 한다. 그래서 사무실 경로가 없으면 안 된다.

**재등록의 수정은 편의다.** 라인에서 잘못 넣은 것을 그 자리에서 고치려고 두는 것이고, 없어도 사무실에서 다 된다.

**「마지막 접속 3분 전 / 온라인」이 떠 있으면 손을 멈춘다.** 그 단말은 현장에서 돌고 있다는 뜻인데 라인 작업대에 있을 수 없다 — **MAC을 잘못 스캔했거나 MAC이 중복된 단말**이다.

### 7.2 계정은 한 번 발행하면 그대로 간다

**`@MQTTID`는 MAC이라 애초에 안 바뀌고, `@MQTTPW`도 바꾸지 않는다.** 그 단말이 폐기될 때까지 같은 값을 쓴다.

**현장에서 바뀌는 것은 서버 DB 항목뿐이다.**

| 바뀌는 것 | 어떻게 |
|---|---|
| 마을·주소·이름·전화·특이사항 | **사무실에서 고친다**(§D1). 케이블이 필요 없다 |
| 단말 자체를 바꿔야 함 | **[단말 교체]**(§D2) — 새 MAC에 새 계정, 정보만 옮긴다 |
| **계정** | **안 바꾼다** |

#### 단말을 잃어버렸으면 — 재발행이 아니라 삭제다

도난·분실·회수 못 한 단말은 **그 MAC의 계정을 브로커에서 지운다**(§D3 「삭제」). 그러면 그 단말은 못 붙는다.

**비밀번호를 바꿔서 막는 것이 아니다.** 바꾼 값을 그 단말에 넣을 방법이 없으므로(케이블이 필요하다) 애초에 성립하지 않는다.

#### [계정 재발행]은 라인 기능이다

**케이블이 꽂힌 상태에서만 쓴다.** 라인에서 재작업할 때 계정을 새로 받아야 하는 경우다 — 발행받은 값을 **그 자리에서 시리얼로 넣는다.**

재등록의 기본은 **재사용**이고(§7 표), 재발행은 고를 수 있는 예외다.

> **현장에 나가 있는 단말은 대상이 아니다.** 그쪽 계정을 바꿔야 하는 상황이 생기면 **별도 사양이 필요하다** — 지금은 그런 상황을 두지 않는다.

## 8. 화면 구성

```text
마을 관리          목록 / [마을 추가] / 마을 상세(수정·삭제)
                   삭제는 속한 단말이 있으면 금지

단말 관리          목록 + 필터(온라인·오프라인·미배정) + 검색
                   [단말 등록]  ← 등록 모드로
 └ 단말 상세       마을 변경 / 주소·이름·전화·특이사항
                   [단말 교체] [사용 안 함] [삭제]

등록 모드          한 화면에 세 영역. 배치 = 세션이다
                   재스캔이면 기존 정보를 채워 보여준다(§7)
                   재작업이면 [계정 재발행]도 여기서(§7.2)
```

#### 등록 모드 — 화면을 나누지 않는다

```text
┌─ 등록 모드 ───────────────────────────────────────┐
│ [포트 연결]   라인 Wi-Fi: village_ap               │  세션 설정
│ 마을: 월선리 ▾                                     │  (선택)
├───────────────────────────────────────────────────┤
│ 스캔 대기…                                         │  B2 — 한 대씩
│ 방금: 58e6c5f2cc74   전송 완료                     │
├───────────────────────────────────────────────────┤
│ 이번 배치 17대   ✓접속 15  ⏳대기 2  ✗실패 0      │  B3 — 배치
│                                                   │
│  58e6c5f2cc74   ✓ 접속   [🔊]   마을: 월선리 ▾    │
│  58e6c5f2cc90   ✓ 접속   [🔊]   마을: 월선리 ▾    │
│  58e6c5f2cca1   ⏳ 대기                            │
│  …                                                │
│                                                   │
│ [테스트 방송]                       [배치 완료]    │
└───────────────────────────────────────────────────┘
```

**배치 = 세션이다.** `[포트 연결]`부터 `[배치 완료]`까지 등록한 것이 그 배치다. **「배치를 만든다」는 절차가 따로 없다.**

**B2를 하는 동안 B3 목록이 저절로 채워진다.** 앞서 등록한 단말의 STATUS가 도착하면 그 행이 ⏳ → ✓ 로 바뀐다. 작업자는 스캔하면서 곁눈으로 본다.

**화면을 오가지 않는다.** 손이 바쁜 자리에서 화면 전환은 실수의 원인이다.

| 버튼 | 언제 |
|---|---|
| **[테스트 방송]** | 목록 전체에 발행한다. **옵션**이라 안 눌러도 된다 |
| 행마다 **[🔊]** | 안 나온 한 대만 다시 확인할 때 |
| **[배치 완료]** | 목록을 비우고 다음 배치로 |

#### 마을은 행마다 바꾼다

**세션 설정의 마을은 다음에 스캔하는 단말에 붙는 기본값이다.** 이미 목록에 오른 행은 그 값을 따라가지 않는다.

**바꿔야 하면 그 행에서 직접 고른다.** 목적지가 다른 단말이 한 배치에 섞여도 되고, 드롭다운을 중간에 바꿔도 앞의 것들이 흔들리지 않는다.

**이미 등록된 행의 마을 변경은 §7.1과 같은 동작이다** — 서버가 retained CONFIG를 다시 발행하고, 다음 STATUS의 `village_id`로 확인된다.

---

**마을 관리는 별도 메뉴다.** 단말과 수명주기가 다르다 — 마을은 수십~수백 개에 계약될 때 한 번, 단말은 수천 개에 만들 때마다다.

**[단말 등록]은 단말 관리 안의 버튼이다.** 생산 등록은 단말 목록에 행을 하나 더하는 일이다.

## 9. 1차 범위

### 넣는 것

- 마을 관리 화면 (라인 예외 생성 포함, §A1)
- 단말 관리 + 단말 상세
- 등록 모드 (Web Serial, 네트워크 5개 항목)
- `@GET` 비교, STATUS 도착 확인
- **라인에서 마을 배정** (§B4) — 목적지를 알면 여기서 끝낸다
- **배치 목록 + [테스트 방송]**(§8) — 접속 상태를 한 화면에서. 마을은 행마다 바꾼다
- **고정 테스트 음원** 1개 (5초 미만 mp3, `store_flash: 0`)
- **재등록 시 정보 수정**(§7) — 기존 값을 채워 보여주고 고친 것만 반영
- 사용 안 함 / 삭제 / 단말 교체

### 빼는 것

| | 왜 |
|---|---|
| **RF·모델 항목** | KEY3+KEY4 기존 경로가 이미 한다 |
| **비밀번호 체크섬** | 쓰지 않는다. STATUS 도착이 이미 증명한다 |
| **시리얼 로그 분석** | 서버가 ESP32 로그를 파싱하지 않는다 |
| 일괄 배정, 권한 분리, 목록 내보내기 | 있으면 좋으나 급하지 않다 |

**셋 다 서버가 만들 것이 없다.**

### 단말 쪽 작업

**없다.** 등록에 쓰는 것이 전부 동작한다.

```text
@GET  @OFF  @SSID  @PASSWORD  @SERVER  @MQTTID  @MQTTPW
```

라인이 쓰는 `@WIFICLR`과 설정 화면 `WIFI(FACT)` 행도 있다(`PRODUCTION_PROVISIONING_SPEC.md` §4.5.1, §4.9). **서버가 부를 일은 없다.**

## 10. 전제 조건

**아래가 갖춰져야 이 흐름이 성립한다.**

### 생산 라인에 인터넷이 있어야 한다

**필수다.** 라인에서 하는 두 가지가 인터넷 없이는 안 된다.

| | 왜 |
|---|---|
| **접속 확인** (B3) | STATUS가 서버에 도착해야 등록이 완료된다 |
| **방송 테스트** (B3, 옵션) | 서버가 테스트 음원을 내리고 단말이 재생한다 |

**둘 다 못 하면 단말이 정상인지 모르는 채로 출하하게 된다.** 현장에 가서야 알게 되고, 그때는 회수 비용이 든다.

라인 Wi-Fi AP는 **인터넷이 나가는 것**이어야 한다. 내부망만 되는 AP로는 안 된다.

### HW 검증을 통과한 단말만 들어온다

HW 검증은 **등록 이전 단계에서 끝난다**(§B0). 서버는 관여하지 않는다.

**서버 접속은 등록 단계에서 처음 시험된다.** 그래서 B3의 접속 확인이 등록의 완료 조건이다.

### 라인 PC

| | |
|---|---|
| 브라우저 | **Chrome 또는 Edge** — Web Serial API가 필요하다 |
| 서버 접속 | **HTTPS** — Web Serial은 보안 컨텍스트에서만 동작한다 |
| 장비 | 바코드/QR 스캐너(HID), USB-시리얼 케이블 |

Firefox와 Safari는 Web Serial을 지원하지 않는다. 라인 PC는 통제된 환경이므로 브라우저를 지정하면 된다.

### 계정

`@MQTTID`는 **그 단말의 MAC**이다. `@MQTTPW`는 서버가 MAC별로 발행한다.

password 정책과 브로커 등록 방법은 `SERVER_DEVICE_CREDENTIAL_SPEC_2026-08-27.md`에 있다.
