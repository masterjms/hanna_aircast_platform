## 1. 질문 1: 반영 가능 여부와 일정

**완료했습니다.** 2026-08-24 기준 단말 펌웨어에 반영되어 빌드 검증까지 끝났습니다.

구현 내용:

| 항목 | 구현 |
|---|---|
| `stream_url` 파싱 | `LIVE_START` payload에서 추출 |
| 있을 때 | 그 문자열로 Icecast 접속 |
| 없거나 빈 문자열 | 컴파일타임 기본 mount로 접속 (요청하신 fallback 유지) |
| 파싱/재조립 | **하지 않음.** 받은 문자열을 그대로 HTTP GET 대상으로 사용 |
| 최대 길이 | **512바이트**(NUL 포함) |
| 길이 초과 시 | 잘라 쓰지 않고 방송 시작을 **거절** |
| 재접속 | ~~세션 동안 URL을 보관해 같은 mount로 재접속 (3초 주기)~~ → **정정: 재접속하지 않음** |

요청서 §3.2의 "village_id나 job_id로 경로를 직접 만들지 말아 달라"는 그대로 지켰습니다. 단말은 경로 구조를 전혀 해석하지 않으므로, 나중에 경로가 바뀌어도 펌웨어를 고칠 필요가 없습니다.

### 1.1 재접속 시 동작 (서버측 확인 필요)

> ⚠ **이 절은 2026-08-24 단말측 정정으로 폐기됨** — `ESP32_정정_스트림단절시_단말동작_260824.md` 참고.
> 단말은 **재접속하지 않는다.** 단절되면 `LIVE_READY status=2` 를 올리고 IDLE 로
> 돌아가며 그 방송은 끝난다. 아래 원문은 이력 보존용이다.

스트림이 끊기면 단말은 **같은 `stream_url`로 3초 주기 재접속**을 시도합니다. 따라서 **방송이 끝날 때까지 해당 mount를 유지**해 주셔야 합니다. 방송 중간에 mount를 닫았다 다시 여는 구성이면 알려주세요.

### 1.2 버퍼 크기를 512로 잡은 이유

요청서 §3.5에서 "256이면 충분, 여유는 512 권장"이라 하셔서 **512**로 잡았습니다.

다만 잘린 URL로 엉뚱한 mount에 조용히 붙는 것이 가장 위험하다고 봐서, **초과 시 잘라 쓰지 않고 거절**하도록 했습니다. 거절되면 방송이 시작되지 않으므로, MQTT 명령 payload 전체 상한(**1024바이트**)과 함께 서버 발행 전 검사를 부탁드립니다.

## 3. 중요: `https://`는 TLS 전환 이후에 지원됩니다

**현재 단말은 `https://` Icecast URL로 접속하지 못합니다.** `http://`만 동작합니다.

이유는 단말 Icecast 클라이언트에 TLS 인증서 검증 설정(`crt_bundle_attach`)이 아직 없기 때문입니다. 파일 다운로드(`FILE_START`)와 OTA 클라이언트에는 이미 들어가 있어서 그쪽은 `https://`가 되지만, Icecast 경로만 빠져 있습니다.

**따라서 TLS 전환 전까지 `stream_url`은 `http://`로 발행해 주세요.**

`https://` 지원은 TLS 전환 작업(`HOST_CONFIRMED_TLS_ROLLOUT_CHECKLIST_2026-08-23.md`)에서 Icecast 클라이언트에 인증서 검증을 추가하면서 함께 처리합니다. 그 작업은 실제 도메인 확정을 기다리는 중이라, 도메인이 정해지면 같이 진행됩니다. 요청서 §3.4의 `https://<도메인>/live/...`(포트 생략) 형태는 그 시점부터 동작합니다.

## 4. 중요: 마을마다 mount를 만들 필요는 없습니다

요청서 §4에서 "고정 mount면 마을별 동시 방송이 불가능하다"고 하셨는데, **운영 전제를 확인한 결과 마을마다 mount를 나눌 필요가 없습니다.** 이 부분은 서버 작업량과 직결되니 먼저 정리합니다.

### 4.1 운영 전제

**동시에 나가는 방송은 항상 같은 내용입니다.** 마을 A에 X를, 마을 B에 Y를 같은 시각에 내보내는 운용은 하지 않습니다. 여러 마을에 동시 방송한다는 것은 **하나의 방송을 여러 마을이 함께 받는다**는 뜻입니다.

### 4.2 그래서 mount는 방송 1건당 1개면 됩니다

Icecast의 "mount당 source 1개" 제약은 **송출하는 쪽**에만 걸립니다. 듣는 쪽(listener)은 제한이 없습니다 — 원래 여러 대에 뿌리라고 있는 서버니까요.

원본 오디오가 하나면 mount도 하나면 되고, 그 URL을 대상 마을 수만큼 MQTT로 발행하면 됩니다.

```text
방송 1건(job_id 141)을 마을 1,2,3에 전송

  Icecast   mount 1개  /live/141   <- source 1개만 붙임
  MQTT      iotradio/village/00000001/cmd  LIVE_START stream_url=.../live/141
            iotradio/village/00000002/cmd  LIVE_START stream_url=.../live/141
            iotradio/village/00000003/cmd  LIVE_START stream_url=.../live/141
```

요청서 §3.4의 `/live/<village_id>/<job_id>` 형태로 마을마다 mount를 만들면, **같은 오디오를 마을 수만큼 중복 송출**하게 됩니다. 서버 부하만 늘고 얻는 것이 없습니다.

mount를 나눠야 하는 때는 **오디오 원본이 둘 이상 동시에 존재할 때**뿐입니다. 현재 운영 전제에서는 발생하지 않습니다. 나중에 마을별로 다른 내용을 동시 송출하는 요구가 생기면 그때 원본 수만큼 나누면 되고, 단말은 `stream_url`을 그대로 쓰므로 **그때도 펌웨어 변경이 필요 없습니다.**

### 4.3 다만 세션마다 경로는 새로 잡아 주세요

원본이 하나여도 **`job_id`마다 mount 경로를 다르게 하는 것**은 권장합니다(예: `/live/141`, `/live/142`).

고정 `/live` 하나를 계속 재사용하면, 단말이 `LIVE_STOP`을 놓쳐 이전 mount에 붙어 있을 때 다음 방송 오디오가 그 단말로 그대로 흘러들어갑니다. 세션마다 경로가 다르면 그런 단말은 새 방송을 못 받고 조용히 끊기므로 상태가 분명해집니다.

### 4.4 §6 "발신 전까지 서버측 임시 대응"에 대한 답

요청서 §6에서 "펌웨어 반영 일정에 따라 서버가 임시로 `/live` 고정 mount를 쓰는 설정 스위치를 둘 수 있다"고 하셨는데, **그럴 필요 없습니다.** 단말 반영이 이미 끝났습니다.

## 5. 질문 3: 스트림 접속 실패 시 단말 동작 — **이미 보고되고 있습니다**

가장 중요한 답변입니다. 그리고 **기존 사양서에 누락되어 있던 동작**이라 이번에 사양서에 추가했습니다.

### 5.1 서버는 `LIVE_READY`를 두 번 받습니다

```text
1) LIVE_READY status=0            <- P4 오디오 출력 준비 완료 (Icecast 접속 시도 前)
2) LIVE_READY status=2 reason=0x01 <- 스트림 접속 실패로 abort
```

```json
{"type":"LIVE_READY","ver":267,"job_id":101,"device":"58:e6:c5:f2:cc:74","status":0,"reason":0}
{"type":"LIVE_READY","ver":267,"job_id":101,"device":"58:e6:c5:f2:cc:74","status":2,"reason":1}
```

`status=2`는 ABORT, `reason=0x01`은 FAIL/ABORT입니다. 함께 `STATUS`도 `state=IDLE, busy=0`으로 돌아옵니다.

### 5.2 그래서 서버가 주의할 점

**`LIVE_READY status=0`만 보고 방송 성공으로 처리하면 안 됩니다.**

`status=0`은 "P4 스피커 출력 준비가 됐다"는 뜻이지 "스트림을 받기 시작했다"는 뜻이 아닙니다. 순서상 Icecast 접속 **전에** 나갑니다. 두 번째 메시지까지 봐야 실제 성공 여부를 알 수 있습니다.

### 5.3 실측 로그 (2026-08-24, mount 미생성 상태에서 LIVE_START)

```text
LIVE_CTRL_READY session=161 status=0 reason=0x00      <- LIVE_READY status=0 발행
icecast: connect url=http://192.168.0.41:8000/live
icecast: HTTP status=404                              <- mount 없음
icecast: command stream stopped: ESP_ERR_INVALID_RESPONSE
[ICECAST] stream inactive, clear live state
STATUS ... "state":"IDLE","busy":0
LIVE_CTRL_READY session=161 status=2 reason=0x01      <- LIVE_READY status=2 발행
```

단말은 실패를 감지하고 상태를 정리한 뒤 정상 복귀했습니다. 매달리거나 BUSY로 굳지 않습니다.

### 5.4 실패를 줄이려면

요청서 §7에서 "`LIVE_START` 발행 **전에** source를 붙여 mount를 먼저 만든다"고 하셨는데, 그게 정확한 순서입니다. 그대로 유지해 주세요. 순서가 뒤바뀌면 위 로그처럼 404가 납니다.

## 5.5 MQTT 발행 방법 (mount 개수는 §4 참고)

대상에 따라 발행처만 달라집니다. mount는 §4대로 방송 1건당 1개입니다.

| 대상 | MQTT 발행 | mount |
|---|---|---|
| 특정 마을 몇 곳 | 해당 `iotradio/village/<id>/cmd`에 각각 발행 (같은 `stream_url`) | 1개 |
| 전체 마을 | `iotradio/all/cmd`에 한 번 발행 | 1개 |

단말은 자기 마을 topic 하나만 구독하므로 서로 간섭하지 않습니다. 두 경우 모두 **현재 MQTT 사양 그대로 동작하며 변경이 필요 없습니다.**

## 5.6 한 단말에 방송이 겹칠 때 — 서버가 순서를 만들어 주셔야 합니다

**단말에는 우선순위 판단 기능이 없습니다.** 먼저 시작한 것이 끝날 때까지 단말을 차지하고, 그 사이에 온 LIVE/FILE/OTA 명령은 전부 거부됩니다.

| 진행 중 | `LIVE_START` | `FILE_START` |
|---|---|---|
| LIVE | `LIVE_READY status=3 reason=0x08` | `FILE_ABORT reason=PREEMPTED_BY_LIVE` |
| FILE | `LIVE_READY status=3 reason=0x08` | `FILE_ABORT reason=BUSY` |
| OTA | `LIVE_READY status=3 reason=0x08` | `FILE_ABORT reason=BUSY` |

**파일 다운로드 중이면 그 사이에 온 실시간 방송도 거부됩니다.** 긴급 방송이라도 예외가 없습니다. 사양서 §5의 `OTA > LIVE > FILE` 순서는 STATUS 표시용이지 선점 규칙이 아닙니다(이번에 사양서에서 명확히 했습니다 — §5.1).

### 권장 순서

```text
1. STATUS로 대상 단말이 방송 중인지 확인
2. 방송 중이면 먼저 LIVE_STOP / FILE_STOP 발행
3. STATUS가 state=IDLE, busy=0 으로 돌아온 것 확인   <- 생략하면 거부될 수 있음
4. 새 LIVE_START / FILE_START 발행
```

**3번이 중요합니다.** 정지 명령을 받으면 단말은 내부 상태를 바로 내리지만, Icecast 수신 태스크가 실제로 끝나기까지 **최대 5초**, P4 오디오 정리에 약 3초가 더 걸립니다. 그 사이에 새 명령이 오면 거부됩니다.

특히 **이미 끊긴 스트림을 정지할 때가 가장 오래 걸립니다** — 서버가 "왜 안 멈추지" 하고 재시도하기 쉬운 바로 그 상황입니다. 고정 지연을 추측하지 마시고 STATUS를 기다려 주세요. 단말은 상태가 바뀌면 주기를 기다리지 않고 STATUS를 즉시 발행합니다.

3번이 정해둔 시간(권장 10초) 안에 오지 않으면 그 단말은 이상으로 보고 **건너뛰고 나머지 마을 방송을 계속 진행**해 주세요. 단말 한 대 때문에 다른 마을 방송이 막히면 안 됩니다.

## 6. 서버측에 부탁드리는 것 정리

1. `stream_url`을 **`http://`로** 발행 (TLS 전환 전까지). `https://`는 §3 참고
2. URL 길이 **512바이트 이하**, MQTT payload 전체 **1024바이트 이하** 보장
3. `LIVE_START` 발행 **전에** mount 생성 (요청서 §7대로)
4. 방송 종료까지 **mount 유지** (단말이 3초 주기로 같은 URL에 재접속)
5. **`LIVE_READY status=0`만으로 성공 판단 금지** — §5.2
6. **mount는 방송 1건당 1개.** 마을 수만큼 만들지 마세요 — 같은 오디오를 중복 송출하게 됩니다 — §4.2
7. 다만 `job_id`마다 **mount 경로는 새로** (`/live/141`, `/live/142` …) — §4.3
8. 방송 중인 단말에 새 방송을 보낼 때는 **정지 → STATUS `IDLE` 확인 → 시작** 순서. 단말에 선점 기능이 없어 곧바로 보내면 거부됨 — §5.6
9. 위 STATUS 확인이 10초 안에 안 오면 그 단말은 **건너뛰고 나머지 마을 방송 진행** — §5.6

## 7. 참고: 관련해서 확인된 다른 사항

이번 연동 테스트 중 확인된 것들입니다. 참고만 하세요.

- **파일 다운로드(`FILE_START`)는 이미 `https_url`을 그대로 쓰고 있습니다.** 요청서 §2에 쓰신 대로입니다. 다만 2026-08-24 테스트에서 `192.168.0.41:8080` 연결이 타임아웃되는 구간이 있었습니다(이후 복구 확인). 파일 서버 기동/바인딩 주소/방화벽을 한 번 봐 주세요.
- **파일명에 한글+공백**(`남성 보이스 시험.mp3`)이 들어온 건은 MQTT 수신까지는 정상 확인했으나, 위 연결 실패로 저장까지는 검증되지 않았습니다. 8080 정상화 후 재확인이 필요합니다.
- **단말 다운로드 실패 시 복구 동작**을 이번에 개선했습니다. 이전 펌웨어는 파일 서버 접속 실패 후 내부 상태가 BUSY로 굳어 이후 파일·라이브 방송을 모두 거부했는데, 이를 수정해 실패해도 즉시 `IDLE`로 복귀합니다. 위 8080 타임아웃 상황에서 실제로 정상 복귀를 확인했습니다.
