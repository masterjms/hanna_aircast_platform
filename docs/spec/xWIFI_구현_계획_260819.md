xWIFI 운영서버 구현 계획 (v1)

설계 문서 4종(운영서버 개요/DB 스키마/API 설계/화면 설계)과 신규 요구사항(역할별 권한 UI, TTS, 파일 저장 방식), 그리고 기존 구현체 조사 결과를 하나로 합친 실행 계획이다. 앞선 문서들이 "무엇을 만들 것인가"였다면 이 문서는 "어떤 순서로, 무엇부터"에 해당한다.

단말(ESP32) 쪽 프로토콜은 `xWIFI_통신_사양_최종_260813.md`를 그대로 따르며 이 문서에서 바꾸지 않는다.

## 1. 역할별 권한 (super_admin / village_admin)

### 1-1. 원칙

권한은 **백엔드가 강제**한다. 프론트가 메뉴를 숨기는 것은 편의일 뿐이고, API가 직접 막지 않으면 권한이 없는 것과 같다. 모든 조회 API는 응답을 만들기 전에 담당 village_id 범위로 필터링하고, 모든 제어 API는 대상이 범위를 벗어나면 403으로 거절한다.

- `super_admin`: 전체 마을. 계정은 원칙적으로 1개(개발/운영 담당자).
- `village_admin`: 마을별 방송 관리자. `user_villages`에 배정된 마을만. 복수 마을 담당 가능(UI 예시의 `park_leader` = 대곡마을, 하평마을).

### 1-2. 메뉴 접근 (UI 예시 사이드바 기준)

UI 예시에서 `관리자` 태그가 붙은 4개 메뉴가 super_admin 전용이다. village_admin 로그인 시 사이드바에서 **아예 렌더링하지 않는다**(비활성화가 아니라 제거).

| 메뉴 | super_admin | village_admin |
|---|---|---|
| 대시보드 | 전체 | 담당 마을만 집계 |
| 단말 관리 | 전체 + 미배정 | 담당 마을 단말만. 미배정 섹션 없음 |
| 방송 제어 | 전체/마을/구역/개별 | 담당 마을 이하만. "전체" 옵션 없음 |
| 파일함 | 전체 | 전체 공용(파일은 마을에 귀속되지 않음) |
| 이력 | 전체 | 담당 마을 관련 이벤트만 |
| 스케줄 | 전체 | 담당 마을 대상 규칙만 생성/조회 |
| 비용 | 실비용 + 마을별 추정 | 담당 마을 추정치만 |
| OTA 관리 `관리자` | 가능 | **메뉴 없음** |
| 설정(CONFIG) `관리자` | 가능 | **메뉴 없음** |
| 마을 관리 `관리자` | 가능 | **메뉴 없음** |
| 계정 관리 `관리자` | 가능 | **메뉴 없음** |

상단 우측 `담당 범위` 필스는 역할에 따라 문구가 바뀐다.

```
super_admin  : 담당 범위  전체 12개 마을 · 300대
village_admin: 담당 범위  신동마을 · 34대
```

**UI 예시에 `비용` 메뉴가 빠져 있다.** 화면 설계 문서에는 있으므로 사이드바에 추가한다(이력과 스케줄 사이, 관리자 태그 없음).

### 1-3. 데이터 범위 규칙

| 대상 | 규칙 |
|---|---|
| 단말 | `devices.village_id IN (담당 마을)` |
| 미배정 단말 | `village_id IS NULL` → **super_admin만 조회·배정**. 소속이 없으므로 village_admin에게 보일 근거가 없다 |
| 마을/구역 | 마을 생성·삭제는 super_admin. village_admin은 담당 마을의 **구역**만 관리 |
| 파일 | 공용. 단, 삭제는 업로더 본인 또는 super_admin |
| 이력 | `broadcast_events.target_id`가 담당 마을이거나, `device_events.mac`이 담당 마을 단말인 것 |
| 비용 | village_admin은 `scope=village` + 담당 village_id만. `scope=all`은 403 |
| CONFIG | 전체 단말에 영향 → super_admin 전용 |

### 1-4. MQTT 토픽 권한 매핑

권한 체크는 **MQTT 발행 직전**에 한 번 더 한다. 토픽이 곧 영향 범위이기 때문이다.

| target_scope | 발행 토픽 | 허용 |
|---|---|---|
| `all` | `iotradio/all/cmd` | **super_admin만** |
| `village` | `iotradio/village/<8자리>/cmd` | 담당 마을이면 village_admin 가능 |
| `zone` | 소속 단말 MAC별 개별 토픽으로 분할 | 담당 마을 소속이면 가능 |
| `device` | `iotradio/device/<mac>/cmd` | 담당 마을 소속이면 가능 |

`zone`은 MQTT에 존재하지 않는 개념이므로(구역은 DB 안에만 있음) 백엔드가 `devices`를 조회해 MAC 목록으로 펼쳐 개별 발행한다.

### 1-5. 구현 메모

- 로그인 시 JWT에 `role`과 `village_ids`를 담되, **권한 판정은 DB를 다시 조회해서** 한다. 토큰 발급 후 담당 마을이 바뀌었을 때 토큰이 만료될 때까지 옛 권한이 유지되는 것을 막는다.
- FastAPI 의존성으로 `require_super_admin()`, `scoped_village_ids(user)` 두 개를 만들고 모든 라우터가 이 중 하나를 반드시 거치게 한다. 누락을 막기 위해 라우터 등록 시점에 의존성이 없는 엔드포인트가 있으면 기동 실패시키는 체크를 넣는다.

## 2. 파일 저장 설계

### 2-1. 결정: EC2 로컬 디스크

S3/GCS 등 외부 오브젝트 스토리지를 **원본 저장소로 쓰지 않는다.** 근거 4개:

1. **MQTT payload 1024바이트 제한.** `FILE_START`에 URL을 실어야 하는데 S3 presigned URL(SigV4)은 400~600자다. sha256(64자)과 나머지 필드를 더하면 700~900바이트가 되어 파일명이 조금만 길어도 초과한다. 자체 토큰 URL이면 전체 payload가 250바이트 안쪽이다.
2. **온프레미스 전환 원칙.** 운영서버 개요의 "지금 단계에서 준비해둘 것" 3번에 이미 명시되어 있다.
3. **용량이 문제가 아니다.** TTS 8초 ≈ 130KB, mp3 1분 ≈ 1MB. 1000개 쌓아도 500MB 수준.
4. **단말 CA 관리.** 외부 도메인을 쓰면 ESP32가 해당 루트 CA를 신뢰해야 한다. 지금은 `iot_radio.co.kr` 하나로 끝난다.

### 2-2. 디렉토리 구조

```
/var/lib/iotradio/files/
├─ upload/2026/08/<uuid>.mp3      업로드 원본
├─ tts/<sha1(text|lang|voice)>.mp3  TTS 생성물 (캐시 키가 곧 파일명)
└─ update/IOT_RADIO.pkg            OTA 펌웨어
```

경로는 환경변수 `IOTRADIO_FILE_ROOT`로 분리한다(온프레미스 전환 시 이 값만 바뀜). 컨테이너에서는 볼륨 마운트.

### 2-3. DB 스키마 보강

현재 `files` 테이블에 실제 저장 경로 컬럼이 없다. 아래를 추가한다.

```sql
ALTER TABLE files ADD COLUMN storage_path  VARCHAR(500) NOT NULL;  -- FILE_ROOT 기준 상대경로
ALTER TABLE files ADD COLUMN duration_sec  NUMERIC(8,2);           -- 목록의 "길이" 컬럼용
ALTER TABLE files ADD COLUMN tts_voice     VARCHAR(50);            -- Polly voice id
ALTER TABLE files ADD COLUMN content_type  VARCHAR(50) NOT NULL DEFAULT 'audio/mpeg';
CREATE UNIQUE INDEX files_tts_cache ON files (sha256) WHERE source = 'tts';
```

`duration_sec`은 화면 설계의 파일 목록 "길이(0:32)" 컬럼에 필요한데 기존 스키마에 없었다. 업로드 시 `ffprobe`로 계산한다.

**바이너리는 DB에 넣지 않는다.** BYTEA로 넣으면 백업 크기가 폭증하고 범위 요청 스트리밍이 어려워진다.

### 2-4. 만료 토큰

```
POST /api/broadcast/file/start
  → 토큰 발급 (file_id, 만료시각, 발급 job_id)
  → https_url = https://<host>/dl/<token>
  → FILE_START 발행
```

- 토큰은 랜덤 16~22자(URL-safe). 짧게 유지해 payload 여유를 확보한다.
- 유효기간 기본 **10분**. 방송 1회를 수행하기에 충분하고, 유출돼도 금방 죽는다.
- 검증 실패 시 404(403이 아니라 — 토큰 존재 여부를 노출하지 않음).
- 저장은 별도 테이블 `download_tokens(token PK, file_id, expires_at, job_id, created_at)`. 만료분은 일별 배치가 정리.
- OTA pkg도 같은 방식을 쓰되 유효기간을 길게(예: 2시간 — 300대가 순차 다운로드).

### 2-5. 백업

원본은 로컬이고, 백업은 매일 새벽 `aws s3 sync`로 복사본만 올린다. 온프레미스 전환 시 대상만 NAS로 바꾸면 된다.

```bash
aws s3 sync /var/lib/iotradio/files s3://<bucket>/files --delete
```

## 3. TTS (문장 → mp3)

### 3-1. 흐름

UI 예시의 "문장으로 만들기(TTS)" 폼 기준.

```
문구 입력 → 언어(한/영/일/중) + 보이스(여성/남성) 선택
  → [미리듣기 ▶]  : Polly 호출 → 임시 재생 (아직 저장 안 함)
  → [파일로 저장]  : files 테이블 insert + 로컬 저장
  → 파일함에 "TTS · 한국어" 로 표시 → 방송 대상 선택으로 이동
```

### 3-2. 캐시

같은 문장을 반복 방송하는 경우가 많으므로(민원 안내, 영농 교육 등) 매번 Polly를 호출하지 않는다.

```
cache_key = sha1(text + "|" + lang + "|" + voice)
```

이 키로 기존 파일이 있으면 재사용한다. 미리듣기도 같은 캐시를 타므로 "미리듣기 → 저장" 흐름에서 Polly 호출은 **1회**만 발생한다.

### 3-3. 출력 포맷

Polly `OutputFormat=mp3`의 기본 샘플레이트는 22050Hz다. 단말(P4)의 mp3 디코더가 지원하는 샘플레이트/비트레이트 범위를 확인해서 맞춰야 한다 — **코덱스 확인 항목**(§9). 확인 전까지는 기존에 검증된 업로드 mp3와 동일한 파라미터로 후처리한다.

```bash
ffmpeg -i polly_out.mp3 -ar 22050 -ac 1 -b:a 64k out.mp3
```

### 3-4. 비용

안내문 위주면 무시 가능한 수준(월 1천원 미만). 캐시가 있으므로 실제 호출은 더 적다. 다만 super_admin이 Polly 호출 횟수를 볼 수 있게 `files` 생성 이력으로 간접 확인 가능하게 둔다.

## 4. LIVE 방송 경로

### 4-1. 기존 구현 자산

`IoT_radio_server`(Python/aiohttp) + `IoT_radio_front`(React/TS)에 브라우저 마이크 → 서버 경로가 **이미 완성되어 있다.** 새로 설계하지 않고 이식한다.

```
브라우저 마이크
 → opus-recorder (WASM, 16kHz mono / VOIP / 40ms / maxFramesPerPage=1)
 → WSS /ingest  (첫 메시지 JWT 인증, 동시 방송자 1명 제한)
 → 서버
```

핵심 설계 3가지를 그대로 가져간다.

- **`/ingest` 연결 자체가 LIVE 시작 트리거.** 연결 → `LIVE_START` 발행, 끊김 → `LIVE_STOP` 발행. 별도 API와 타임아웃 로직이 필요 없다.
- **첫 메시지 인증.** 브라우저 WebSocket은 커스텀 헤더를 못 넣으므로 `{"type":"auth","token":"<JWT>"}`를 첫 메시지로 받는다(3초 타임아웃).
- **close code로 거절 사유 구분.** `4001` 인증실패(재시도 안 함) / `4003` 단말없음 / `4009` 이미 방송중.

### 4-2. Icecast 전환에 따른 변경

기존 시스템은 서버가 WSS로 오디오를 직접 fan-out했지만, 신규 사양은 Icecast가 담당한다. 따라서:

| 기존 모듈 | 신규 |
|---|---|
| `pacing.py` (239줄, 07 정책) | **삭제.** Icecast + 단말 지터버퍼(38프레임 프리버퍼)가 대신함 |
| `audio_channel.py` fan-out | **삭제.** Icecast가 리스너 N명 관리 |
| 프론트 `OggOpusDemuxer` | **삭제.** 아래 참고 |

**디먹서를 지우는 게 핵심 이득이다.** 기존 프론트는 opus-recorder가 뱉은 Ogg를 벗겨 raw Opus packet으로 보냈는데, Icecast는 Ogg/Opus를 그대로 받는다. 즉 벗길 이유가 없어진다.

```
기존: 브라우저 [Ogg 벗김] → raw packet → 서버 [pacing] → WSS fan-out
신규: 브라우저 [Ogg 그대로] ─────────→ 서버 [ffmpeg stdin] → Icecast → 단말이 GET
```

서버 측 코드는 이 정도로 줄어든다.

```python
ff = await asyncio.create_subprocess_exec(
    "ffmpeg", "-f", "webm", "-i", "pipe:0",
    "-c:a", "libopus", "-b:a", "24k", "-ac", "1", "-ar", "16000",
    "-application", "voip", "-page_duration", "40000",
    "-content_type", "application/ogg", "-f", "ogg",
    f"icecast://source:{PASS}@127.0.0.1:8000/live",
    stdin=asyncio.subprocess.PIPE)

async for msg in ws:                      # 받은 걸 그대로 흘려보내기만 한다
    if msg.type == WSMsgType.BINARY:
        ff.stdin.write(msg.data)
```

**절대 하면 안 되는 것:** 받은 바이트를 파싱하거나 재청킹하거나 프레임을 재조립하는 것. Opus packet 경계는 Ogg의 segment table(lacing, 255 규칙)로만 알 수 있고 page 경계를 넘어 이어지기도 하므로, 고정 크기로 자르면 반드시 깨진다. FFmpeg에 그대로 넘긴다.

### 4-3. 대규모 방송 시작 정책 (진행순서 8번의 답)

기존 사양 7-2는 "LIVE_READY 확인 후에만 송출 시작"인데, 이건 단말 1대 데모 기준이다. 300대에서는 전부 기다릴 수 없다.

**Icecast 구조에서는 기다릴 필요 자체가 없다.** 스트림은 FFmpeg이 밀어넣는 순간부터 흐르고, 각 단말은 준비되는 대로 `GET /live`로 붙는다. 늦게 붙은 단말은 그 시점부터 들릴 뿐 다른 단말에 영향을 주지 않는다.

따라서 정책을 이렇게 정한다.

- 송출은 `/ingest` 연결 즉시 시작한다. **LIVE_READY를 게이트로 쓰지 않는다.**
- `LIVE_READY`는 **UI 표시와 실패 집계 전용**이다 — "준비 완료 8 / 10대".
- 대상 카운트는 **온라인 단말만** 넣는다(최근 STATUS 5분 이내). 오프라인 단말은 분모에서 제외하고 별도 표시.
- `status=3, reason=8`(BUSY)로 거절한 단말은 "실패" 목록에 넣고 **자동 재시도하지 않는다**(기존 BUSY 정책 그대로).
- `ready_timeout_sec`(기본 30) 경과 후에도 무응답인 단말은 "대기 중" → "무응답"으로 전환.

## 7. 구현 단계

각 단계는 앞 단계에 의존한다. 특히 **권한을 Phase 1에 넣는 이유**는, 나중에 얹으면 모든 쿼리와 라우터를 다시 뜯어야 하기 때문이다.

### Phase 0 — 준비

- 기술 스택 최종 확정(§6 승인)
- 리포지토리 생성, Docker Compose 골격(backend/postgres/mosquitto/icecast)
- 로컬 개발 환경: Postgres + Mosquitto 컨테이너, 단말 없이도 돌 수 있게 mock STATUS 발행 스크립트
- 기존 문서 갱신(§8)

### Phase 1 — 기반: DB + 인증 + MQTT 수신

여기까지 되면 단말 전원만 넣어도 데이터가 쌓이기 시작한다. 이후 화면 개발이 훨씬 쉬워지므로 최우선.

- DDL 실행(§2-3 보강 포함) + Alembic 초기 마이그레이션
- `auth`: 로그인/로그아웃/me, bcrypt + JWT
- **권한 의존성 2종**: `require_super_admin()`, `scoped_village_ids(user)`
- MQTT 구독 데몬: `status` / `result` 토픽 → `device_events` 적재, `devices.last_status`·`last_seen_at` 갱신
- 미등록 MAC 자동 등록(`village_id=NULL`)
- QoS 1 중복 방지(`session_id`/`cmd_id`/`file_id` 기준 멱등 처리)
- CONFIG reconciliation: 기동 시 1회 + 1시간 주기로 `current_config` → `iotradio/all/config` 재발행
- `/health` (DB / MQTT / Icecast 연결 확인)

### Phase 2 — 조회계 API + 프론트 골격

- 마을/구역 CRUD, 계정 CRUD, 단말 CRUD·재배정
- 대시보드 `summary` / `map`
- React 프로젝트 셋업, 로그인 화면
- **역할별 사이드바**(관리자 태그 4개 조건부 렌더), 담당 범위 필스
- 단말 관리 화면(필터, 목록, 미배정 섹션, 상세 모달)
- 폴링 훅(5초) 공통화

### Phase 3 — 파일 저장 + FILE 방송

- 파일 업로드(multipart), size/sha256/duration 서버 계산, 로컬 저장
- `download_tokens` + `/dl/<token>` 서빙
- `POST /api/broadcast/file/start` → 토큰 발급 → `FILE_START` 발행 → `broadcast_events` insert
- `FILE_END` / `FILE_ABORT` / `FILE_STOP_RESULT` 수집 → 진행 상황 집계
- 방송 제어 화면(대상 선택, 파일 방송, 진행 상황 카드)

FILE을 LIVE보다 먼저 하는 이유: 오디오 파이프라인 없이 MQTT 왕복만으로 전체 제어 흐름을 검증할 수 있다.

### Phase 4 — LIVE 방송

- `/ingest` WSS 이식 + FFmpeg → Icecast 파이프(§4-2)
- 프론트 마이크 캡처 이식(디먹서 제거)
- 송출 정책 적용(§4-3), 준비율 실시간 표시(2초 폴링)
- Icecast 설정 이전(`queue-size` 16KB, `page_duration` 40ms)

### Phase 5 — 파일함 + TTS

- Polly 연동, 캐시(§3-2), 미리듣기
- 파일함 화면(목록, 업로드, TTS 모달)

### Phase 6 — 스케줄 + 이력

- `schedules` CRUD(10개 제한 API 체크), APScheduler 1분 폴링
- 방송 중이면 스킵(기존 BUSY 정책 재사용)
- 이력 화면(기간/마을/타입 필터, 페이지네이션, 상세)

### Phase 7 — OTA

- pkg 업로드, size/sha256 계산
- `OTA_START` → `OTA_STATUS` 수집 → `OTA_APPLY` 승인 버튼
- 재부팅 후 STATUS 펌웨어 버전으로 성공 판정
- OTA 진행 중 단말은 방송 API에서 거절 + UI 배지·버튼 잠금

### Phase 8 — 비용 + 운영

- 일별 배치: `broadcast_events`/`device_events` 집계 → `daily_cost_summary` upsert
- Cost Explorer API로 전체 실비용 조회(super_admin 전용 행)
- 비용 화면(사이드바 메뉴 추가 포함)
- TLS: nginx(웹/파일) + Mosquitto TLS 포트, MQTT는 `stream{}` 또는 직접 노출
- CloudWatch 알람 + SNS, RDS 백업 설정, 파일 S3 sync cron
- 배포 문서화
