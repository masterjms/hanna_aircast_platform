# xWIFI 서비스 KPI와 SLO

기준일: 2026-09-06

관련 문서: [시스템 아키텍처](01_시스템_아키텍처.md) · [단말 연동](02_단말_연동_사양.md) · [데이터 모델](04_데이터_모델.md) · [프론트엔드 운영 화면](05_프론트엔드_운영.md) · [인프라와 운영](06_인프라_운영.md)

이 문서는 xWIFI의 제품 성과와 운영 품질을 같은 기준으로 판단하기 위한 측정 규칙이다. SLO는 **지금 측정할 수 있는 항목에만** 둔다. 측정 경로가 아직 없는 항목은 §14의 관측 항목으로 두고, 실제 회선과 단말 300대 규모의 기준 데이터를 4주 이상 모은 뒤 SLO로 올린다.

## 1. 지표 체계

| 구분 | 의미 | 예 |
|---|---|---|
| KPI | 제품과 운영이 달성해야 하는 핵심 결과 | 방송 재생 시작 성공률 |
| SLI | 결과를 계산하는 실제 측정값 | 성공 응답 단말 수 ÷ 대상 단말 수 |
| SLO | 내부 운영 목표 | 월간 99.0% 이상 |
| SLA | 고객과 계약한 보상·책임 기준 | 별도 계약에서 정하며 SLO와 동일시하지 않음 |

비율은 고객별·마을별·방송 유형별로 집계하고, 전체 평균으로 특정 마을의 장애를 가리지 않는다. 운영 대시보드는 최근 24시간, 7일, 30일 값을 제공하고 월간 리뷰는 30일 값을 기준으로 한다.

## 2. 최상위 목표

### 2.1 North Star

> 필요한 방송이 올바른 단말에 제시간에 끊김 없이 도달한 비율

다음을 모두 만족한 대상 단말을 성공으로 센다.

1. 권한과 대상 계산이 정확했다.
2. 명령 후 정해진 시간 안에 재생 시작을 확인했다.
3. 방송 도중 중대한 끊김이나 오류가 없었다.
4. 종료 명령 후 정상 상태로 복귀했다.

단말은 스피커의 물리적 음압을 측정하지 않는다. `LIVE_READY`, `STATUS.state=LIVE`, `FILE_RESULT`, `LIVE_STATS`는 **재생 가능 상태와 소프트웨어 동작의 근사 지표**다. 실제 가청 여부는 표본 현장 점검으로 별도 검증한다.

### 2.2 핵심 KPI

| 우선순위 | KPI | 계산 기준 | 초기 SLO |
|---:|---|---|---:|
| 1 | 방송 재생 시작 성공률 | 제한 시간 안에 재생 시작이 확인된 대상 단말 ÷ 시작 시점 대상 단말 | 99.0% 이상 |
| 2 | 긴급 방송 시작 시간 | 운영자가 시작을 누른 시점부터 대상 단말의 재생 시작 확인까지 | P95 10초 이하 |
| 3 | 운영 서비스 가용성 | 정상적인 로그인·방송 시작·방송 종료가 가능한 시간 ÷ 운영 시간 | 월 99.5% 이상 |
| 4 | 중대 방송 사고 | 오방송, 무권한 방송, 전체 방송 불능, 방송 종료 불능 | 월 0건 |

`P95`는 측정값의 95%가 해당 시간 이내라는 뜻이다. 성공률은 방송 건수가 아니라 대상 단말 수 기준으로 계산한다. 단말 1대 방송과 300대 방송을 같은 1건으로 세면 영향도가 왜곡된다.

가용성은 공지된 점검 시간을 제외한다. 단일 EC2와 Single-AZ RDS 구성에서 배포 중단이 회당 1~2분 발생한다.

## 3. 방송 품질 KPI

### 3.1 실시간 방송

| KPI | 정의 | 초기 SLO | 측정 |
|---|---|---:|---|
| 준비 성공률 | `live_ready_timeout_sec + 5초` 안에 `LIVE_READY ok=true`를 보낸 단말 ÷ `expected_count` | 99.5% 이상 | `device_events` |
| 방송 준비 시간 | `triggered_at`부터 `LIVE_READY` 수신까지 | P95 8초 이하 | `device_events.received_at` |
| 정상 종료 시간 | `stop_requested_at`부터 대상 단말의 `LIVE_RESULT` 수신까지 | P95 5초 이하 | `device_events.received_at` |
| underrun 발생률 | underrun이 1회 이상 보고된 단말 ÷ 재생 단말 | 1.0% 미만 | `LIVE_STATS` |

`LIVE_READY`는 오디오 출력 준비 완료이며 실제 음성이 들렸다는 증거는 아니다. 화면은 준비, 재생 확인, 품질을 한 개의 성공 표시로 합치지 않는다.

### 3.2 파일·TTS 방송

| KPI | 정의 | 초기 SLO | 측정 |
|---|---|---:|---|
| 파일 방송 성공률 | `FILE_RESULT ok=true`를 보낸 단말 ÷ `expected_count` | 99.5% 이상 | `device_events` |
| 파일 수신 시간 | `triggered_at`부터 `FILE_RESULT ok=true`까지, 1 MiB 이하 파일 기준 | P95 10초 이하 | `device_events.received_at` |
| 중지 응답 시간 | `stop_requested_at`부터 `FILE_RESULT`까지 | P95 5초 이하 | `device_events.received_at` |

`FILE_RESULT ok=true`는 다운로드와 검증 완료이며 재생 시작 시점이다. 재생 종료는 단말이 보고하지 않으므로 서버가 음원 길이로 판정하고, 재생 종료 시간은 KPI로 두지 않는다.

TTS 방송은 생성된 MP3의 파일 방송이므로 전달 품질은 파일 방송 KPI에 포함한다. TTS 합성 자체의 성공률과 생성 시간은 외부 서비스 품질 지표로 별도 집계한다.

## 4. 단말과 네트워크 KPI

| KPI | 정의 | 초기 SLO | 측정 |
|---|---|---:|---|
| 단말 온라인율 | 온라인 단말 ÷ 운영 대상 단말 | 97% 이상 | `last_seen_at`, `last_status` |
| 24시간 이상 오프라인율 | 24시간 이상 상태가 없는 단말 ÷ 운영 대상 단말 | 1.0% 미만 | `last_seen_at` |
| broker 재시작 후 복구 시간 | broker 가용 시점부터 단말 재연결까지 | P95 3분 이하 | Mosquitto log, `last_seen_at` |
| CONFIG 일치율 | 변경 10분 뒤 최신 `config_version`을 적용한 온라인 단말 ÷ 온라인 단말 | 99.9% 이상 | `last_status.config_version` |
| 단말별 자격 증명 적용률 | 고유 계정과 마을 ACL을 가진 운영 단말 ÷ 운영 단말 | 100% | `devices.mqtt_password`, generated ACL |

온라인율은 가정용 Wi-Fi와 공유기 재부팅 영향을 받는다. 24시간 이상 오프라인율을 함께 본다.

## 5. 대상·권한·안전 KPI

사고 0건을 목표로 한다.

| KPI | 초기 SLO | 판정 기준 |
|---|---:|---|
| 오방송 | 0건 | 선택하지 않은 마을·구역·단말에 명령 또는 오디오 전달 |
| 권한 범위 위반 | 0건 | `village_admin`이 담당 밖 자원 조회·제어 |
| retained 명령 사고 | 0건 | CONFIG 외 방송 명령이 retained되어 재접속 단말에서 실행 |
| 실행자 제어 가시성 | 100% | 방송을 시작한 관리자가 그 방송을 조회·종료 가능 |

현재 `village_admin`이 `device`·`zone` 범위로 시작한 방송은 active/detail/stop 가시성 검사에서 숨겨진다. 이 결함을 해소하기 전에는 해당 관리자의 방송 대상을 마을 범위로 제한하거나 `super_admin`이 제어한다.

## 6. 관리자 사용성 KPI

주요 사용자는 컴퓨터에 익숙하지 않은 이장과 지자체 관리자다.

| KPI | 정의 | 초기 SLO |
|---|---|---:|
| 첫 시도 방송 성공률 | 별도 도움 없이 첫 시도에 올바른 대상 방송을 완료한 사용자 ÷ 시험 사용자 | 95% 이상 |
| 단말 등록 시간 | QR 또는 수동 등록 시작부터 완료까지 | 중앙값 5분 이하 |
| 방송 100건당 지원 문의 | 방송 조작 때문에 접수된 문의 수 | 2건 미만 |

분기마다 대표 사용자 5명 이상을 대상으로 마을 방송, 전체 방송, 방송 중지, 오프라인 단말 확인, 단말 등록 과제를 관찰한다.

## 7. 서버와 운영 KPI

| KPI | 정의 | 초기 SLO | 측정 |
|---|---|---:|---|
| API 가용성 | 정상 API 응답 가능 시간 ÷ 운영 시간, 공지 점검 제외 | 월 99.5% 이상 | 외부 uptime monitor |
| 서버 오류율 | HTTP 5xx ÷ 전체 API 응답 | 0.1% 미만 | nginx access log |
| 주요 API 응답 시간 | 로그인·대시보드·대상 조회·방송 요청 | P95 500ms 이하 | nginx `$upstream_response_time` |
| 대시보드 상태 신선도 | 서버가 STATUS를 받은 시점부터 화면 반영까지 | 7초 이하 | STATUS flush 1초 + polling 5초 |
| MQTT 이벤트 저장 지연 | broker 수신부터 DB 저장까지 | P95 2초 이하 | backend log |
| 고아 방송 작업 | 재시작 정리를 제외하고 종료 판정 없이 남은 active 작업 | 0건 | `broadcast_events` |
| 평균 복구 시간 MTTR | 장애 인지부터 핵심 방송 기능 복구까지 | 2시간 이하 | incident 기록 |
| 인증서 만료 사전 알림 | 만료까지 남은 기간 | 20일 전 알림 | `healthcheck.sh` |
| 디스크 사용률 | 파일 보관 volume | 80% 미만 | `healthcheck.sh` |

가용성은 `/health` 응답만으로 계산하지 않는다. DB 연결, MQTT publish, Icecast source 생성, 파일 volume 접근을 포함하는 합성 점검을 운용한다.

## 8. 백업과 복구 KPI

| KPI | 초기 SLO |
|---|---:|
| RDS 자동 backup·PITR 활성화율 | 운영 고객 100% |
| 파일 volume snapshot 성공률 | 예약 snapshot 100% |
| 최신 유효 backup 나이 | 24시간 이하 |
| 정기 복구 시험 성공률 | 100% |
| RPO | 최대 24시간, RDS PITR 구성 시 5분 이하 |
| RTO | 핵심 서비스 4시간 이하 |

복구 시험은 backup job의 성공 표시가 아니라 격리 환경에 DB와 파일을 복원하고 로그인·파일 조회·시험 방송 준비까지 확인해야 성공으로 센다. RTO는 EC2 재구축·EBS 복원·TLS 재발급이 수동인 현재 절차 기준이며 자동화 뒤에 줄인다.

`scripts/backup-db.sh`와 `scripts/healthcheck.sh`는 local PostgreSQL container를 전제로 한다. RDS 운영에서 이 지표를 신뢰하려면 RDS backup 상태와 복구 가능 시점을 직접 확인하도록 수정해야 한다.

| KPI | 계산식 |
|---|---|
| 활성 단말당 월 비용 | 고객별 월 총 운영비 ÷ 해당 월 활성 단말 수 |
| 전송량과 egress 비용 | 고객·방송 유형별 실제 전송 byte와 cloud egress 비용 |

`bytes_estimated`는 응답한 고유 단말 수 기반의 하한 추정치다. 비용 정산과 egress KPI에는 nginx access log와 AWS 실제 사용량을 사용한다.

## 13. 운영 대시보드의 기본 지표

첫 화면에는 다음만 상시 노출한다.

1. 방송 재생 시작 성공률
2. 긴급 방송 시작 시간 P95
3. 파일 방송 성공률
4. 단말 온라인율과 24시간 이상 오프라인 수
5. CONFIG·자격 증명 일치율
6. 오방송·권한·보안 사고 수
7. 운영 서비스 가용성
8. 평균 복구 시간
9. 활성 단말당 월 비용

등록 단말 수, 방송 횟수, TTS 생성 횟수는 규모를 설명하는 보조 지표다. 값이 커지는 것 자체가 품질 향상을 뜻하지 않는다.

## 14. 관측 항목 — SLO 없이 수집만

측정 경로나 기준선이 없어 SLO를 두지 않는다. 기준 데이터가 4주 이상 쌓이면 §2~§7로 올린다.

| 항목 | 현재 한계 |
|---|---|
| 재생 시작 성공률 (`STATUS.state=LIVE` 기준) | STATUS는 이력에 저장되지 않아 방송별 소급 계산 불가. PLAYING 확인을 `device_events`에 남기는 작업이 먼저다 |
| 무음·끊김 단말 비율, 일시 장애 회복률 | WAN 기준선 없음. `LIVE_STATS`와 `LIVE_RESULT code`로 수집 |
| 브라우저 업링크 실패율 | ingest 세션 metric 없음 |
| 파일 검증·네트워크·저장 실패율 | `FILE_RESULT code`별 집계. 기준선 후 SLO |
| MQTT 연결 성공률 | Mosquitto 인증 log 파싱 필요 |
| 약한 Wi-Fi 비율, 최신 펌웨어 비율 | RSSI 기준값과 승인 펌웨어 목록이 없음. OTA 구현 뒤 |
| 방송 대상 정확도, 대상 snapshot 보존율 | 시작 당시 대상 MAC snapshot이 저장되지 않음 |
| 실패 원인 식별률 | 표준 원인 코드 정리 뒤 |
| 장애 감지 시간 MTTD | 외부 1분 프로브와 호출 체계 구축 뒤 |
| 사용성 세부 지표 (준비 시간, 오류율, 자가 해결률, 경고 이해율) | 사용자 시험에서 수집 |

## 15. 측정 구현 우선순위

### 1단계: 출시 전

- 방송 시작 시 대상 MAC snapshot과 요청·준비·재생·종료 시각 저장
- LIVE·FILE 실패 원인 코드 표준화
- API·MQTT·Icecast·DB·file volume 합성 상태 점검과 외부 uptime monitor
- 고객·마을·방송 유형별 KPI 집계 쿼리

### 2단계: 초기 운영 4주 안

- metric 저장소와 운영 dashboard
- incident 기록과 MTTR 집계
- nginx·AWS 실제 전송량 기반 비용 집계
- broker 재시작·TLS 재접속 부하 시험
- backup 복구 자동 점검과 월 1회 복구 훈련

### 3단계: 안정화 후

- 단말의 실제 오디오 출력 여부 telemetry 검토
- 관리자 과업별 funnel 분석
- 고객별 기준선을 반영한 SLO와 알림 threshold 조정

## 16. 운영 리뷰 주기

| 주기 | 확인 내용 | 결과 |
|---|---|---|
| 실시간 | 중대 사고, active 방송 이상, 전체 offline 급증 | 즉시 알림과 incident 대응 |
| 매일 | 방송 실패, 장기 offline, backup, 인증서·disk | 운영 점검과 담당자 배정 |
| 매주 | 성공률·지연·재접속·오류 상위 원인 | 개선 작업 우선순위 |
| 매월 | 전체 KPI·비용·SLO 위반·고객별 편차 | 월간 운영 보고와 목표 조정 |
| 분기 | 사용자 시험, 복구 훈련, 보안·권한 audit | 제품·운영 개선 계획 |

SLO를 변경할 때는 이전 기간의 값을 덮어쓰지 않는다. 적용 시작일과 변경 이유를 남겨 기간별 성과를 같은 기준으로 비교한다.
