# xWIFI 서비스 KPI와 SLO

기준일: 2026-09-06

관련 문서: [시스템 아키텍처](01_시스템_아키텍처.md) · [단말 연동](02_단말_연동_사양.md) · [데이터 모델](04_데이터_모델.md) · [프론트엔드 운영 화면](05_프론트엔드_운영.md) · [인프라와 운영](06_인프라_운영.md)

이 문서는 xWIFI의 제품 성과와 운영 품질을 같은 기준으로 판단하기 위한 현행 측정 규칙이다. 숫자는 초기 운영 목표이며, 실제 고객 회선과 단말 300대 규모의 기준 데이터를 4주 이상 모은 뒤 조정한다.

## 1. 지표 체계

| 구분 | 의미 | 이 문서에서의 예 |
|---|---|---|
| KPI | 제품과 운영이 달성해야 하는 핵심 결과 | 방송 재생 시작 성공률 |
| SLI | 결과를 계산하는 실제 측정값 | 성공 응답 단말 수 ÷ 대상 단말 수 |
| SLO | 내부 운영 목표 | 월간 99.0% 이상 |
| SLA | 고객과 계약한 보상·책임 기준 | 별도 계약에서 정하며 SLO와 동일시하지 않음 |

모든 비율은 원칙적으로 고객별·마을별·방송 유형별로 집계하고, 전체 평균만으로 특정 고객이나 마을의 장애를 가리지 않는다. 운영 대시보드는 최근 24시간, 7일, 30일 값을 제공하고 월간 리뷰에서는 30일 값을 기준으로 삼는다.

## 2. 최상위 목표

### 2.1 North Star

> 필요한 방송이 올바른 단말에 제시간에 끊김 없이 도달한 비율

다음 조건을 모두 만족한 대상 단말을 성공으로 센다.

1. 권한과 대상 계산이 정확했다.
2. 명령 후 정해진 시간 안에 재생 시작을 확인했다.
3. 방송 도중 중대한 끊김이나 오류가 없었다.
4. 종료 명령 후 정상 상태로 복귀했다.

현재 단말 데이터는 스피커의 물리적인 음압을 직접 측정하지 않는다. 따라서 서버에서 확인하는 `LIVE_READY`, `STATUS.state=LIVE`, `FILE_RESULT`, `LIVE_STATS`는 **재생 가능 상태와 소프트웨어 동작의 근사 지표**다. 실제 가청 여부는 표본 현장 점검 또는 향후 단말의 오디오 출력 감지 기능으로 별도 검증한다.

### 2.2 경영·운영 핵심 KPI

| 우선순위 | KPI | 계산 기준 | 초기 SLO |
|---:|---|---|---:|
| 1 | 방송 재생 시작 성공률 | 제한 시간 안에 재생 시작이 확인된 대상 단말 ÷ 시작 시점 대상 단말 | 99.0% 이상 |
| 2 | 긴급 방송 시작 시간 | 운영자가 시작을 누른 시점부터 대상 단말의 재생 시작 확인까지 | P95 10초 이하 |
| 3 | 방송 대상 정확도 | 의도한 대상 집합과 실제 명령 대상 집합이 일치한 방송 ÷ 전체 방송 | 100% |
| 4 | 운영 서비스 가용성 | 정상적인 로그인·방송 시작·방송 종료가 가능한 시간 ÷ 운영 시간 | 월 99.9% 이상 |
| 5 | 중대 방송 사고 | 오방송, 무권한 방송, 전체 방송 불능, 방송 종료 불능 | 월 0건 |

`P95`는 측정값의 95%가 해당 시간 이내라는 뜻이다. 성공률은 방송 건수뿐 아니라 대상 단말 수 기준으로도 함께 본다. 단말 1대 방송과 300대 방송을 같은 1건으로 계산하면 실제 영향도가 왜곡되기 때문이다.

## 3. 방송 품질 KPI

### 3.1 실시간 방송

| KPI | 정의 | 초기 SLO | 현재 측정 상태 |
|---|---|---:|---|
| 준비 성공률 | 제한 시간 안에 `LIVE_READY`를 보낸 단말 ÷ 대상 단말 | 99.5% 이상 | 부분 가능 |
| 재생 시작 성공률 | `STATUS.state=LIVE`가 확인된 단말 ÷ 대상 단말 | 99.0% 이상 | 부분 가능 |
| 방송 준비 시간 | 시작 요청부터 `LIVE_READY` 수신까지 | P95 8초 이하 | 보강 필요 |
| 재생 시작 시간 | 시작 요청부터 `STATUS.state=LIVE` 확인까지 | P95 10초 이하 | 보강 필요 |
| 무음·끊김 단말 비율 | 방송 중 장시간 무음 또는 재버퍼링이 감지된 단말 ÷ 재생 단말 | 0.5% 미만 | 근사 측정·보강 필요 |
| 일시 장애 회복률 | Icecast 일시 장애 후 재접속에 성공한 단말 ÷ 재접속 시도 단말 | 95% 이상 | 단말 사유 코드 보강 필요 |
| underrun 발생률 | underrun이 1회 이상 보고된 단말 ÷ 재생 단말 | 1.0% 미만 | `LIVE_STATS`로 가능 |
| 정상 종료 시간 | 운영자 종료 요청부터 대상 단말의 LIVE 이탈 확인까지 | P95 5초 이하 | 보강 필요 |
| 브라우저 업링크 실패율 | 시작된 ingest 중 비정상 종료된 세션 ÷ 전체 ingest 세션 | 0.2% 미만 | 서버 metric 필요 |

`LIVE_READY`는 오디오 출력 준비 완료를 뜻하지만 실제 방송 음성이 지속적으로 들렸다는 증거는 아니다. 운영 화면에서는 준비, 재생 확인, 방송 품질을 한 개의 성공 표시로 합치지 않고 단계별로 보여준다.

### 3.2 파일·TTS 방송

| KPI | 정의 | 초기 SLO | 현재 측정 상태 |
|---|---|---:|---|
| 파일 방송 성공률 | 다운로드·검증 성공 결과를 보낸 단말 ÷ 대상 단말 | 99.5% 이상 | 가능하나 대상 snapshot 필요 |
| 파일 재생 시작 시간 | 시작 요청부터 성공 `FILE_RESULT`까지 | P95 10초 이하 | 보강 필요 |
| 파일 검증 실패율 | hash·format 검증 실패 단말 ÷ 다운로드 시도 단말 | 0.05% 미만 | result code 표준화 필요 |
| 네트워크 다운로드 실패율 | network·timeout 실패 단말 ÷ 다운로드 시도 단말 | 0.5% 미만 | result code 표준화 필요 |
| 저장 실패율 | 단말 저장 실패 건 ÷ 저장 요청 단말 | 0.5% 미만 | result code 표준화 필요 |
| 파일 방송 종료 시간 | 종료 요청부터 재생 종료 확인까지 | P95 10초 이하 | 종료 확인 보강 필요 |

TTS 방송도 생성된 MP3를 파일 방송하는 구조이므로 전달 품질은 파일 방송 KPI에 포함한다. TTS 합성 자체의 성공률과 생성 시간은 외부 서비스 품질 지표로 별도 집계한다.

broker 재시작 시 모든 단말이 동시에 TLS handshake를 시도하면 서버와 회선에 순간 부하가 집중된다. 단말 재접속 지터를 적용하고, 재시작 후 시간대별 연결 시도 수·성공률·복구 P95를 함께 확인한다.

## 5. 대상·권한·안전 KPI

이 영역은 평균 개선이 아니라 사고 0건을 목표로 한다.

| KPI | 초기 SLO | 판정 기준 |
|---|---:|---|
| 오방송 | 0건 | 선택하지 않은 마을·구역·단말에 명령 또는 오디오 전달 |
| 권한 범위 위반 | 0건 | `village_admin`이 담당 밖 자원 조회·제어 |
| retained 명령 사고 | 0건 | CONFIG 외 방송 명령이 retained되어 재접속 단말에서 실행 |
| 중복 방송 충돌 | 0건 | 정책상 허용되지 않은 동시 작업이 같은 단말에서 경합 |
| 방송 대상 snapshot 보존율 | 100% | 시작 당시 계산된 대상 MAC 전체를 감사 가능하게 저장 |
| 실패 원인 식별률 | 95% 이상 | 실패 단말 중 표준 원인 코드가 남은 단말 비율 |
| 실행자 제어 가시성 | 100% | 권한 있는 실행자가 자신이 시작한 방송을 조회·종료 가능 |

현재 `broadcast_events.expected_count`와 응답한 `device_events`만으로는 시작 당시 전체 대상 MAC을 복원할 수 없다. 대상 snapshot 100% KPI를 달성하려면 별도 snapshot 저장 구조가 필요하다.

현재 `village_admin`이 `device` 또는 `zone` 범위로 시작한 방송이 active/detail/stop 권한 검사에서 숨겨질 수 있다. 이 결함을 해소하기 전에는 해당 관리자의 방송 대상을 마을 범위로 제한하거나 `super_admin`이 제어한다.

## 6. 관리자 사용성 KPI

주요 사용자는 컴퓨터에 익숙하지 않은 이장과 지자체 관리자다. 기능 수보다 실수 없이 끝까지 수행하는 비율을 우선한다.

| KPI | 정의 | 초기 SLO |
|---|---|---:|
| 첫 시도 방송 성공률 | 별도 도움 없이 첫 시도에 올바른 대상 방송을 완료한 사용자 ÷ 시험 사용자 | 95% 이상 |
| 일반 방송 준비 시간 | 로그인 후 대상·파일을 정하고 시작하기까지 | 중앙값 60초 이하 |
| 긴급 실시간 방송 준비 시간 | 로그인 후 마이크 방송 시작 요청까지 | 중앙값 30초 이하 |
| 단말 등록 성공률 | 등록 절차를 시작해 정상 등록까지 완료한 비율 | 95% 이상 |
| 단말 등록 시간 | QR 또는 수동 등록 시작부터 완료까지 | 중앙값 5분 이하 |
| 취소·입력 오류율 | 사용자 오류로 중단되거나 재입력한 작업 ÷ 시작한 작업 | 3% 미만 |
| 방송 100건당 지원 문의 | 방송 조작 때문에 접수된 문의 수 | 2건 미만 |
| 자가 해결률 | 화면 안내만으로 해결한 일반 오류 ÷ 일반 오류 | 80% 이상 |
| 중요 경고 이해율 | 오방송 방지 확인 화면에서 대상과 영향을 정확히 답한 시험 사용자 비율 | 90% 이상 |

사용성 지표는 로그만으로 완성되지 않는다. 분기마다 대표 사용자 5명 이상을 대상으로 마을 방송, 전체 방송, 방송 중지, 오프라인 단말 확인, 단말 등록 과제를 관찰한다.

| KPI | 정의 | 초기 SLO |
|---|---|---:|
| API 가용성 | 정상 API 응답 가능 시간 ÷ 전체 운영 시간 | 월 99.9% 이상 |
| 서버 오류율 | HTTP 5xx 응답 ÷ 전체 API 응답 | 0.1% 미만 |
| 주요 API 응답 시간 | 로그인·대시보드·대상 조회·방송 요청의 서버 처리 시간 | P95 500ms 이하 |
| 대시보드 상태 신선도 | 마지막 단말 상태가 화면에 반영되기까지 | 정상 설정에서 7초 이하 |
| MQTT 이벤트 저장 지연 | broker 수신부터 DB 저장 완료까지 | P95 2초 이하 |
| 고아 방송 작업 | 재시작 상황을 제외하고 종료·실패 판정 없이 남은 active 작업 | 0건 |
| 장애 감지 시간 MTTD | 장애 발생부터 운영 알림까지 | 2분 이하 |
| 평균 복구 시간 MTTR | 장애 인지부터 핵심 방송 기능 복구까지 | 30분 이하 |
| 인증서 만료 사전 알림 | 만료까지 남은 기간 | 최소 20일 전에 알림 |
| 디스크 사용률 | 파일 보관 volume 사용률 | 80% 미만 |

서비스 가용성은 단순 `/health` 응답만으로 계산하지 않는다. DB 연결, MQTT publish, Icecast source 생성, 파일 volume 접근을 포함하는 합성 점검을 별도로 운용한다.

## 8. 백업과 복구 KPI

| KPI | 초기 SLO |
|---|---:|
| RDS 자동 backup·PITR 활성화율 | 운영 고객 100% |
| 파일 volume snapshot 성공률 | 예약 snapshot 100% |
| 최신 유효 backup 나이 | 24시간 이하 |
| 정기 복구 시험 성공률 | 100% |
| RPO | 최대 24시간, RDS PITR 구성 시 목표 5분 이하 |
| RTO | 핵심 서비스 1시간 이하 |
| DB·파일 정합성 | 복구 시험 표본 100% 일치 |

복구 시험은 backup job의 성공 표시가 아니라 격리 환경에 실제 DB와 파일을 복원하고 로그인·파일 조회·시험 방송 준비 단계까지 확인해야 성공으로 센다.

현재 `scripts/backup-db.sh`와 `scripts/healthcheck.sh`는 local PostgreSQL container를 전제로 한다. 기본 운영 구성인 RDS에서 이 지표를 신뢰하려면 RDS backup 상태, 복구 가능 시점, DB 연결 상태를 직접 확인하도록 수정해야 한다.

| 외부 평문 연결 | 0건 |
| Git·image·log의 secret 노출 | 0건 |
| 중요 보안 patch 반영 시간 | 공개 또는 확인 후 7일 이내 |
| 퇴직·권한 변경 계정 회수 | 요청 후 1영업일 이내 100% |

보안 지표는 차단된 시도와 실제 성공 사고를 나누어 집계한다. 공격 시도 수가 증가했다는 이유만으로 서비스 품질이 나빠졌다고 판정하지 않되, 차단 실패는 즉시 중대 사고로 분류한다.

## 10. 비용 KPI

| KPI | 계산식·용도 |
|---|---|
| 활성 단말당 월 비용 | 고객별 월 총 운영비 ÷ 해당 월 활성 단말 수 |
| 단말·방송 분당 비용 | 방송 관련 변동비 ÷ 실제 방송을 수신한 단말의 재생 시간 합계 |
| 전송량과 egress 비용 | 고객·마을·방송 유형별 실제 전송 byte와 cloud egress 비용 |
| 고객별 고정비 | EC2, RDS, EBS, domain, monitoring 등 방송량과 무관한 비용 |
| TTS 생성 단가 | TTS 요청 비용 ÷ 생성 성공 건수 |
| TTS cache 적중률 | 기존 합성 파일을 재사용한 요청 ÷ 전체 TTS 요청, 초기 목표 50% 이상 |
| 예산 오차율 | 실제 월 비용 ÷ 계획 월 비용, 초기 관리 범위 90~110% |
| 유휴 자원 비용 | 사용되지 않은 instance·volume·snapshot·IP 비용 |

현재 DB의 `bytes_estimated`는 실제 응답한 고유 단말 수를 기반으로 한 하한 추정치다. 응답하지 않은 단말의 전송량을 놓칠 수 있으므로 비용 정산과 egress KPI에는 nginx access log와 AWS 실제 사용량을 사용한다.

| 배포 장애 복구 시간 | 배포 장애 인지부터 이전 정상 버전 또는 수정 버전 복구까지 30분 이하 |

배포 횟수 자체를 목표로 무리하게 늘리지 않는다. 변경 실패율과 복구 시간을 함께 보며 작은 변경을 안전하게 자주 배포하는 능력을 평가한다.

## 13. 운영 대시보드의 기본 10개 지표

첫 화면에는 다음 10개만 상시 노출한다. 나머지는 상세 운영·월간 리뷰 화면에서 본다.

1. 방송 재생 시작 성공률
2. 긴급 방송 시작 시간 P95
3. 실시간 방송 무음·재접속 발생률
4. 파일 방송 성공률
5. 단말 온라인율과 24시간 이상 오프라인 수
6. CONFIG·자격 증명 일치율
7. 오방송·권한·보안 사고 수
8. 운영 서비스 가용성
9. 장애 평균 복구 시간
10. 활성 단말당 월 비용

등록 단말 수, 방송 횟수, TTS 생성 횟수는 규모와 이용량을 설명하는 보조 지표다. 값이 커지는 것 자체가 품질이나 사용자 가치 향상을 뜻하지 않으므로 핵심 KPI로 사용하지 않는다.

## 14. 측정 구현 우선순위

### 1단계: 출시 전 반드시 확보

- 방송 시작 시 대상 MAC snapshot과 요청·준비·재생·종료 시각 저장
- LIVE·FILE 실패 원인 코드 표준화
- API·MQTT·Icecast·DB·file volume 합성 상태 점검
- 고객·마을·방송 유형별 KPI 집계
- 오방송·권한 위반·중복 작업 감사 log와 즉시 알림

### 2단계: 초기 운영 4주 안에 확보

- Prometheus 또는 동등한 metric 저장소와 운영 dashboard
- MTTD·MTTR incident 기록
- nginx·AWS 실제 전송량 기반 비용 집계
- broker 재시작·TLS 재접속 부하 시험
- backup 복구 자동 점검과 월 1회 실제 복구 훈련

### 3단계: 운영 안정화 후 개선

- 단말의 실제 오디오 출력 여부를 확인할 수 있는 telemetry 검토
- 관리자 과업별 funnel과 사용자 오류 분석
- 회선·firmware·지역별 방송 품질 비교
- 고객별 기준선을 반영한 SLO와 알림 threshold 조정

## 15. 운영 리뷰 주기

| 주기 | 확인 내용 | 결과 |
|---|---|---|
| 실시간 | 중대 사고, active 방송 이상, 전체 offline 급증 | 즉시 알림과 incident 대응 |
| 매일 | 방송 실패, 장기 offline, backup, 인증서·disk | 운영 점검과 담당자 배정 |
| 매주 | 성공률·지연·재접속·오류 상위 원인 | 개선 작업 우선순위 |
| 매월 | 전체 KPI·비용·SLO 위반·고객별 편차 | 월간 운영 보고와 목표 조정 |
| 분기 | 사용자 시험, 복구 훈련, 보안·권한 audit | 제품·운영 개선 계획 |

SLO를 변경할 때는 이전 기간의 값을 덮어쓰지 않는다. 적용 시작일과 변경 이유를 남겨 기간별 성과를 같은 기준으로 비교할 수 있게 한다.
