# xWIFI 인프라와 운영

기준일: 2026-09-06

관련 문서: [시스템 아키텍처](01_시스템_아키텍처.md) · [데이터 모델](04_데이터_모델.md) · [단말 연동](02_단말_연동_사양.md)

이 문서는 고객 1곳에 xWIFI 운영 스택 1벌을 배포하는 기준이다. 실제 호스트명, IP, SSH key 경로, 비밀번호와 cloud account ID는 기록하지 않는다.

## 1. 운영 토폴로지

권장 기본 구성:

| 영역 | 구성 |
|---|---|
| Region | AWS 서울 |
| Compute | Ubuntu 24.04 LTS, x86 EC2 `t3.medium` 2 vCPU/4 GiB |
| App runtime | Docker Engine + Docker Compose |
| DB | RDS PostgreSQL 18 `db.t4g.micro`, Single-AZ, private |
| File/OS | gp3 EBS 50 GiB |
| Public address | Elastic IP + 단일 도메인 |
| TLS | Let's Encrypt full chain 1벌을 nginx와 Mosquitto가 공유 |
| Backup | RDS 자동 backup/PITR + EBS DLM snapshot |

위 사양은 약 300대 고객의 시작점이다. 3,000대까지의 연결 한도는 설정에 여유를 둔 수치이며 EC2·RDS sizing을 검증한 부하 시험 결과가 아니다. 고객별 실제 STATUS 주기, 동시 방송 수, 업로드 보관량, egress에 맞춰 조정한다.

RDS 없이 독립 설치할 때는 같은 Compose의 `local-db` profile을 사용하고 `DATABASE_URL`만 바꾼다. 온프레미스 이식 시에도 애플리케이션 코드는 유지하고 DB, backup, monitoring만 환경에 맞춘다.

## 2. Docker Compose 서비스

현재 `docker-compose.yml`은 다음 서비스와 volume을 정의한다.

| 서비스 | 컨테이너 | 역할 | 외부 공개 |
|---|---|---|---|
| `backend` | `xwifi-backend` | FastAPI, MQTT worker, scheduler, WSS ingest | nginx 경유만 |
| `frontend` | `xwifi-frontend-build` | React build 후 web volume에 복사하고 종료 | 없음 |
| `postgres` | `xwifi-postgres` | PostgreSQL 18, `local-db` profile | 기본 운영에서는 기동 안 함 |
| `mosquitto` | `xwifi-mosquitto` | MQTT broker와 단말 인증·ACL | TCP 8883 |
| `icecast` | `xwifi-icecast` | 실시간 audio fan-out | nginx `/live/` 경유 |
| `nginx` | `xwifi-nginx` | TLS, SPA, API/WSS/stream proxy, file sendfile | TCP 80, 443 |

named volume:

| volume | 데이터 | backup 필요 |
|---|---|---|
| `files` | upload·TTS·향후 OTA file | 예 |
| `web` | frontend build 결과 | 아니오, 재생성 가능 |
| `mqtt-dynamic` | backend가 생성한 passwd·ACL 전달 파일 | 아니오, DB에서 재생성 |
| `mosquitto-data` | broker persistence와 설치된 계정·ACL | 재생성 가능하나 retained 상태 점검 필요 |
| `pgdata` | local-db profile DB | local DB 사용 시 필수 |

호스트 bind mount:

- `infra/nginx/nginx.conf`
- `infra/mosquitto/config`
- `infra/mosquitto/entrypoint.sh`
- `infra/icecast/icecast.xml`
- `infra/certs`
- `infra/certbot-webroot`
- `infra/secrets`의 Google TTS credential

## 3. 네트워크와 방화벽

### 3.1 외부 포트

| 포트 | 용도 | 허용 주체 | 비고 |
|---:|---|---|---|
| 80/TCP | ACME HTTP-01, HTTPS redirect | 인터넷 | challenge 외 전부 443 redirect |
| 443/TCP | 관리자 UI·API·WSS·파일·Icecast | 인터넷 또는 운영 정책 범위 | TLS 1.2/1.3 |
| 8883/TCP | 단말 MQTTS | 설치 단말 회선 | TLS 1.2 이상 |
| 22/TCP | SSH | 관리자 고정 IP 또는 비활성 | 가능하면 SSM 사용 |
| 5432/TCP | RDS | EC2 security group만 | public access 금지 |

1883과 8000은 운영 security group과 호스트 port에서 외부 공개하지 않는다.

### 3.2 내부 경로

| 출발 | 목적지 | 주소 |
|---|---|---|
| backend | Mosquitto | `mosquitto:1883`, container network plaintext |
| backend | Icecast | `icecast:8000`, source PUT |
| nginx | backend | `backend:8000` |
| nginx | Icecast | `icecast:8000` |
| backend | RDS | private endpoint `:5432`, SSL required |

Docker 내부 평문은 EC2 밖으로 노출되지 않는다. RDS 연결 문자열에는 SSL 요구 옵션을 사용한다.

## 4. nginx

nginx가 한 도메인의 모든 public path를 처리한다.

| Path | 처리 |
|---|---|
| `/` | web volume의 SPA, 없는 path는 `index.html` |
| `/api/*` | FastAPI reverse proxy |
| `/health` | FastAPI reverse proxy |
| `/ingest` | WebSocket upgrade, buffering off, read timeout 1시간 |
| `/dl/*` | FastAPI token 검증 |
| `/_files/*` | internal only, X-Accel-Redirect로 file volume sendfile |
| `/live/*` | Icecast proxy, buffering off, read timeout 24시간 |
| `/.well-known/acme-challenge/*` | certbot webroot |

현재 설정:

- `worker_processes auto`
- `worker_rlimit_nofile 65536`
- worker당 `worker_connections 16384`
- backend upstream keepalive 64
- TLS 1.2·1.3, HSTS 1년
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: same-origin`
- server version 숨김
- 로그인 IP별 `10 requests/min`, burst 5
- `client_max_body_size 256m`

nginx body 상한이 크더라도 앱은 방송 MP3를 2.5 MiB, 600초로 다시 제한한다.

파일 download의 핵심은 백엔드가 token과 경로만 판정하고 nginx가 bytes를 보내는 것이다. `/_files/`는 외부에서 직접 접근할 수 없어야 하며, Range 요청도 nginx가 처리한다.

## 5. Mosquitto

### 5.1 listeners

- 1883: Docker 내부 backend 전용, 호스트 port mapping 없음
- 8883: 단말 전용 TLS, 호스트 공개
- 두 listener 모두 anonymous 금지
- 8883은 full-chain 인증서와 private key 사용
- 현재 `require_certificate false`; 단말 client certificate는 사용하지 않음

### 5.2 계정과 ACL 동기화

정본은 DB의 `devices.mqtt_password`와 `devices.village_id`다.

1. backend가 passwd와 ACL 전체를 임시 파일에 쓴 뒤 원자적으로 교체한다.
2. `mqtt-dynamic` 공유 volume에 `passwd.generated`, `aclfile.generated`가 생성된다.
3. Mosquitto entrypoint 감시 loop가 owner·permission을 맞춰 data volume에 설치한다.
4. Mosquitto에 SIGHUP을 보내 연결을 유지한 채 reload한다.

backend 기동 때와 단말 등록·삭제·credential·마을 변경 때 전체를 다시 생성한다. 부분 merge를 하지 않는다.

초기 `infra/mosquitto/config/aclfile`은 bootstrap seed일 뿐이며 backend가 뜬 뒤 generated ACL로 교체된다. 운영 확인은 repository seed가 아니라 `/mosquitto/data/aclfile`을 대상으로 해야 한다.

단말별 계정 전환이 끝난 운영 환경에서는 `MQTT_DEVICE_PASSWORD` 공유 credential을 설정하지 않는다. 값이 있으면 backend가 passwd 재생성 때 호환용 공유 계정을 남긴다.

### 5.3 용량·지속성

- container `nofile` soft/hard: 65536
- `max_queued_messages`: 200
- `max_inflight_messages`: 40
- persistence 활성
- autosave: 60초
- log: stdout notice

offline 단말에 QoS 1 명령을 무한 적재하지 않는다. 방송 명령은 만료·재생 방지를 위해 retained가 아니므로 장기간 offline 단말을 나중에 방송에 참여시키지 않는다.

브로커 재시작 시험에서는 단말 backoff 지터로 TLS 재접속이 시간에 분산되는지 확인한다.

## 6. Icecast

현재 운영값:

| 설정 | 값 |
|---|---:|
| clients | 4000 |
| sources | 64 |
| threadpool | 8 |
| queue-size | 16384 bytes |
| client-timeout | 30 sec |
| header-timeout | 15 sec |
| source-timeout | 60 sec |
| burst-on-connect | 0 |
| burst-size | 0 |

source password와 admin password는 서로 다른 secret을 사용한다. mount는 public directory에 노출하지 않는다.

세션마다 `/live/<job_id>` mount를 사용한다. 여러 마을이 같은 방송 요청에 포함되면 하나의 mount를 공유하고, 서로 다른 방송은 별도 mount를 가진다.

`LIVE_UPLINK_GRACE_SEC`는 `source-timeout`보다 작아야 한다. 현재 기본은 30초와 60초다. 업링크가 시작되지 않은 무음 session을 backend가 먼저 종료할 시간을 확보한다.

단말은 Icecast-only 단절 때 약 6.5초 범위에서 세 번 재접속할 수 있다. 방송 중 source 재시작은 같은 mount를 그 안에 복구하지 못하면 단말 결과 실패로 이어진다. 계획된 maintenance는 진행 중 방송이 없을 때 수행한다.

## 7. PostgreSQL과 파일 저장

### 7.1 RDS 기본

- PostgreSQL 18
- public access 비활성
- EC2 security group에서만 5432 허용
- storage encryption 활성
- 자동 backup 7일 이상
- point-in-time recovery 활성
- 정기 maintenance window와 backup window가 마을 방송 시간과 겹치지 않게 설정
- application `DATABASE_URL`은 TLS/SSL 요구

Single-AZ는 가용성보다 비용을 우선한 기본안이다. 복구 시간 목표가 짧아지면 Multi-AZ를 검토한다.

### 7.2 local DB profile

RDS가 없는 설치에서는:

```text
docker compose --profile local-db up -d
```

PostgreSQL 18 image는 volume을 `/var/lib/postgresql`에 mount한다. `pgdata` volume backup과 host 장애 복구를 직접 책임져야 한다.

### 7.3 파일 저장

컨테이너 경로 기본값:

```text
/var/lib/iotradio/files/
├─ upload/
├─ tts/
└─ update/
```

DB `files.storage_path`에는 위 root 기준 상대 경로만 저장한다. volume은 backend에서 read/write, nginx에서 read-only다.

운영 backup은 DB만으로 충분하지 않다. `files` volume이 사라지면 메타데이터는 남아도 방송할 bytes가 없다. EBS DLM snapshot 또는 검증된 object storage sync를 사용하고 복구 리허설에서 DB와 같은 시점의 파일을 함께 확인한다.

## 8. 환경 변수와 secret

`.env.prod.example`을 기준으로 실제 `.env`를 만들며 `.env`는 Git에 커밋하지 않는다.

| 범주 | 주요 값 |
|---|---|
| app | `APP_ENV`, `LOG_LEVEL`, `PUBLIC_BASE_URL`, `CORS_ORIGINS` |
| DB | `DATABASE_URL`; local profile은 `POSTGRES_*` |
| auth | `JWT_SECRET`, `JWT_EXPIRE_MINUTES` |
| MQTT | `MQTT_HOST`, `MQTT_PORT`, `MQTT_USERNAME`, `MQTT_PASSWORD`, `MQTT_TLS`, `MQTT_TOPIC_ROOT` |
| Icecast | 내부 host/port, source/admin password, public base URL |
| Kakao | REST API secret key, JavaScript public key |
| TTS | engine, Google application credential path |
| file | `FILE_ROOT`, download·OTA token TTL |
| operation | online threshold, CONFIG reconcile, STATUS flush, live uplink grace |
| alert | Slack webhook |

운영 필수:

- `APP_ENV=prod`
- 최소 32바이트의 무작위 `JWT_SECRET`
- `PUBLIC_BASE_URL`과 `ICECAST_PUBLIC_BASE_URL`은 HTTPS public origin
- 서로 다른 MQTT, Icecast source, Icecast admin password
- RDS URL에서 SSL 요구
- Kakao key의 허용 도메인 제한
- credential JSON과 `.env`, 인증서 private key의 별도 안전 backup

private key는 `root:1883`, mode 640으로 nginx master와 Mosquitto가 읽게 한다. public certificate는 644로 둘 수 있다.

## 9. TLS 인증서

최초 구축:

```text
sudo bash scripts/setup-certs.sh <domain> <operator-email>
```

script는 다음을 수행한다.

1. DNS가 서버 public IP를 가리키는지 확인한다.
2. nginx 실행 여부에 따라 webroot 또는 standalone HTTP-01로 발급한다.
3. Let's Encrypt fullchain과 private key를 `infra/certs`로 복사한다.
4. container가 읽을 owner·permission을 적용한다.
5. certbot deploy hook을 등록해 갱신 후 nginx와 Mosquitto를 재시작한다.

검증:

```text
sudo certbot renew --dry-run
```

인증서 갱신은 MQTT 연결 재수립을 유발할 수 있다. 단말 재접속 지터가 동작하는지 확인하고 가능하면 방송 시간 밖에 수행한다.

## 10. 초기 구축 절차

1. AWS root MFA, 운영 IAM/SSM 역할, Budget alert를 설정한다.
2. VPC, EC2·RDS security group, Elastic IP를 만든다.
3. PostgreSQL 18 RDS를 private로 생성하고 backup/PITR를 켠다.
4. EC2와 encrypted gp3 volume을 만들고 Docker를 설치한다.
5. repository를 clone하고 별도 보관한 `.env`와 cloud credentials를 설치한다.
6. MQTT bootstrap 계정 파일을 만들고 per-device generated account가 덮어쓰는지 확인한다.
7. Google TTS credential을 제한된 권한으로 설치한다.
8. DNS를 연결하고 TLS 인증서를 발급한다.
9. migration, 초기 `super_admin`, frontend build, stack 기동을 수행한다.
10. `/health`에서 DB와 MQTT가 true인지 확인한다.
11. 단말 한 대로 MQTTS, CONFIG, FILE Range download, LIVE HTTPS를 끝까지 시험한다.
12. RDS backup, EBS snapshot, 외부 uptime, host/container alert를 설정한다.
13. EC2 소실을 가정한 복구 리허설을 수행한다.

운영 서버 직접 접근은 담당자 또는 명시적으로 권한을 받은 작업자만 수행한다.

## 11. CI

`.github/workflows/ci.yml`은 모든 branch push와 pull request에서 실행되고 같은 branch의 이전 실행을 취소한다.

| Job | 검증 |
|---|---|
| backend | Python 3.12, dependency install, Ruff, Pytest, pyproject/Dockerfile dependency sync |
| migration | PostgreSQL 18에서 upgrade head → downgrade base → upgrade head |
| frontend | Node 22, `npm ci`, typecheck를 포함한 production build |
| stack | test TLS·MQTT secret 준비, 전체 Compose 기동, migration·demo seed, HTTPS health |

CI stack은 RDS가 없으므로 `local-db` profile을 사용한다. CI 통과는 실제 단말, 외부 DNS, certificate chain, WAN 지터, AWS backup을 검증하지 않는다.

현재 continuous deployment는 구축되어 있지 않다. GHCR image publish, 승인 environment, SSM 배포는 계획 상태다.

## 12. 배포

표준 명령:

```text
bash scripts/deploy.sh
```

옵션:

| 옵션 | 용도 |
|---|---|
| `--no-pull` | 현재 checkout으로 재build·배포 |
| `--force` | 진행 방송이 있어도 배포; 방송 중단을 명시적으로 감수할 때만 |

script 순서:

1. `.env` 존재 확인
2. 현재 commit 기록
3. 진행 중 방송 count 확인; 있으면 기본 중단
4. `git pull --ff-only`
5. image build
6. 현재 서비스 교체 전에 `alembic upgrade head`
7. Compose update
8. nginx restart
9. 최대 약 30초 동안 HTTPS health 확인

nginx는 upstream 주소를 시작 시 해석하므로 backend container 교체 뒤 함께 restart한다.

배포 전 checklist:

- [ ] CI 전체 통과
- [ ] Git working tree clean, 배포 commit 확인
- [ ] 진행 중 방송 없음
- [ ] DB migration data 영향 검토
- [ ] RDS snapshot 또는 최신 backup 확인
- [ ] file volume snapshot 확인
- [ ] certificate와 disk 여유 확인
- [ ] 사용자 공지·rollback 담당자 확보

배포 후 checklist:

- [ ] `/health`: status ok, database true, mqtt true
- [ ] `docker compose ps`: 필요한 서비스 정상
- [ ] backend·Mosquitto·Icecast·nginx error log 확인
- [ ] 로그인·대시보드 확인
- [ ] 단말 STATUS와 CONFIG version 확인
- [ ] 개별 단말 짧은 파일 방송 확인
- [ ] 필요한 경우 제한 대상 live 방송 확인

rollback은 application commit만 되돌리는 것으로 끝나지 않을 수 있다. 새 migration이 옛 code와 호환되지 않으면 먼저 검증된 downgrade 또는 forward fix 계획이 필요하다. 파일과 DB를 무조건 이전 시점으로 복구하면 신규 데이터가 사라지므로 incident 책임자가 범위를 결정한다.

## 13. 백업과 복구

### 13.1 RDS 운영

주 backup 경로:

- RDS 자동 snapshot 7일 이상
- PITR 활성화
- 주요 배포 전 manual snapshot
- file EBS DLM 일일 snapshot 7일 이상
- repository와 별도로 `.env`, TTS credential, DNS·cloud 설정 기록을 보안 저장소에 보관

`scripts/backup-db.sh`는 기본적으로 Compose의 `postgres` service에서 `pg_dump`를 실행한다. 따라서 **RDS 기본 배포에서는 그대로 동작하지 않는다.** RDS는 managed backup/PITR를 우선 사용하고, 논리 dump가 추가로 필요하면 RDS endpoint에 맞는 별도 job 또는 client container로 수정·검증한 뒤 사용한다.

### 13.2 local-db 운영

`scripts/backup-db.sh`:

- `pg_dump --clean --if-exists`
- gzip 압축
- 최소 크기, `gzip -t` 무결성, `CREATE TABLE` 포함 여부 확인
- 기본 local 7일 보관
- `S3_BUCKET`이 있으면 추가 upload
- 실패하면 그 자리에서 `SLACK_WEBHOOK_URL`로 알린다

`CREATE TABLE` 확인은 `pipefail`을 끈 subshell에서 한다. `grep -q`가 첫 일치에서 파이프를 닫으면 dump를 쓰고 있던 `zcat`이 SIGPIPE로 죽고, `pipefail`이 켜져 있으면 정상 백업이 실패로 판정된다. dump가 파이프 buffer 64KiB를 넘긴 시점부터 매일 조용히 실패한다.

`scripts/restore-db.sh`:

- backup 목록 또는 최신/지정 파일 선택
- `yes` 명시 확인
- 복구 전 현재 DB safety dump
- backend 정지
- psql 복구
- 마을·단말·계정·방송 count 확인
- backend와 nginx 재기동

복구는 파괴적이다. 실제 backup copy로 별도 환경에서 정기 복구 시험을 해야 한다.

### 13.3 전체 복구 리허설

EC2 소실을 가정한다.

1. 새 EC2·보안 그룹 준비
2. repository checkout
3. secret store에서 `.env`와 credential 복원
4. RDS snapshot/PITR 복원 또는 기존 RDS 연결
5. file EBS snapshot을 새 volume으로 복원
6. TLS 재발급 또는 안전하게 보관한 인증서 설치
7. Compose와 migration 기동
8. DB count, 파일 실제 존재, MQTT account 재생성 확인
9. 단말 한 대 end-to-end 시험

복구 목표 시간과 허용 데이터 손실량은 고객 계약에 맞춰 별도 수치로 확정한다.

## 14. 모니터링과 알림

### 14.1 앱 내부 health

`GET /health`는 DB와 MQTT를 확인한다. 외부 uptime monitor가 1분 주기로 HTTPS에서 호출해야 한다. host가 죽으면 host 내부 script도 실행되지 않으므로 외부 감시가 필수다.

### 14.2 host 점검 script

`scripts/healthcheck.sh`는 다음을 점검하고 문제가 있을 때만 Slack으로 보낸다.

- root disk 사용률: 기본 경고 80%
- memory: 기본 경고 85%
- container 상태
- app health
- 최근 DB dump: 기본 30시간 이내
- certificate 만료: 기본 20일 전 경고

백업 최신성은 사후 감시다. 실패 시점의 알림은 `scripts/backup-db.sh`가 직접 보낸다.

현재 script의 `EXPECTED` 목록에는 `xwifi-postgres`가 항상 포함되어 있다. RDS 배포에서는 local postgres container가 없으므로 그대로 실행하면 오탐이 발생한다. 또한 backup 최신성도 local `pg_dump`를 전제로 한다. RDS 운영 전에 profile에 따라 예상 container와 RDS snapshot 상태를 보도록 script를 보완해야 한다.

### 14.3 cloud alarms

최소 권장:

- EC2 `StatusCheckFailed`
- EC2 CPU 80% 15분
- disk 80%, memory 85%: CloudWatch Agent 필요
- RDS free storage 2 GiB 이하
- RDS CPU, connection, latency
- external HTTPS health failure
- certificate 만료
- daily backup/snapshot 실패 또는 지연
- Mosquitto connection 급감·인증 실패 증가
- Icecast listener/source 한도와 4xx/5xx 증가

Docker logs에는 rotation limit을 설정해 disk를 채우지 않게 한다. 현재 Compose에는 log rotation 설정이 없으므로 운영 host daemon 또는 service별 `logging` 설정으로 보강한다.

### 14.4 비용 보고

`scripts/cost-report.sh`는 EC2 instance role의 `ce:GetCostAndUsage`로 전날 service별 비용과 이번 달 누적·예상치를 조회해 Slack으로 전송한다. 이 script는 앱의 `daily_cost_summary`를 채우지 않는다.

Cost Explorer API 호출비와 Slack webhook secret을 고려하고, `--dry`로 출력부터 검증한다. 앱 내부 비용 화면을 구현하려면 별도 일별 집계 job과 환율·추정 egress 기준을 정해야 한다.

## 15. 장애 대응

### 15.1 단말 다수가 동시에 오프라인

1. 외부에서 8883 TCP와 certificate chain 확인
2. Mosquitto container·log·fd 사용량 확인
3. passwd·ACL generated 파일 설치와 reload 확인
4. server account MQTT 연결 확인
5. 단말이 지터를 포함해 재접속하는지 sample log 확인
6. broker 복구 후 STATUS가 다시 올라오는지 확인

브로커가 복구돼도 끊긴 방송은 자동 재개되지 않는다.

### 15.2 마을 방송만 안 됨

1. 개별 단말 명령이 동작하는지 확인
2. DB의 `village_id`, `village_code` 확인
3. 단말 STATUS의 `village_id`, `config_version` 확인
4. retained device CONFIG 확인
5. generated ACL에 정확한 village topic이 있는지 확인
6. CONFIG·account resync 후 다시 시험

### 15.3 LIVE_READY는 오지만 소리가 안 남

1. `STATUS.live`가 PLAYING인지 RECONNECTING인지 확인
2. 브라우저 `uplink_connected`와 전송 byte 확인
3. Icecast source와 mount 존재 확인
4. public `stream_url`의 HTTPS·path·certificate 확인
5. nginx `/live/` proxy와 Icecast log 확인
6. LIVE_STATS의 buffer와 underrun 확인

READY는 P4 준비 신호일 뿐 stream 재생 성공 신호가 아니다.

### 15.4 파일 다운로드 실패

1. FILE_RESULT `code`, `last_offset` 확인
2. token TTL과 DB token 행 확인
3. 파일 DB 메타와 volume 실파일 존재 확인
4. nginx X-Accel internal path 확인
5. HEAD/GET와 Range 206 동작 확인
6. size·SHA-256·확장자·2.5 MiB 한계 확인

### 15.5 DB 또는 파일 손실

쓰기 중지 → 피해 범위와 복구 시점 선택 → 새 환경에 복원 시험 → count·참조·실파일 검증 → 제한된 단말 방송 시험 → 서비스 개방 순서로 진행한다. 검증 없이 운영 DB 위에 바로 restore하지 않는다.

## 16. 용량 검증 항목

운영 전 최소 부하 시험:

- MQTTS 3,000 동시 연결과 broker restart 재접속 분산
- STATUS 30초 주기에서 backend buffer와 RDS write량
- 3,000대 `/dl` 동시 Range download와 nginx fd·network
- 3,000 listener live stream과 Icecast clients·nginx upstream fd
- 64 source 한도 내 동시 서로 다른 방송 수
- live 30분 이상에서 end-to-end delay, underrun, reconnect
- TTS 동시 요청과 외부 API quota
- disk 증가율: 파일함, container log, Mosquitto persistence
- backup 중 DB·방송 영향과 실제 restore 시간

부하 시험 결과에 따라 EC2 network·CPU·memory, RDS class/IOPS, Icecast·nginx 한도와 STATUS 주기를 조정한다.
