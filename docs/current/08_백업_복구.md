# xWIFI 백업과 복구

기준일: 2026-10-12 (문제점 70번 ⑥)

관련 문서: [인프라와 운영](06_인프라_운영.md) §7·§13 · [공공 납품 요건](09_공공_납품_요건.md)

이 문서는 운영 서버 한 벌을 무엇으로 백업하고, 사고 유형별로 어떻게 되돌리는지 적은 절차서다. 스크립트가 해 주는 일과 사람이 해야 하는 일을 구분해 적었고, 스크립트가 다루지 않는 단계는 **수동**으로 표시했다. 실제 버킷 이름, 호스트, 비밀번호는 적지 않는다.

## 1. 무엇을 어디에 백업하나

| 대상 | 내용 | 백업 수단 | 비고 |
|---|---|---|---|
| DB (RDS 구성, 기본) | 마을·단말·계정·방송 기록·스케줄·파일 메타·단말별 MQTT 비밀번호 | RDS 자동 백업 7일 이상 + PITR, 주요 배포 전 수동 스냅샷 | 설정은 AWS 콘솔에서 **수동**. `backup-db.sh`·`restore-db.sh`는 RDS에서 동작하지 않는다(compose의 `postgres` 컨테이너 안에서 `pg_dump`/`psql`을 실행하기 때문) |
| DB (local-db 구성) | 위와 같음, `pgdata` 볼륨 | `scripts/backup-db.sh` 일일 덤프 → `~/db-backups/xwifi-<날짜-시각>.sql.gz`, `S3_BUCKET` 지정 시 S3 업로드 | 온프레미스·RDS 없는 설치 |
| `files` 볼륨 | 업로드 MP3, TTS 결과, OTA 패키지 | EBS DLM 일일 스냅샷 7일 이상 | 볼륨은 루트 EBS의 Docker 영역에 있다. DLM 정책 설정은 **수동** |
| `.env` | DB 접속, JWT, MQTT·Icecast 비밀번호, Kakao 키, Slack webhook | 비밀번호 관리자 등 별도 보안 저장소 | **수동**. 없으면 서버가 사라졌을 때 복구 불가 |
| `infra/secrets/google-tts.json` | Google TTS 자격증명 | 별도 보안 저장소 | **수동**. 다시 받으려면 gcloud 로그인 후 `scripts/setup-tts-credentials.sh` |
| `infra/certs/server.crt`, `server.key` | TLS 인증서·개인키(nginx와 Mosquitto 공용) | 별도 보안 저장소, 또는 재발급 | **수동**. Let's Encrypt는 `scripts/setup-certs.sh`로 재발급 가능 |
| `infra/nginx/admin-allow.d/local.conf` | 관리자 접속 허용 IP | 별도 보관(저장소에 올리지 않음) | **수동**. 없으면 제한 없이(누구나 접속) 뜬다 — 복구 때 반드시 되돌린다 |
| `infra/mosquitto/config/passwd` | MQTT 서버 계정(부트스트랩) | 별도 보관 | **수동**. 없으면 `scripts/setup-mqtt-users.sh`로 다시 만들고 `.env`의 `MQTT_PASSWORD`를 맞춘다. 단말별 계정은 DB가 정본이라 백엔드 기동 때 재생성된다 |
| crontab | `backup-db.sh`·`healthcheck.sh`·`cost-report.sh` 등록 | `crontab -l` 출력 보관 | **수동** |
| 재생성 가능 | `web`(프론트 빌드), `mqtt-dynamic`, `mosquitto-data` | 백업 안 함 | 배포·기동 때 다시 만들어진다 |

EBS 스냅샷에는 루트 볼륨 전체가 들어가므로 저장소 디렉터리의 `.env`, 인증서, `admin-allow.d/local.conf`, 로컬 덤프도 함께 담긴다. 그래도 계정이나 리전이 통째로 사고 나는 경우에 대비해 비밀값은 AWS 밖에 따로 둔다.

DB를 EBS 스냅샷으로만 백업하지 않는 이유: 돌아가는 Postgres의 디스크 스냅샷은 전원을 뽑은 상태와 같아 복구가 보장되지 않는다. DB는 RDS 백업 또는 `pg_dump`가 맡고, EBS 스냅샷은 방송 파일용이다.

## 2. 일정과 보존

| 항목 | 주기 | 보존 | 누가 돌리나 |
|---|---|---|---|
| RDS 자동 백업 | 매일(백업 창) + 트랜잭션 로그 상시 | 7일 이상 | AWS. 백업 창은 방송 시간과 겹치지 않게 **수동** 설정 |
| RDS 수동 스냅샷 | 주요 배포·마이그레이션 전 | 직접 지울 때까지 | **수동** |
| EBS DLM 스냅샷 | 매일 | 7일 이상 | AWS DLM 정책 |
| `backup-db.sh` (local-db) | 매일 1회 cron | 로컬 `KEEP_DAYS`(기본 7일), S3는 버킷 수명주기 정책 | cron. 등록은 **수동** |
| `healthcheck.sh` | 매일 cron(`--always` 권장) | — | local-db면 최신 덤프가 30시간(`BACKUP_MAX_AGE_H`) 넘으면 Slack 경고. RDS면 백업 점검을 건너뛴다 |

`backup-db.sh`가 읽는 환경 변수(셸 환경에서 읽는다 — `.env`가 아니다):

| 변수 | 기본값 | 의미 |
|---|---|---|
| `BACKUP_DIR` | `$HOME/db-backups` | 덤프 저장 위치 |
| `KEEP_DAYS` | `7` | 이보다 오래된 `xwifi-*.sql.gz` 삭제 |
| `S3_BUCKET` | 비어 있음 | 예: `s3://<버킷>/db`. 비우면 로컬에만 보관 |
| `DB_SERVICE` | `postgres` | compose 서비스 이름 |

cron 등록 예(EC2 기본 UTC 기준, 03:00 KST):

```bash
( crontab -l 2>/dev/null; echo '0 18 * * * cd ~/xwifi-server && S3_BUCKET=s3://<버킷>/db bash scripts/backup-db.sh >> ~/backup.log 2>&1' ) | crontab -
```

`backup-db.sh`는 덤프 뒤 최소 크기, `gzip -t`, `CREATE TABLE` 포함 여부를 확인하고, 실패하면 그 자리에서 `.env`의 `SLACK_WEBHOOK_URL`로 알린다. S3 업로드만 실패하면 로컬 사본을 남기고 노란 경고를 보낸다.

주의: `restore-db.sh`가 복구 직전에 만드는 `before-restore-*.sql.gz`는 정리 대상 패턴(`xwifi-*.sql.gz`)이 아니어서 자동으로 지워지지 않는다. 복구가 끝나 확인되면 **수동**으로 정리한다.

데이터 손실 범위(대략): RDS PITR은 보통 최근 수 분 전까지, local-db 덤프와 `files` 스냅샷은 최대 하루. 목표 복구 시간·허용 손실량은 고객 계약에 맞춰 따로 정한다.

## 3. 복구 시나리오

공통 원칙: 진행 중인 방송이 없는지 먼저 본다(복구 중 방송은 끊기고 단말은 스스로 재개하지 않는다). 운영 DB 위에 검증 없이 바로 덮어쓰지 않는다. 복구 범위와 시점은 사고 책임자가 정한다.

### a. DB에서 행을 잘못 지우거나 고쳤다

**RDS 구성 — PITR (전부 수동)**

1. 사고 시각을 확정한다(방송 기록, 로그인 기록, 백엔드 로그 `docker compose logs backend`).
2. RDS 콘솔에서 "특정 시점으로 복원"으로 사고 직전 시각의 **새 인스턴스**를 만든다. 기존 인스턴스는 건드리지 않는다.
3. 둘 중 하나를 고른다.
   - 일부 행만 되살리기: 새 인스턴스에서 필요한 테이블·행만 꺼내 운영 DB에 넣는다. 호스트에 Postgres 클라이언트가 없으므로 `postgres:18-alpine` 컨테이너로 `pg_dump`/`psql`을 실행한다. 참조 관계(마을→단말, 계정→담당 마을)를 확인하며 넣는다.
   - 통째로 되돌리기: 사고 이후 새로 생긴 데이터를 포기하는 경우만. `.env`의 `DATABASE_URL` 호스트를 새 인스턴스 엔드포인트로 바꾸고 `bash scripts/deploy.sh --no-pull`.
4. §5 확인 절차를 수행한다. 끝나면 쓰지 않는 복원 인스턴스를 지운다(과금).

**local-db 구성 — restore-db.sh**

```bash
bash scripts/restore-db.sh --list               # 백업 목록
bash scripts/restore-db.sh                      # 가장 최근 백업으로
bash scripts/restore-db.sh ~/db-backups/xwifi-<날짜-시각>.sql.gz
```

스크립트가 하는 일: `yes` 입력 확인 → 현재 DB를 `before-restore-*.sql.gz`로 저장 → `backend` 정지 → 덤프 적용 → 마을·단말·계정·방송이력 건수 출력 → `backend` 시작, `nginx` 재시작. 실패하면 되돌리는 명령(`restore-db.sh <safety 파일>`)을 출력한다.

`restore-db.sh`는 DB 전체를 그 시점으로 되돌린다. 일부 행만 되살리려면 덤프를 별도 Postgres 컨테이너에 풀어 필요한 행만 옮긴다(**수동**).

### b. EC2를 잃었다 (RDS·스냅샷은 남아 있음)

1. 같은 리전에 새 EC2를 준비한다(**수동**). 둘 중 하나:
   - 쉬운 길: 최신 EBS 스냅샷에서 볼륨을 만들어 새 EC2의 루트로 쓴다. 저장소, `.env`, 인증서, `files` 볼륨, 로컬 덤프가 스냅샷 시점 그대로 돌아온다.
   - 새로 설치: Ubuntu + Docker 설치 후 저장소 clone, 보안 저장소에서 `.env`, `infra/secrets/google-tts.json`, `infra/certs/*`, `infra/nginx/admin-allow.d/local.conf`, `infra/mosquitto/config/passwd`를 제자리에 둔다. 스냅샷 볼륨을 보조 디스크로 붙여 `files` 볼륨 데이터(`docker volume ls`로 이름 확인, 보통 `xwifi-server_files`)만 새 볼륨으로 복사한다.
2. 보안 그룹: 새 EC2에 443·8883(·80) 인바운드, RDS 보안 그룹에 새 EC2의 5432 접근을 허용한다(**수동**).
3. Elastic IP를 새 EC2로 옮긴다(**수동**). 단말에는 도메인이 주입돼 있으므로 DNS·EIP가 같으면 단말 쪽 조치는 없다.
4. DB: 기존 RDS가 살아 있으면 그대로 연결한다. RDS도 되돌려야 하면 a의 PITR로 새 인스턴스를 만들고 `DATABASE_URL`을 바꾼다. 파일 스냅샷 시각과 DB 시점을 가능한 한 맞춘다 — DB가 더 새로우면 "파일 메타는 있는데 실파일이 없는" 항목이 생긴다.
5. 인증서가 없으면 `sudo bash scripts/setup-certs.sh <도메인> <운영자 이메일>`로 재발급한다.
6. `bash scripts/deploy.sh --no-pull` — 이미지 빌드, 마이그레이션, 기동, nginx 재시작, `/health` 확인까지 한다.
7. crontab을 다시 등록한다(**수동**).
8. §5 확인 절차를 수행한다.

### c. local-db(온프레미스) 설치에 덤프를 복원한다

새 서버(기관 전산실 등)를 RDS 없이 세우고 기존 데이터를 옮기는 경우다.

1. 원본 덤프를 준비한다.
   - 원본이 local-db면 `backup-db.sh`가 만든 `xwifi-*.sql.gz`를 쓴다.
   - 원본이 RDS면 스크립트가 없다(**수동**). `postgres:18-alpine` 컨테이너로 RDS에 `pg_dump --clean --if-exists`를 실행해 gzip으로 저장하고, 파일 이름을 `xwifi-<날짜-시각>.sql.gz` 형식으로 맞춘다(`restore-db.sh`가 이 패턴으로 찾는다). 이때 접속 문자열은 libpq 형식(`postgresql://…?sslmode=require`)이며 `.env`의 `postgresql+asyncpg://…?ssl=require`와 다르다.
2. 새 서버에 저장소(또는 오프라인 번들, [09 문서](09_공공_납품_요건.md) 참고)와 비밀 파일을 둔다.
3. `.env`를 local-db용으로 고친다.
   - `DATABASE_URL`의 호스트를 compose 서비스 이름 `postgres`로: `postgresql+asyncpg://xwifi:<암호>@postgres:5432/xwifi`
   - `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`를 넣는다(`POSTGRES_PASSWORD`가 비면 postgres가 기동을 거부한다).
   - `COMPOSE_PROFILES=local-db`를 넣어 두면 `deploy.sh`·`restore-db.sh` 안의 `docker compose` 명령이 항상 postgres를 포함한다(Compose 표준 변수 — 적용 뒤 `docker compose ps`로 `xwifi-postgres`가 보이는지 확인).
4. DB만 먼저 띄운다: `docker compose --profile local-db up -d postgres`
5. 덤프를 `~/db-backups/`에 두고 `bash scripts/restore-db.sh ~/db-backups/xwifi-<날짜-시각>.sql.gz`. 처음이라 safety 덤프와 backend 정지가 실패해도 스크립트는 계속 진행한다.
6. `bash scripts/deploy.sh --no-pull` — 덤프가 옛 버전이면 여기서 마이그레이션이 최신까지 올린다.
7. `files` 볼륨 데이터를 옮긴다(**수동**, 원본 볼륨 tar 또는 스냅샷 복사).
8. `backup-db.sh`와 `healthcheck.sh` cron을 등록한다. `healthcheck.sh`는 `DATABASE_URL` 호스트가 `postgres`이면 자동으로 컨테이너와 덤프 최신성까지 점검한다.
9. §5 확인 절차를 수행한다.

## 4. 복구 훈련 (분기 1회)

운영 서버가 아니라 별도 EC2(또는 별도 장비)에서 한다. 결과(소요 시간, 막힌 단계)를 기록하고 이 문서를 고친다.

- [ ] 보안 저장소에서 `.env`, TTS 자격증명, 인증서, `admin-allow.d/local.conf`, MQTT `passwd`를 실제로 꺼낼 수 있다
- [ ] 최신 백업이 하루 이내다(RDS 최근 복원 가능 시각 / `restore-db.sh --list` / S3 목록)
- [ ] RDS PITR로 임시 인스턴스를 만들 수 있다(또는 local-db 덤프를 임시 컨테이너에 복원)
- [ ] EBS 스냅샷에서 볼륨을 만들어 `files` 데이터를 읽을 수 있다
- [ ] 시나리오 b 또는 c를 처음부터 끝까지 수행해 `/health`가 ok다
- [ ] 마을·단말·계정·방송이력 건수가 원본과 맞다
- [ ] 파일함의 임의 파일 3개가 미리듣기된다(메타만 있고 실파일 없는 항목 없음)
- [ ] 시험 단말 1대가 훈련 서버에 붙어 짧은 파일 방송이 끝까지 된다(시험 단말 주소를 훈련 서버로 바꾸는 것은 **수동**)
- [ ] 걸린 시간과 데이터 손실 구간을 기록했다
- [ ] 훈련용 인스턴스·볼륨·스냅샷 복사본을 지웠다(과금)

## 5. 복구 뒤 확인

| 순서 | 확인 | 방법 |
|---|---|---|
| 1 | 앱 health | `curl -sk https://localhost/health` → `status` ok, database true, mqtt true |
| 2 | 컨테이너 | `docker compose ps`, `bash scripts/healthcheck.sh --dry` |
| 3 | 로그인 | 관리자 계정 로그인, 대시보드 숫자가 복구 전과 비슷한지 |
| 4 | 관리자 IP 제한 | `admin-allow.d/local.conf`가 운영 값으로 되돌아왔는지(없으면 제한 없음) |
| 5 | 단말 재접속 | 대시보드 온라인 수가 몇 분 안에 평소 수준으로 돌아오는지. 단말은 지터를 섞어 최대 60초 간격으로 재시도한다 |
| 6 | 단말 상태 | 몇 대의 STATUS와 CONFIG version, 마을 배정 확인. 마을 방송만 안 되면 [06 문서](06_인프라_운영.md) §15.2 |
| 7 | 파일 | 파일함 미리듣기, 개별 단말 1대에 짧은 파일 방송 |
| 8 | 실시간 방송 | 필요하면 제한 대상으로 짧게 |
| 9 | 스케줄 | 예정표가 그대로인지, 복구 공백 중 놓친 예약이 있었는지 |
| 10 | 기록 | 복구 시점에 진행 중이던 방송 기록이 종료로 정리됐는지 |
| 11 | 백업 재개 | cron 등록(`crontab -l`), 다음 날 백업·점검 알림 수신 |
