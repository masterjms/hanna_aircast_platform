# xWIFI 단말 연동 사양

기준일: 2026-09-06

대상: ESP32 P4+C6 단말, FastAPI MQTT worker, Mosquitto, Icecast, 파일 서버

관련 문서: [시스템 아키텍처](01_시스템_아키텍처.md) · [백엔드 API](03_백엔드_API.md)

## 1. 통신 원칙

단말은 세 채널을 사용한다.

| 채널 | 운영 프로토콜 | 연결 주체 | 용도 |
|---|---|---|---|
| 제어·상태 | MQTTS `:8883` | 단말이 부팅 후 연결해 유지 | 명령, CONFIG, STATUS, 결과, LWT |
| 실시간 음성 | HTTPS `GET /live/<job_id>` | `LIVE_START`를 받은 단말 | Icecast Ogg/Opus 스트림 수신 |
| 파일 | HTTPS `GET /dl/<token>` | `FILE_START`를 받은 단말 | MP3 다운로드와 Range 이어받기 |

운영 환경에서는 평문 1883과 8000을 외부에 열지 않는다. 1883은 백엔드와 Mosquitto 사이의 Docker 내부 연결, 8000은 백엔드·nginx와 Icecast 사이의 내부 연결에만 쓴다.

MQTT는 제어 메시지만 전달한다. 라이브 오디오나 MP3 본문을 MQTT payload에 넣지 않는다.

## 2. 단말 식별과 마을 배정

### 2.1 MAC 정규형

- DB, MQTT username, MQTT client ID, 토픽 경로는 콜론 없는 소문자 MAC 12자리를 쓴다.
- 예: 물리 표기 `58:E6:C5:F2:CC:74` → 정규형 `58e6c5f2cc74`
- STATUS payload의 `device`는 콜론이 있는 표기가 올 수 있다. 서버는 정규화한 뒤 처리한다.
- MQTT username과 client ID는 같은 MAC 정규형이어야 한다.

### 2.2 마을 토큰

API와 DB 관계에는 정수 `villages.id`를 쓰지만, 단말 CONFIG와 MQTT 토픽에는 별도의 숫자 문자열인 **마을 토큰**을 쓴다.

```text
주소가 있는 운영 마을: 법정동코드 10자리 + 방송 그룹 연번 2자리
예: 1281033021 + 01 = 128103302101

주소 없는 시험 마을: DB id를 8자리 0 패딩
예: id 3 = 00000003

미배정: 000000000000
```

- 단말은 숫자 8~16자리를 받고 의미를 해석하지 않은 채 토픽에 그대로 사용한다.
- 모든 자리가 `0`이면 미배정이며 마을 토픽을 구독하지 않는다.
- 연번은 단말 번호가 아니라 같은 법정리 안의 방송 그룹 번호다.
- 발급된 `village_code`는 해당 마을이 존재하는 동안 바꾸지 않는다.
- 마을을 삭제하면 사용하지 않게 된 연번은 나중에 새 마을이 사용할 수 있다.
- 주소가 없는 시험 마을에 처음 법정동코드를 넣으면 12자리 코드가 생성되고, 서버는 단말별 CONFIG와 ACL을 다시 배포한다.

## 3. MQTT 연결과 보안

### 3.1 인증값

| 항목 | 값 |
|---|---|
| host | 생산 등록 때 주입한 도메인 또는 IP |
| port | `8883` |
| TLS | TLS 1.2 이상, 서버 인증서 검증 |
| username | MAC 정규형 |
| client ID | MAC 정규형 |
| password | 서버가 발급한 단말별 임의 8자 문자열 |
| keepalive | 20초 |
| clean session | 새 연결은 진행 중 LIVE·FILE을 이어받지 않음 |

비밀번호 생성 문자 집합은 영문 대·소문자, 숫자와 `#$%^&*-_+?.~`를 사용한다. `@`, `!`, `=`는 생성하지 않는다. DB에는 생산 주입을 위해 평문이 필요하고, Mosquitto passwd에는 PBKDF2-SHA512 해시만 기록한다.

### 3.2 ACL

서버 계정은 `iotradio/#`를 읽고 쓸 수 있다. 단말 계정은 아래 최소 권한만 갖는다.

| 권한 | 토픽 |
|---|---|
| read | `iotradio/all/cmd` |
| read | `iotradio/all/config` |
| read | `iotradio/device/<자기 MAC>/cmd` |
| read | `iotradio/device/<자기 MAC>/config` |
| read | 배정된 경우 `iotradio/village/<자기 마을 토큰>/cmd` |
| write | `iotradio/device/<자기 MAC>/result` |
| write | `iotradio/device/<자기 MAC>/status` |

단말은 cmd 토픽에 발행할 수 없다. 마을 토픽은 와일드카드가 아니라 계정별 정확한 토큰 한 줄로 생성한다.

ACL 거부는 단말 로그에 명확한 publish 오류로 보이지 않을 수 있다. 접속은 되는데 마을 방송만 받지 못하면 DB 마을 배정, generated ACL, 단말 CONFIG의 `village_id`를 함께 비교한다.

### 3.3 재접속 지터

MQTT 연결이 끊기면 단말은 1초부터 재시도를 시작해 실패할 때마다 간격을 늘리고 최대 60초 간격으로 계속 시도한다. 각 재시도 시점에는 **지터**, 즉 작은 무작위 시간차를 섞어야 한다.

브로커가 재시작되면 수백·수천 대가 동시에 끊긴다. 모든 단말이 정확히 1초, 2초, 4초에 재접속하면 TLS handshake와 인증 요청이 한순간에 몰리는 thundering herd가 발생한다. 지터는 같은 backoff 단계에 있는 단말들의 재접속 시점을 흩어 브로커 CPU와 네트워크 폭주를 완화한다.

예를 들어 기준 대기가 4초라면 모든 단말이 정확히 4초를 기다리는 대신 각자 약 3.2~4.8초처럼 다른 값을 사용한다. 구체적인 난수 범위는 펌웨어 구현값으로 관리하되, **지터를 제거해서는 안 된다.**

### 3.4 연결 순서

1. Wi-Fi 연결
2. SNTP 시간 동기화
3. TLS 인증서 검증이 가능한 시간이 된 뒤 MQTTS 연결
4. LWT 등록
5. cmd·config 토픽 구독
6. retained CONFIG 수신 또는 최대 10초 대기
7. 첫 STATUS를 QoS 1로 발행
8. 이후 주기 STATUS와 상태 변경 즉시 STATUS 발행

MQTT가 끊기면 진행 중 LIVE와 FILE은 즉시 종료한다. MQTT가 복구되어도 끝난 방송을 자동 재개하지 않으며 서버가 새 `job_id`로 다시 시작해야 한다.

## 4. 토픽과 전달 정책

토픽 root의 기본값은 `iotradio`다.

| 방향 | 토픽 | 메시지 | QoS | retain |
|---|---|---|---:|---:|
| 서버→단말 | `iotradio/device/<mac>/cmd` | 개별 LIVE·FILE·OTA 명령 | 1 | false |
| 서버→단말 | `iotradio/village/<token>/cmd` | 마을 명령 | 1 | false |
| 서버→단말 | `iotradio/all/cmd` | 전체 명령 | 1 | false |
| 서버→단말 | `iotradio/all/config` | 공통 CONFIG | 1 | true |
| 서버→단말 | `iotradio/device/<mac>/config` | 단말별 마을 CONFIG | 1 | true |
| 단말→서버 | `iotradio/device/<mac>/result` | LIVE·FILE·OTA 결과·진행 | 메시지별 | false |
| 단말→서버 | `iotradio/device/<mac>/status` | STATUS·LIVE_STATS·LWT | 메시지별 | false |

명령 payload는 공백 없는 UTF-8 JSON으로 직렬화하며 **전체 1,024바이트 이하**여야 한다. 서버는 초과 payload를 발행 전에 거부한다.

명령은 절대 retained로 발행하지 않는다. retained 명령은 재접속한 단말에서 끝난 방송이나 OTA를 다시 실행시킬 수 있다.

## 5. CONFIG

### 5.1 공통 CONFIG

토픽: `iotradio/all/config`

```json
{
  "config_version": 42,
  "status_interval_sec": 30,
  "live_stats_interval_sec": 10,
  "event_qos": 0
}
```

| 필드 | 서버 기본 | 허용 범위 | 의미 |
|---|---:|---:|---|
| `config_version` | 1 | 단조 증가 | 단말 적용 버전 |
| `status_interval_sec` | 30 | 10~3600 | 주기 STATUS 간격 |
| `live_stats_interval_sec` | 10 | 1~60 | 방송 중 LIVE_STATS 간격 |
| `event_qos` | 0 | 0~1 | 주기 STATUS, 상태 변경 STATUS, LIVE_STATS, OTA_PROGRESS QoS |

### 5.2 단말별 CONFIG

토픽: `iotradio/device/<mac>/config`

```json
{
  "config_version": 42,
  "village_id": "128103302101"
}
```

- `village_id`는 마을 토큰이다.
- 미배정은 빈 retained 메시지가 아니라 `000000000000`을 명시해 보낸다.
- 공통 CONFIG와 단말별 CONFIG는 항상 같은 `config_version`을 쓴다.
- 단말의 STATUS가 DB의 version 또는 마을 토큰과 다르면 서버가 해당 CONFIG를 재발행한다. 같은 단말에 대한 불일치 재동기화는 60초 단위로 제한한다.
- 서버는 기동 직후 한 번, 이후 기본 1시간마다 전체 CONFIG를 재조정한다.

`live_ready_timeout_sec`, `live_stop_wait_sec`, `file_wait_sec`는 서버의 방송 제어값이며 공통 CONFIG로 전송하지 않는다. 이 중 준비 제한만 `LIVE_START.ready_timeout_sec`로 단말에 내려간다.

## 6. STATUS와 LWT

### 6.1 STATUS

토픽: `iotradio/device/<mac>/status`

```json
{
  "type": "STATUS",
  "device": "58:e6:c5:f2:cc:74",
  "village_id": "128103302101",
  "ip": "192.168.0.21",
  "rssi": -54,
  "state": "IDLE",
  "busy": 0,
  "live": "OFF",
  "config_version": 42,
  "p4_fw": "V.260905-1",
  "c6_fw": "V.260905-1"
}
```

| 필드 | 규칙 |
|---|---|
| `device` | 물리 MAC. 서버가 정규형으로 변환 |
| `village_id` | 단말이 현재 적용한 마을 토큰 |
| `ip`, `rssi` | 현재 Wi-Fi 정보 |
| `state` | `IDLE`, `LIVE`, `FILE`, `RF`, `OTA`, `OFFLINE` |
| `busy` | 작업 수락 가능 여부 표시 |
| `live` | `OFF`, `PLAYING`, `RECONNECTING` |
| `config_version` | 현재 적용한 CONFIG version |
| `p4_fw`, `c6_fw` | 실행 중인 펌웨어 버전; OTA 최종 확인에 사용 |

여러 내부 상태가 겹칠 때 STATUS 표시 우선순위는 `OTA > LIVE > FILE > RF > IDLE`이다. 이것은 표시 순서일 뿐 명령 선점 순서가 아니다.

상태가 바뀌면 주기를 기다리지 않고 STATUS를 즉시 발행한다. 서버는 최근 STATUS 시각과 LWT를 함께 사용하며, 기본 300초 동안 새 메시지가 없으면 오프라인으로 본다.

### 6.2 LWT

단말은 연결할 때 아래 최소 payload를 QoS 1 Last Will로 등록한다.

```json
{
  "type": "STATUS",
  "device": "58:e6:c5:f2:cc:74",
  "village_id": "128103302101",
  "state": "OFFLINE"
}
```

LWT는 단말이 직접 보내는 정상 종료 메시지가 아니라, 비정상 연결 단절을 감지한 브로커가 대신 발행한다. 정상 OTA 재부팅처럼 LWT가 없을 수 있는 흐름은 `OTA_RESULT`와 재부팅 후 STATUS를 함께 판단한다.

## 7. 공통 작업 규칙

### 7.1 `job_id`

- LIVE, FILE, OTA의 외부 식별자는 `job_id` 하나다.
- 값은 0이 아니어야 한다.
- 서버는 PostgreSQL `job_id_seq`에서 발번한다.
- QoS 1은 중복 전달될 수 있으므로 단말과 서버 모두 `job_id` 기준 멱등 처리를 한다.
- 이미 처리 중인 같은 `LIVE_START`가 QoS 1로 재전달되어 단말이 BUSY를 보내더라도, 서버는 앞서 같은 단말에서 정상 `LIVE_READY`를 받았다면 그 BUSY로 성공 상태를 덮지 않는다.

### 7.2 선착순·비선점

단말은 LIVE, FILE, OTA 중 먼저 시작한 작업을 유지한다. 새 명령이 기존 작업을 자동으로 중단시키지 않는다.

| 현재 작업 | 새 LIVE | 새 FILE | 새 OTA |
|---|---|---|---|
| 없음 | 수락 | 수락 | 수락 |
| LIVE | BUSY | `PREEMPTED_BY_LIVE` | BUSY |
| FILE | BUSY | BUSY | BUSY |
| OTA | BUSY | BUSY | BUSY |

서버도 진행 중 방송의 대상이 겹치면 새 방송을 409로 거부한다. 우선순위를 바꾸려면 기존 방송을 명시적으로 중지하고 단말 결과 또는 `STATUS state=IDLE`을 확인한 뒤 새 작업을 시작한다.

RF 상태에서 LIVE·FILE 명령의 최종 응답 규칙은 아직 장비팀 확인 대상이다. 서버는 확인 전까지 RF가 선점될 것이라고 가정하지 않는다.

### 7.3 결과 판정

최종 결과 메시지는 다음 공통 필드를 가진다.

```json
{
  "type": "FILE_RESULT",
  "ver": 267,
  "job_id": 201,
  "device": "58:e6:c5:f2:cc:74",
  "ok": true,
  "code": "OK"
}
```

- 성공·실패는 `ok`만으로 판정한다.
- `code`는 원인 표시와 로그에 사용한다.
- `*_RESULT`를 받으면 해당 단말의 작업은 끝난 것으로 본다.
- `OTA_PROGRESS`와 `LIVE_STATS`는 진행 텔레메트리이며 최종 결과가 아니다.
- 종료된 방송에 늦게 도착한 텔레메트리는 현재 상태를 되살리지 않도록 버린다.

## 8. 실시간 방송 LIVE

### 8.1 오디오 형식

| 항목 | 값 |
|---|---|
| 컨테이너 | Ogg |
| 코덱 | Opus |
| 채널 | mono |
| 샘플레이트 | 16,000 Hz |
| 목표 비트레이트 | 24 kbps |
| 프레임 | 40 ms |
| Ogg page | 40 ms, page당 최대 1 frame |

브라우저, `LIVE_START`, Icecast source, 단말 디코더 설정이 모두 일치해야 한다. 서버는 WSS로 받은 Ogg bytes를 재인코딩하지 않는다.

### 8.2 LIVE_START

```json
{
  "type": "LIVE_START",
  "job_id": 101,
  "stream_url": "https://example.invalid/live/101",
  "codec": "opus",
  "frame_ms": 40,
  "sample_rate": 16000,
  "record_flash": 1,
  "ready_timeout_sec": 30
}
```

| 필드 | 필수 | 규칙 |
|---|---|---|
| `job_id` | 예 | 0이 아닌 값 |
| `stream_url` | 운영에서 예 | 단말이 그대로 GET하는 완성 URL, 운영은 HTTPS |
| `codec` | 아니오 | 서버는 `opus` 명시 |
| `frame_ms` | 아니오 | 서버는 40 명시 |
| `sample_rate` | 아니오 | 서버는 16000 명시 |
| `record_flash` | 아니오 | 단말 생략 기본 0; 현재 API 선택 기본 true이며 서버가 0/1 명시 |
| `ready_timeout_sec` | 아니오 | 기본 30, 1~60초 |

`stream_url`은 NUL을 포함하는 단말 버퍼 한계가 512바이트이므로 충분히 짧아야 하며, 서버는 UTF-8 512바이트 초과를 거부한다. 단말은 URL의 path를 해석하거나 마을·작업 ID로 재조립하지 않는다.

서버 순서는 다음과 같다.

1. 대상과 겹침을 확인한다.
2. `job_id`와 이벤트를 만든다.
3. Icecast의 `/live/<job_id>` mount에 source를 먼저 연결한다.
4. 같은 `stream_url`을 모든 대상 토픽에 `LIVE_START`로 발행한다.
5. 브라우저가 응답의 WSS 경로로 업링크를 연결한다.
6. 업링크가 기본 30초 안에 한 번도 연결되지 않으면 무음 방송으로 보고 자동 종료한다.

### 8.3 LIVE_READY

```json
{
  "type": "LIVE_READY",
  "ver": 267,
  "job_id": 101,
  "device": "58:e6:c5:f2:cc:74",
  "ok": true,
  "code": "OK"
}
```

| `ok` | `code` | 의미 |
|---:|---|---|
| true | `OK` | P4 오디오 출력 준비 완료 |
| false | `BUSY` | 다른 작업 진행 중 |
| false | `BAD_FIELD` | URL scheme 또는 `job_id` 오류 |
| false | `TIMEOUT` | P4 준비 제한 초과 |

외부 AMP 모델은 전원과 안정화가 끝난 뒤에만 성공 READY를 보낸다. `ready_timeout_sec`는 AMP 준비 시간보다 길어야 한다.

READY는 Icecast 연결 전에 오므로 방송 청취 성공 증거가 아니다. 실제 청취는 `STATUS.live=PLAYING`으로 확인하고, 연결 실패는 후속 `LIVE_RESULT ok=false`로 받는다.

### 8.4 스트림 단절과 재접속

Icecast만 끊기면 단말은 같은 `stream_url`로 최대 3회 재접속한다.

```text
끊김 감지
→ STATUS live=RECONNECTING 즉시 발행, P4 LIVE 유지, 스피커 무음
→ 0.5초 / 2초 / 4초 간격으로 같은 URL 재접속
├─ 성공: STATUS live=PLAYING 즉시 발행, 같은 방송 계속
└─ 실패: LIVE_RESULT ok=false, STATUS state=IDLE live=OFF
```

서버는 방송이 끝날 때까지 같은 mount와 source를 유지해야 한다. source를 재시작해야 한다면 단말의 약 6.5초 재시도 창 안에 같은 mount로 복원해야 한다. MQTT까지 끊기면 LIVE 작업 자체가 종료되므로 Icecast 재접속으로 복구되지 않는다.

### 8.5 LIVE_STATS와 지터 버퍼

LIVE_STATS는 방송 중 공통 CONFIG의 간격과 QoS로 발행한다. 대표적으로 `p4_buffer_ms`, underrun 누계 등 수신 품질을 포함하며, 서버는 방송·단말별 최신값만 유지한다.

현재 장비 기준 지터 버퍼 참고값은 다음과 같다.

| 항목 | 값 |
|---|---:|
| 재생 전 prebuffer | 38 frame |
| 과다 적재 trim 시작 | 65 frame |
| trim 목표 | 50 frame |
| hard cap | 75 frame |

40 ms frame 기준이다. 이 값과 Icecast queue 16 KiB, burst 비활성 조합은 WAN·TLS 실제 회선에서 underrun과 지연을 다시 측정해야 한다.

### 8.6 LIVE_STOP과 LIVE_RESULT

```json
{"type":"LIVE_STOP","job_id":101}
```

종료 순서는 반드시 다음과 같다.

1. 서버가 `LIVE_STOP`을 QoS 1로 발행한다.
2. Icecast mount와 source를 유지한 채 대상별 `LIVE_RESULT`를 기다린다.
3. 모든 결과가 오거나 `live_stop_wait_sec` 기본 10초가 지나면 이벤트를 종료한다.
4. 마지막으로 source를 닫는다.

source를 먼저 닫으면 단말이 네트워크 장애로 해석해 재접속을 시작해 정상 종료가 늦어진다.

| `ok` | `code` | 의미 |
|---:|---|---|
| true | `STOPPED_BY_SERVER` | 정상 중지 |
| false | `ABORTED` | P4가 작업 중단 |
| false | `TIMEOUT` | 15초간 frame이 없어 정리 |
| false | `NOT_ACTIVE` | 해당 `job_id`의 LIVE가 없음 |

## 9. 파일 방송 FILE

### 9.1 파일 제약

- 형식: MP3
- 서버 업로드 상한: 2.5 MiB, 즉 2,621,440바이트
- 재생 시간 상한: 600초
- 단말 재생 watchdog: 약 10분 30초
- 무결성: 전체 byte 수와 SHA-256 64 hex
- 단말 전달 파일명: ASCII 영문·숫자·`-`, `_`와 `.mp3`
- 다운로드 토큰 기본 TTL: 600초
- HTTP Range 지원: 필수 운영 기능

서버의 한국어 표시명과 단말 저장 파일명은 분리한다. 단말에는 짧은 ASCII 파일명을 보낸다.

### 9.2 FILE_START

```json
{
  "type": "FILE_START",
  "job_id": 201,
  "size": 73990,
  "resume_offset": 0,
  "sha256": "071e5e40ad46b332a4f6d013625dcccd522ecc5f72336a088789bd3d4ad3d556",
  "https_url": "https://example.invalid/dl/short-token",
  "file_name": "notice.mp3",
  "store_flash": 0,
  "autoplay": 1
}
```

| 필드 | 규칙 |
|---|---|
| `job_id` | 0이 아닌 값 |
| `size` | 1~2,621,440 |
| `resume_offset` | 서버는 항상 0. 단말 내부 이어받기와 별개 |
| `sha256` | 실제 MP3 bytes의 SHA-256 |
| `https_url` | 만료 전 여러 Range 요청에 재사용 가능해야 함 |
| `file_name` | `.mp3`, 64바이트 이내 안전한 ASCII 이름 |
| `store_flash` | 현재 API 기본 false, 서버가 0/1 명시 |
| `autoplay` | 현재 API 기본 true, 서버가 0/1 명시 |

다운로드가 끊기면 단말은 받은 byte offset부터 `Range: bytes=<offset>-`로 최대 3회 재요청한다. 간격은 0.5초, 2초, 4초이며 URL 토큰은 재시도 내내 유효해야 한다. 4xx는 즉시 실패하고, 5xx와 연결 실패는 재시도한다. 서버가 Range를 지원하지 않고 200 전체 응답을 보내면 단말은 처음부터 다시 받는다.

`store_flash=0`이면 재생만 하고 영구 저장하지 않는다. 10분을 넘길 수 있는 방송은 LIVE·FILE 모두 저장 옵션을 0으로 보내야 한다.

### 9.3 FILE_RESULT와 방송 종료

```json
{
  "type": "FILE_RESULT",
  "ver": 267,
  "job_id": 201,
  "device": "58:e6:c5:f2:cc:74",
  "ok": true,
  "code": "OK",
  "last_offset": 0
}
```

`FILE_RESULT ok=true code=OK`은 다운로드와 SHA-256 검증이 끝났다는 뜻이다. `autoplay=true`이면 그 시점부터 재생을 시작한다. 서버는 대상 전체의 성공 결과가 모인 시각을 `playing_since`로 기록하고, 음원 길이와 5초 여유가 지난 뒤 자연 종료 처리한다. `autoplay=false`이면 결과 수집 후 종료한다.

| `ok` | `code` | 의미 |
|---:|---|---|
| true | `OK` | 다운로드·검증 완료, autoplay면 재생 시작 |
| true | `STOPPED_BY_SERVER` | 서버 중지로 종료 |
| false | `BAD_FIELD` | URL, 확장자, 크기, ID 등 입력 오류 |
| false | `BUSY` | 다른 작업 중 |
| false | `PREEMPTED_BY_LIVE` | LIVE 중 새 FILE 거부 |
| false | `NET_ERROR` | 최종 다운로드 실패 |
| false | `VERIFY_FAIL` | SHA-256 불일치 |
| false | `STORAGE_FAIL` | 영구 저장 실패; 검증된 음원 재생은 가능 |
| false | `NO_MEMORY` | 수신 버퍼 부족 |
| false | `CREDIT_TIMEOUT` | P4가 chunk를 가져가지 못함 |
| false | `NOT_ACTIVE` | 정지할 작업 없음 |

시작·중지 결과 대기 상한은 모두 `file_wait_sec`를 사용하며 현재 기본 30초, 허용 10~60초다.

### 9.4 FILE_STOP

```json
{"type":"FILE_STOP","job_id":201}
```

다운로드 중인 작업과 autoplay 재생 중인 작업을 모두 중지한다. 서버는 결과가 모두 오거나 대기 상한이 지나면 이벤트를 종료한다.

## 10. OTA 계약

서버 애플리케이션의 OTA API와 화면은 아직 구현되지 않았지만 단말 계약은 다음으로 확정한다.

- 명령은 `OTA_START` 하나만 사용한다.
- `job_id`, HTTPS package URL, size, SHA-256와 생산용 서명 검증 정보를 제공한다.
- 패키지 이름은 `IOT_RADIO.pkg`다.
- 단말이 package 내부를 보고 P4·C6 대상 firmware를 판단한다.
- 별도의 승인·적용 명령은 없다.
- 단말은 다운로드, 검증, flash 적용, 재부팅까지 자동 진행한다.
- `targets`, `reboot` 필드를 사용하지 않는다.
- `OTA_START`는 QoS 1, retain false다.

진행 메시지:

```json
{
  "type": "OTA_PROGRESS",
  "job_id": 301,
  "state": "DOWNLOADING",
  "percent": 50,
  "received": 3600000,
  "total_size": 7297148
}
```

진행 state는 `ACCEPTED`, `PREPARE`, `DOWNLOADING`, `VERIFYING`이다. 이 메시지는 공통 CONFIG의 `event_qos`를 따르고 최신 상태만 의미한다.

최종 메시지는 `OTA_RESULT`이며 job당 한 번, QoS 1이다.

| `ok` | `code` | 의미 |
|---:|---|---|
| true | `OK` | 적용 단계 완료, 곧 연결 종료·재부팅 |
| false | `BAD_FIELD` | URL, ID, size 오류 |
| false | `BUSY` | 다른 작업 진행 중 |
| false | `NO_MEMORY` | PSRAM 확보 실패 |
| false | `DL_FAIL` | package 다운로드 실패 |
| false | `VERIFY_FAIL` | SHA-256 또는 서명 검증 실패 |
| false | `APPLY_FAIL` | flash 적용 실패 |

`OTA_RESULT ok=true`만으로 최종 성공을 선언하지 않는다. 재부팅 후 새 STATUS의 `p4_fw`, `c6_fw`가 목표 버전인지 확인해야 롤백까지 구분할 수 있다.

## 11. 생산 등록과 현장 설치

### 11.1 QR 데이터

생산 라벨의 기본 데이터는 파이프 구분 5필드다.

```text
MAC|P4_MODEL|P4_VERSION|C6_MODEL|C6_VERSION
```

화면은 바코드 리더의 한글/영문 IME 상태와 무관하게 값을 받아야 한다. MAC은 필수이며 나머지 하드웨어 필드는 수동 등록에서는 비워도 된다.

### 11.2 Web Serial 주입

- 지원 브라우저: Chrome 또는 Edge의 HTTPS 페이지
- serial: 115200 bps
- 생산 설정 진입: 장비 정의에 따른 KEY1+KEY4 조합
- 서버 등록 화면에서 credential을 먼저 발급받고, 단말과 DB에 같은 값을 확정한다.

주입 frame:

```text
@SSID=<site wifi>
@PASSWORD=<site wifi password>
@SERVER=<hostname>
@MQTTID=<mac_nocolon>
@MQTTPW=<8-char password>
@END
```

현재 서버의 credential 응답은 `server_host`, MQTT username, password를 제공한다. 현장 Wi-Fi 값은 설치 환경에서 입력한다. 주입 후 GET/verify로 값을 읽어 비교하고 설정 모드를 종료한다.

전체 serial protocol에는 RF·색상·PIR·배터리·재부팅 설정도 있을 수 있으나, 운영 서버의 단말 등록 기능이 직접 관리하는 범위는 네트워크 5개 항목이다.

### 11.3 설치 검증

1. 단말의 MAC·모델·버전을 QR로 등록한다.
2. 서버·MQTT credential과 현장 Wi-Fi를 serial로 주입한다.
3. 마을과 선택적으로 구역·설치 위치를 배정한다.
4. 서버가 단말별 retained CONFIG와 ACL을 배포했는지 확인한다.
5. STATUS의 마을 토큰, config version, firmware, RSSI를 확인한다.
6. 개별 단말 토픽으로 5초 미만의 짧은 시험 음원을 `store_flash=0`으로 방송한다.
7. 스피커 출력과 FILE_RESULT를 확인한다.

생산·현장 시험에서는 `all/cmd`를 사용하지 않는다. 여러 대를 동시에 시험해야 해도 각 단말의 개별 토픽을 사용한다.

## 12. 서버 구현 체크리스트

- [ ] MAC은 모든 입력에서 정규화한다.
- [ ] DB 마을 ID와 MQTT 마을 토큰을 혼용하지 않는다.
- [ ] CONFIG 두 토픽에 같은 `config_version`을 쓴다.
- [ ] 미배정은 12자리 0 토큰으로 명시한다.
- [ ] 명령 payload는 1,024바이트 이하이고 retain=false다.
- [ ] LIVE source를 연 뒤 LIVE_START를 보낸다.
- [ ] LIVE_READY와 실제 PLAYING을 구분한다.
- [ ] 종료 시 LIVE_STOP 결과를 기다린 뒤 source를 닫는다.
- [ ] FILE URL은 Range와 토큰 재사용을 지원한다.
- [ ] QoS 1 중복과 종료 후 늦은 텔레메트리를 멱등 처리한다.
- [ ] OTA 성공은 재부팅 후 firmware version으로 확인한다.
- [ ] MQTT backoff에 지터가 있는지 실물 단말과 대규모 재접속 시험으로 확인한다.
