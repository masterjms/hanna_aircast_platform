# xWIFI 현행 문서

기준일: 2026-09-06

코드 기준: `main` / `69f9abe`

대상: 운영 서버, 관리자 웹, PostgreSQL, MQTT·Icecast·HTTP 단말 연동

이 폴더는 xWIFI 운영 시스템의 **현재 동작과 확정된 계약**을 한곳에서 읽기 위한 문서 세트다. `docs`에 있던 설계서, 장비팀 전달 문서, 구축 지시서, 시험 가이드, 다이어그램과 현재 코드·마이그레이션·배포 설정을 함께 대조해 작성했다.

기존 문서는 결정 배경과 시험 이력을 보존하는 자료다. 신규 개발과 운영 판단은 이 폴더를 먼저 보고, 더 오래된 근거가 필요한 경우에만 기존 문서를 찾아간다.

## 문서 해석 원칙

같은 항목이 서로 다를 때는 다음 순서로 현재값을 판정했다.

1. 단말이 실제로 송수신하는 형식은 가장 최신 ESP32 통신·네트워크·생산 등록 사양을 따른다.
2. 서버가 현재 제공하는 API와 동작은 실행 코드와 테스트를 따른다.
3. DB 구조는 Alembic `0017`까지 적용한 결과와 SQLAlchemy 모델을 따른다.
4. 배포·포트·리소스 한도는 현재 Docker Compose와 `infra`, `scripts` 설정을 따른다.
5. 화면 범위는 현재 React 라우트와 페이지 구현을 따른다.

이 원칙 때문에 문서상의 기본값과 서버 UI 기본값이 다를 수 있다. 예를 들어 단말은 `LIVE_START.record_flash`가 생략되면 `0`으로 해석하지만, 현재 서버 API는 사용자 선택의 기본값을 `true`로 두고 항상 `0` 또는 `1`을 명시해 보낸다.

## 공통 용어

| 용어 | 의미 |
|---|---|
| DB 마을 ID | `villages.id`. 관리자 API와 DB 관계에 쓰는 정수 키 |
| 마을 토큰 | MQTT 토픽과 단말 CONFIG에 쓰는 숫자 문자열. 보통 `법정동코드 10자리 + 방송 그룹 연번 2자리` |
| MAC | 콜론을 제거한 소문자 12자리 단말 식별자. MQTT username과 client ID에도 사용 |
| `job_id` | LIVE, FILE, OTA가 공유하는 0이 아닌 방송·작업 ID |
| 방송 이벤트 | 서버가 발행한 한 번의 방송을 나타내는 `broadcast_events` 행 |
| 단말 이벤트 | 방송에 대한 단말 한 대의 결과·텔레메트리를 나타내는 `device_events` 행 |
| 업링크 | 브라우저 마이크에서 서버로 올라오는 Ogg/Opus WebSocket 스트림 |
| source | 백엔드가 Icecast mount로 오디오를 밀어 넣는 HTTP source 연결 |

## 반드시 함께 지켜야 할 규칙

- 단말 프로토콜의 필드명, 토픽, QoS, payload 상한을 서버에서 임의로 바꾸지 않는다.
- 관리자 범위는 화면 숨김이 아니라 백엔드 조회·제어 단계에서 강제한다. 범위는 조직 트리를 따르고 마을의 주소는 트리의 입력값이 아니다.
- 방송 명령은 retained 메시지로 발행하지 않는다. CONFIG만 retained 메시지다.
- 단말 다운로드는 장기 공개 URL이 아니라 만료되는 `/dl/<token>`을 사용한다.
- 이력은 남되 참조당하는 쪽(단말·계정·파일)의 삭제를 막지 않는다. 이력이 필요한 값은 그 시점의 스냅샷으로 자기 행에 갖는다.
- 목록 API는 건수에 비례해 질의를 늘리지 않는다. 대상·이름·담당 마을은 한 번에 모아 읽고 재사용한다.
- 실시간 방송은 Icecast source를 연 뒤 `LIVE_START`를 발행한다.
- 실시간 방송 종료는 `LIVE_STOP → 단말 결과 대기 → source 종료` 순서다.
- DB 변경은 Alembic 마이그레이션과 모델을 같이 바꾸고 이 문서 세트도 같은 커밋에서 갱신한다.
- 운영 비밀값, 인증서 개인키, 실제 접속 IP와 개인 PC 경로를 문서나 Git에 기록하지 않는다.

## 현재 남은 결정·작업

아래는 과거 변경 이력이 아니라 아직 닫히지 않은 현재 항목이다.

1. 단말이 RF 상태일 때 `LIVE_START`와 `FILE_START`를 어떻게 응답할지 장비팀 최종 확인이 필요하다.
2. (해결 2026-09-09) 자동 스케줄 구현. 남은 것: 매월 「말일」, 시작·종료 기간 — 스케줄 설계 §9.
3. OTA 패키지 스키마, 서명 키 관리, 업로드·배포 API와 운영 화면을 구현해야 한다.
4. 전체 이력 검색·필터·상세 조회 API와 화면을 구현해야 한다.
5. `daily_cost_summary` 생성 배치와 앱 내부 비용 조회 API·화면을 구현해야 한다.
6. 운영 로그인 토큰의 브라우저 보관 방식을 `httpOnly` 쿠키로 전환할지 보안 검토가 필요하다. 현재는 `localStorage`를 쓴다.
7. WAN·TLS 환경에서 Icecast queue와 단말 지터 버퍼 값을 실제 회선으로 검증해야 한다.
8. (해결 2026-09-08) 진행 중 방송의 가시성을 대상 단말의 소속 마을 기준으로 판정한다.
9. 방송 성공률과 시작 지연을 정확히 계산할 수 있도록 시작 당시 대상 MAC snapshot, 단계별 시각, 표준 실패 원인과 운영 metric 저장소를 추가해야 한다.
10. 계정 역할은 4계층(최고·시도·시군·마을)으로 확정했다(`spec/xWIFI_관리자_계층_설계_260908.md`). 게스트 역할은 두지 않는다. 계정별 파일함·이력·스케줄 분리(문제점 28·32번)는 파일함을 전체 공용으로 유지하기로 하여 별도 설계로 남긴다.
11. 산본마을 경계 폴리곤이 비어 있다. 경기도 「구역의 도형」 자료로 `scripts/import_boundaries.py`를 다시 실행해야 한다(자료 이용 승인 만료 2026-10-01).
